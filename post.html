Why I stopped tuning for throughput first

25 October 2026 6 min read

For a long time I treated every slow system as a throughput problem. Most of the time it was a waiting problem, and the two need very different fixes.

When a queue backs up, the instinct is to make the consumer faster. Profile it, trim the hot loop, add a thread. Sometimes that works. More often the consumer is already quick and spends most of its life waiting on something it cannot see: a lock, a slow neighbour, a request that has not arrived yet.

Measure the wait, not the work

The first habit worth building is recording how long an item sits before anyone touches it. Work time tells you how good the code is. Wait time tells you how good the system is, and it is usually the larger number.

A fast worker behind a bad queue is still a slow system.

A small example. Stamp each item on the way in, and read the difference on the way out:

using Clock = std::chrono::steady_clock;

struct Job {
    Clock::time_point enqueued;
    Payload data;
};

void worker(Queue<Job>& q) {
    while (auto job = q.pop()) {
        auto waited = Clock::now() - job->enqueued;
        // the number that matters
        metrics.record_wait(waited);
        handle(job->data);
    }
}

What the numbers usually say

  • High wait, low work: the bottleneck is upstream or in coordination, not in your code.
  • Low wait, high work: now it really is a throughput problem, and profiling pays off.
  • Both high: fix the wait first, because it hides how slow the work really is.

None of this is new. It is just easy to forget when the profiler is already open and the flame graph looks so inviting.

If you only change one thing after reading this, add the wait metric. Everything else follows from what it shows you.
