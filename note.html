Caching strategies

Updated 25 October 2026 7 min read

A cache trades a little correctness for a lot of speed. Choosing a pattern is really choosing which kind of wrong you can live with.

Reading from memory is thousands of times faster than reading from a database across the network, and most systems read far more than they write. Put the two facts together and a cache is the cheapest speed-up available. The catch is that every cached value is a copy, and copies drift from the original.

Where the cache sits

Before picking a pattern, decide who is responsible for filling the cache. Either your application does it, or the cache does it on your behalf. Everything else follows from that choice.

Cache-aside

The application checks the cache first. On a miss it reads the database, stores the result, and returns it. The cache knows nothing about the database, which makes this the simplest pattern to add to an existing system, and the most common.

def get_user(user_id):
    key = f"user:{user_id}"

    cached = cache.get(key)
    if cached is not None:
        return cached                    # hit

    user = db.query_user(user_id)        # miss: go to the source
    cache.set(key, user, ttl=300)        # keep it for five minutes
    return user

def update_user(user_id, fields):
    db.update_user(user_id, fields)
    cache.delete(f"user:{user_id}")      # next read repopulates it

Notice that a write deletes the cached value instead of updating it. Deleting is safer: two concurrent writers can set the cache in the wrong order, but they cannot delete in the wrong order.

Read-through and write-through

Here the cache sits in front of the database and talks to it directly. A read-through cache loads missing values itself. A write-through cache writes every update to the database before it acknowledges, so the two never disagree. You pay for that guarantee with slower writes.

Write-behind

The cache acknowledges the write immediately and flushes to the database later, often in batches. Writes become very fast and the database sees far less traffic. If the cache dies before it flushes, those writes are gone.

Comparing the patterns

Cache-asideThe application, on a missDatabase, then invalidateStale reads until invalidation
Read-throughThe cache, on a missUsually paired with write-throughSlow first request for every key
Write-throughThe cache, on every writeCache and database togetherHigher write latency
Write-behindThe cache, on every writeCache now, database laterLost writes if the cache fails

Invalidation is the hard part. A time-to-live is a safety net, not a strategy. It limits how long a value can be wrong, but it does nothing to make it right in the meantime.

When a popular key expires

Imagine a key read ten thousand times a second that expires at noon. For a moment every request misses, and all of them hit the database together. This is a cache stampede, and it tends to happen exactly when load is highest.

A cache hides your database's limits right up until it doesn't.

Three habits blunt it:

  1. Let only one request rebuild a missing value while the others wait for it.
  2. Add a small random jitter to every time-to-live, so keys do not expire in unison.
  3. Serve the stale value while a fresh one loads in the background.

What to remember

Start with cache-aside and a short time-to-live, because it is easy to reason about and easy to remove. Reach for write-through when readers must never see stale data, and for write-behind only when you can afford to lose the last few writes. Whatever you choose, measure the hit rate: a cache that rarely hits is just extra latency.
