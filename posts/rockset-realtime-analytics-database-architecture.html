1. The Real-Time Analytics Dilemma

Modern data-driven applications demand operational analytics: customer-facing dashboards, real-time personalization, fraud detection engines, and IoT monitoring. These workloads require executing complex analytical SQL queries (aggregations, filters, multi-way joins) over streaming, semi-structured JSON documents with sub-second query latencies and sub-second data freshness.

Existing database categories fail when forced into this intersection:

  • Cloud Data Warehouses (Snowflake, BigQuery): Built for batch or micro-batch ETL pipelines. Ingestion latency ranges from several minutes to hours, and per-query costs and concurrency limits prohibit high-QPS live application serving.
  • Operational Relational Databases (PostgreSQL, MySQL): Excellent for OLTP point lookups, but lack vectorized columnar execution engines. Analytical scans over millions of rows saturate CPU cores and cause lock contention on live transactional tables.
  • Search Engines (Elasticsearch, OpenSearch): Fast for keyword filtering, but highly inefficient at numeric aggregations (Doc Values require heavy memory) and completely incapable of executing distributed SQL joins without pre-denormalization.
The Rockset Design Goal: Build a cloud-native database engine that consumes raw streaming JSON, automatically builds comprehensive indexes without manual schema declarations, and serves complex SQL queries in under 50 milliseconds with zero data pipeline lag.

2. The Aggregator-Leaf-Tailer (ALT) Architecture

To decouple compute, storage, and ingestion, Rockset pioneered the Aggregator-Leaf-Tailer (ALT) architecture. Unlike monolithic database architectures where a single process handles writes, indexing, and queries, ALT splits responsibilities into three independently scalable tiers:

3. The Tailer Tier: Continuous Streaming & Smart Schemas

The Tailer is the stateless entry point for external data streams. Tailers maintain persistent pull connections to sources (e.g., subscribing to Kafka partition offsets or polling AWS S3 event notifications).

Dynamic Type Inference: Smart Schemas

In traditional databases, developers must define a schema up-front (CREATE TABLE). When a developer introduces a new nested JSON field or sends mixed data types (e.g., "age": 28 in one record and "age": "28" in another), standard databases reject the record or require schema migration downtime.

Rockset's Tailer implements Smart Schema: it accepts arbitrary, deeply nested semi-structured JSON without schema declarations. Each document is shredded into paths, and data types are bound dynamically at the value level. A document with mixed types is indexed cleanly without type coercion errors.

4. The Leaf Tier: Stateful Shards & Inverted LSM-Trees

The Leaf tier constitutes the stateful storage core of Rockset. Collections are partitioned into multiple horizontal shards, and each Leaf node hosts multiple shard replicas.

Under the hood, every shard on a Leaf node is powered by an embedded instance of RocksDB, Facebook's high-performance key-value store built on a Log-Structured Merge-tree (LSM-tree):

  • Sequential Write Speed: LSM-trees convert random incoming document updates into sequential appends to an in-memory MemTable and Write-Ahead Log (WAL), providing high write throughput.
  • The Converged Index: As records enter the Leaf, the engine does not merely store raw bytes. It shreds every field and writes simultaneously to a Row Store, Column Store, and Inverted Search Index—all mapped into RocksDB key-value pairs.
  • Local NVMe Block Cache: Leaves maintain hot data blocks in local NVMe solid-state storage. Queries that hit the local cache bypass network hops entirely, executing in sub-millisecond time.

5. The Aggregator Tier: Distributed Query Coordination

The Aggregator tier is a stateless distributed SQL execution engine. When an application issues an ANSI SQL query:

  1. Parsing & Logical Planning: The Aggregator validates SQL syntax, resolves collection names, and constructs a logical query tree.
  2. Cost-Based Optimization & Predicate Push-down: The optimizer inspects available index statistics (from the Converged Index) to decide whether to evaluate a filter using the Inverted Index, a point lookup using the Row Index, or a vectorized scan using the Columnar Index.
  3. Leaf Fan-Out: The Aggregator partitions the physical plan into distributed sub-queries and broadcasts them to the specific Leaf nodes holding relevant shards.
  4. Stream Merging & Final Aggregations: Leaves stream intermediate result batches back to the Aggregator. The Aggregator performs final global joins, sorts (ORDER BY), and limit evaluations before returning the payload to the client.

6. RocksDB-Cloud & Serverless Compaction

Standard RocksDB stores SST (Sorted String Table) files on local attached disks. If a node fails, its data must be rebuilt from scratch, and scaling compute requires re-sharding local storage.

Rockset pioneered RocksDB-Cloud, extending the storage engine to treat cloud object storage (AWS S3) as its durable backing store:

Storage-Compute Decoupling: When a Leaf node flushes its MemTable, the resulting immutable SSTable is written directly to AWS S3. Local NVMe disks function strictly as ephemeral read/write caches. If a Leaf node crashes, a replacement node can spin up in seconds, attach the existing SST manifests from S3, and begin serving queries immediately via zero-copy clone mechanisms.

Remote Compaction

In standard LSM-trees, background compactions (merging and deduplicating sorted runs across Level $L_i \to L_{i+1}$) consume 30–50% of CPU and IOPS bandwidth, causing severe "write stalls" and query latency tail spikes. Rockset offloads compactions to a dedicated, autoscaling fleet of Serverless Remote Compactors. Leaf query nodes remain 100% dedicated to serving low-latency user queries.

7. End-to-End Query & Ingestion Lifecycle

Lifecycle Stage Responsible Component Latency Budget Core Mechanism
1. Stream Consumption Tailer Worker < 50 ms Continuous pull from Kafka/Kinesis topic partitions.
2. Document Shredding Tailer Worker < 10 ms Smart Schema path decomposition into Converged KV pairs.
3. Shard Ingestion & WAL Leaf Node (RocksDB) < 20 ms Sequential append to MemTable and WAL; immediately queryable!
4. SQL Query Optimization Aggregator < 2 ms Push-down predicate compilation & index selection.
5. Leaf Vector Scan Leaf Node < 15 ms SIMD vectorized scan on local NVMe columnar cache blocks.
6. Final Merge & Return Aggregator < 5 ms Global merge, hash join completion, JSON serialization.

8. Key Architectural Takeaways

  • Decouple Ingestion from Querying: ALT separates write pipelines (Tailers), storage indexing (Leaves), and query execution (Aggregators), preventing high-throughput streaming writes from starving user queries.
  • LSM-Trees Power Real-Time Ingestion: RocksDB turns arbitrary nested JSON mutations into high-speed sequential writes, making updates visible in sub-second time.
  • RocksDB-Cloud Solves Statefulness: Backing immutable SSTables with S3 provides infinite durability, fast crash recovery, and instant serverless compute scaling.
  • Remote Compactions Eliminate Tail Latency: Moving heavy background merges to external worker fleets protects query nodes from CPU spikes and write stalls.
