Shopify Ghostferry: Live MySQL Shard Migration with Zero Downtime

When an enterprise e-commerce merchant outgrows its database shard, moving hundreds of gigabytes of live transactional data without interrupting checkouts is an engineering tightrope. Discover how Shopify's open-source tool Ghostferry copies live MySQL shards with concurrent binlog streaming, sub-500ms cutover write freezes, and zero data loss.

1. Multi-Tenant Sharding at Shopify

Shopify powers millions of online storefronts globally, processing billions in Gross Merchandise Volume (GMV). From its inception, Shopify adopted a shared-nothing, multi-tenant database sharding strategy:

  • Tenant Scoping: All core database tables (orders, line items, customers, inventory) carry a foreign key shop_id.
  • Pod Architecture: A "Pod" consists of independent MySQL primary-replica clusters, Redis instances, and Memcached caches. Each shop is assigned deterministically to a specific database pod.
  • Shared Infrastructure: Multiple smaller merchants co-exist on the same physical MySQL shard to optimize infrastructure costs and server utilization.

2. The Noisy Neighbor Problem & Flash Sales

While multi-tenant sharding is highly cost-effective, it introduces the "Noisy Neighbor" failure mode:

When a high-profile merchant launches a flash sale (e.g., Gymshark Black Friday drop or a celebrity makeup release), thousands of checkouts per second hit a single MySQL shard. CPU utilization hits 100%, disk IOPS saturate, and connection pools exhaust. Neighboring small businesses co-located on that same database shard suffer catastrophic latency degradation and dropped checkouts through no fault of their own.

The solution is online re-sharding: moving the mega-merchant to a dedicated, isolated MySQL pod. However, scheduling multi-hour maintenance windows where the merchant must stop selling is completely unacceptable in modern e-commerce.

4. Row-Based Binlog Streaming & The Out-of-Order Race

A naive migration tool copies all rows first and then replays binlogs. The critical challenge is the interleaving race condition:

The Classic Race Condition:

  1. T0: Ghostferry plans to copy rows 1 to 1000.
  2. T1: An active customer updates row 500 on the Source database. MySQL appends this UPDATE to its binary log.
  3. T2: Ghostferry's binlog streamer reads the UPDATE event from the binlog and applies it to the Target database.
  4. T3: Ghostferry's batch copier finally executes SELECT * FROM table WHERE id BETWEEN 1 AND 1000. It reads row 500's state from before the update (if reading from a lagging snapshot) and writes it to the Target!
  5. Result: Stale data overwrites the newer update!

Ghostferry solves this through Write Invalidation & Row Fingerprinting. Ghostferry starts binlog streaming before copying table data. If a row is updated in the binlog while a batch is in flight, Ghostferry marks that row range as invalidated, guaranteeing that the target row reflects the latest serialized binlog event.

5. Concurrent Batch Copying & Watermarks

Copying hundreds of gigabytes requires high concurrency without starving production database traffic:

  • Cursor-Based Primary Key Pagination: Ghostferry slices tables by primary key: WHERE id >= ? AND id < ? AND shop_id = ?. This avoids expensive table scans and preserves MySQL InnoDB buffer pool locality.
  • Adaptive Throttling: Ghostferry continuously monitors the Source database's replication lag (Seconds_Behind_Master) and thread concurrency. If production CPU exceeds 80% or lag spikes, Ghostferry reduces batch sizes and pauses copier threads.

6. The 500ms Atomic Cutover Sequence

Once historical table copying completes and the binlog streaming lag drops below 100ms, Ghostferry initiates the final cutover. The merchant experiences only a sub-500ms pause:

Step 1: Application Tenant Lock (~50ms) Shopify's routing proxy sets shop state to "READ-ONLY". Inbound customer writes are momentarily queued or delayed by ~200ms at the HTTP layer. Step 2: Binlog Catch-Up (~150ms) Ghostferry waits for the Target to consume the final few binlog events until binlog position matches Source position exactly. Step 3: Verification & Checksum (~50ms) Ghostferry confirms that Source and Target row counts match for the migrating shop. Step 4: Atomic Routing Switch (~10ms) The routing tier (Proxy / ZooKeeper metadata) updates the shop's pod pointer from Source Pod to Target Pod. Step 5: Release Tenant Lock (~10ms) The shop returns to READ-WRITE on the Target Shard. Queued HTTP requests proceed! Total customer-perceived freeze: < 500 milliseconds!

7. Verification & Checksumming Mechanics

To guarantee 100% data integrity before releasing production traffic onto the new shard:

  • Row Hash Verification: Ghostferry computes CRC32/MD5 hashes over concatenated column values across chunks of rows on both Source and Target.
  • Foreign Key Integrity Check: Verifies that all associated child records (e.g., line items referencing order IDs) have transferred without orphan references.

8. Key Architectural Takeaways

  • Binlog Tailing Enables Live Migrations: Combining table chunk copying with continuous Row-Based Replication (RBR) binlog tailing decouples migration duration from downtime duration.
  • Protect Production with Adaptive Throttling: Background data copies must yield instantly when customer checkouts spike. Always monitor replica lag and database thread count.
  • Tenant-Scoping Reduces Blast Radius: Because Shopify partitions data with shop_id, an entire database migration affects only one merchant at a time during cutover, while neighboring merchants experience 0% downtime.
  • Queue, Don't Reject, During Cutover: A 400ms HTTP write delay is completely imperceptible to a browser checkout button, converting what could have been a catastrophic outage into a smooth, seamless transition.
