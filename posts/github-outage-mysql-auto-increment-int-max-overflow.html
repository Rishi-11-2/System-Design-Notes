When IDs Run Out: GitHub's MySQL Auto-Increment INT Overflow Outage

How a high-ingestion MySQL table exhausted its signed 32-bit integer primary key limit at 2,147,483,647, provoking duplicate key collisions, sitewide HTTP 500 errors, and zero-downtime emergency migrations.

1. Executive Summary & Outage Scope

On May 5, 2020, GitHub experienced a 2-hour and 24-minute partial service degradation affecting GitHub Actions, Pages, Dependabot, and webhook deliveries. The incident occurred when an auto-incrementing primary key on a core, high-volume database table reached the upper ceiling of a signed 32-bit integer:

$$\text{INT}_{\text{max}} = 2^{31} - 1 = 2,147,483,647$$

Once this boundary was crossed, MySQL could no longer increment the sequence. In accordance with MySQL's storage engine behavior, subsequent INSERT statements attempted to reuse the maximum integer $2,147,483,647$, immediately violating unique primary key constraints: 

ERROR 1062 (23000): Duplicate entry '2147483647' for key 'PRIMARY'

In the application layer (Ruby on Rails), ActiveRecord raised ActiveModel::RangeError, causing API endpoints and background workers to fail with HTTP 500 errors across the platform.

2. Technical Anatomy: MySQL Integer Storage Mechanics

Relational databases represent numeric types using fixed-width binary encodings. In MySQL InnoDB, an INT column occupies exactly 4 bytes (32 bits) of disk and memory storage per row:

By default in SQL DDL specifications, an INT is signed unless explicitly designated as UNSIGNED. Because negative identifiers are never generated by auto-increment, fully 50% of the 32-bit address space (representing negative numbers from $-2^{31}$ to $-1$) is permanently squandered.

3. What Actually Happens at 2,147,483,647

When an auto-increment column approaches its upper boundary, MySQL's behavior depends on the version and SQL mode, but the catastrophic outcome is identical:

Operation Requested ID Value MySQL Engine Action Resulting Status
Insert Row $N$ NULL (Auto-increment) Sequence allocates $2,147,483,647$ Success Max INT allocated
Insert Row $N+1$ NULL (Auto-increment) Clamps sequence to $2,147,483,647$ Collision ERROR 1062 (Duplicate entry)
Insert Row $N+2$ NULL (Auto-increment) Clamps sequence to $2,147,483,647$ Collision ERROR 1062 (Duplicate entry)
The Complete Write Stoppage

Once clamped at $2,147,483,647$, the auto-increment generator never rolls over or recovers automatically. 100% of subsequent write transactions fail. In high-throughput ingest systems processing thousands of inserts per second, this results in an immediate, absolute write outage.

4. The Remediation Playbook: Emergency Schema Modifications

When an active production table hits this limit during an outage, standard offline ALTER TABLE cannot be executed because copying hundreds of millions of rows takes hours:

Approach 1: Double Headroom to UNSIGNED

Modifying the type from signed INT to UNSIGNED INT doubles the ceiling to $4,294,967,295$, buying months or years of headroom. However, in older MySQL versions, this still requires a table rewrite.

Approach 2: Expand to BIGINT

Upgrading the column to BIGINT ($2^{63}-1 \approx 9.22 \times 10^{18}$) permanently eliminates the issue. Even at 1,000,000 inserts per second, a BIGINT sequence will not exhaust for over 292,000 years.

Emergency Alter Runbook: Fast Path Configuration
-- 1. Disable non-critical runtime checks to accelerate execution
SET SESSION transaction_isolation = 'READ-UNCOMMITTED';
SET SESSION foreign_key_checks = 0;
SET SESSION unique_checks = 0;
SET SESSION sql_log_bin = 0; -- Caution: Must replay manually to replicas!

-- 2. Execute targeted column type expansion
ALTER TABLE high_volume_events 
  MODIFY COLUMN id BIGINT NOT NULL AUTO_INCREMENT;

-- 3. Re-enable safety checks
SET SESSION foreign_key_checks = 1;
SET SESSION unique_checks = 1;
SET SESSION sql_log_bin = 1;

6. Proactive Defense: Continuous Auto-Increment Telemetry

Auto-increment overflow is 100% predictable. By querying MySQL's information_schema metadata dictionary, database reliability teams can track integer saturation metrics and alert weeks or months before a crisis:

SQL Telemetry: Auto-Increment Utilization Scanner
-- Query to detect tables approaching integer exhaustion (> 70% capacity)
SELECT 
    table_schema,
    table_name,
    column_name,
    data_type,
    column_type,
    auto_increment,
    max_value,
    ROUND((auto_increment / max_value) * 100, 2) AS pct_used
FROM (
    SELECT 
        c.table_schema,
        c.table_name,
        c.column_name,
        c.data_type,
        c.column_type,
        t.auto_increment,
        CASE 
            WHEN c.column_type LIKE '%unsigned%' AND c.data_type = 'int' THEN 4294967295
            WHEN c.data_type = 'int' THEN 2147483647
            WHEN c.column_type LIKE '%unsigned%' AND c.data_type = 'bigint' THEN 18446744073709551615
            WHEN c.data_type = 'bigint' THEN 9223372036854775807
        END AS max_value
    FROM information_schema.columns c
    JOIN information_schema.tables t 
      ON c.table_schema = t.table_schema AND c.table_name = t.table_name
    WHERE c.extra = 'auto_increment'
) metrics
WHERE (auto_increment / max_value) > 0.70
ORDER BY pct_used DESC;

7. Production Engineering Checklist

  • Default to BIGINT for primary keys: In high-throughput architectures, always specify BIGINT for surrogate primary keys; the 4 extra bytes per row are trivial compared to the cost of an outage.
  • Never omit the UNSIGNED keyword on 32-bit INTs: If 4-byte INT is strictly required for memory savings, always use UNSIGNED to avoid discarding half the range.
  • Alert at 70% threshold: Wire scheduled monitoring daemons to notify SRE teams whenever auto-increment utilization exceeds 70%.
  • Prepare gh-ost migration templates: Maintain pre-approved migration templates to expand key widths without downtime.
  • Audit client ORM type mapping: Ensure client SDKs (Go, Java, Ruby) map database integers to 64-bit primitives to avoid client-side deserialization overflow.
