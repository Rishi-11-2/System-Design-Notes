DragonflyDB DashTable Internals: Segmented Hashing, Cache Locality, and O(1) Eviction

By Arpit Bhayani Dissection & Roman Gershman Systems Design • October 2026 • 16 min read

1. The Redis Baseline: Separate Chaining & dictEntry Overhead

For over a decade, Redis has reigned as the standard in-memory key-value store. Its core dictionary is implemented using standard separate chaining: an array of bucket pointers where hash collisions are linked together via singly linked lists.

In Redis, every single key-value pair is wrapped inside a heap-allocated C struct called dictEntry: 

typedef struct dictEntry {
    void *key;
    union {
        void *val;
        uint64_t u64;
        int64_t s64;
        double d;
    } v;
    struct dictEntry *next; /* 8-byte pointer for chaining */
} dictEntry;

On a 64-bit architecture, dictEntry consumes 24 bytes ($8\text{ bytes key} + 8\text{ bytes val} + 8\text{ bytes next}$). In practice, due to memory allocators (like Jemalloc) allocating in quantized size classes, each dictEntry allocation incurs at least 24 to 32 bytes of heap metadata overhead, completely separate from the actual string data!

The Pointer Tax: If your dataset contains 100 million keys, Redis spends $2.4\text{ GB} - 3.2\text{ GB}$ of physical RAM solely on dictEntry pointers and allocator headers before a single byte of application data is stored.

Furthermore, separate chaining exhibits disastrous CPU cache behavior:

  • Pointer Chasing: Traversing linked lists involves dereferencing non-contiguous heap addresses, causing mandatory L1/L2/L3 CPU cache misses on collision lookups.
  • Memory Fragmentation: Hundreds of millions of tiny allocations strain the OS virtual memory manager and jemalloc arenas.
  • Rehashing Latency Spikes: When Redis table load factor reaches $\ge 1.0$, it doubles the table size and gradually migrates buckets during read/write cycles. Under heavy mutation loads, this incremental rehash degrades P99 and P999 tail latencies.

2. The DashTable Architecture: Hardware-Conscious Hashing

When Roman Gershman designed DragonflyDB, he abandoned Redis's linked-list dictionary and engineered DashTable, heavily inspired by modern hardware-conscious hashing research (specifically Dash: Scalable Hashed Indices on PMem/DRAM).

DashTable replaces pointers with segmented bucket hashing. Instead of allocating individual nodes on the heap, memory is organized into coarse-grained, fixed-size Segments. Within each segment, records are stored in cache-line-aligned Buckets containing fixed-size slots and 1-byte hash fingerprints.

3. Anatomical Breakdown of a Segment

A DashTable segment is a self-contained hashing unit. Each segment consists of:

  • 56 Regular Buckets: The primary storage area for hashed entries.
  • 4 Stash Buckets: A dedicated spillover overflow buffer to absorb collisions without requiring segment resizing.
  • Segment Metadata: Bitmaps tracking slot occupancy, displacement flags, and local depth for dynamic splitting.

Cache-Line Alignment & 1-Byte Fingerprints

Modern CPU architectures fetch memory into L1/L2 caches in 64-byte lines. DashTable aligns its bucket structures precisely to CPU cache lines.

Each bucket contains an array of 1-byte cryptographic fingerprints (the least significant byte of the key hash) followed by slot payloads (pointers or packed inline values). When searching for a key, DashTable executes SIMD/vectorized instructions across all 1-byte fingerprints in the 64-byte bucket simultaneously. 

// Conceptual Bucket Representation
struct alignas(64) Bucket {
    uint8_t fingerprints[SLOTS_PER_BUCKET]; // 1-byte hash signatures
    uint8_t control_bits;                  // Occupancy & displacement mask
    EntryPayload slots[SLOTS_PER_BUCKET];  // Embedded payload pointers
};

If no fingerprint in the bucket matches the key's fingerprint, the lookup finishes with zero pointer dereferences and exactly one cache line load!

4. Dual-Bucket Routing & Stash Overflow Mechanism

Traditional open-addressing hash tables suffer from primary clustering or high displacement chains under high load factors. DashTable solves this with Dual-Bucket Routing with Stash Overflow:

  1. Candidate Home Buckets ($h_1$ and $h_2$): For any key, the hash function computes two candidate bucket indices within the segment: $$h_1 = \text{hash}(key) \pmod{56}$$ $$h_2 = (\text{hash}(key) \oplus \text{hash\_stride}) \pmod{56}$$
  2. Balanced Insertion: DashTable examines both $h_1$ and $h_2$. If either bucket has an empty slot, the item is inserted into the least-loaded bucket.
  3. Cuckoo Displacement: If both $h_1$ and $h_2$ are fully occupied, DashTable attempts to displace an existing entry in $h_1$ to its alternate home bucket ($h_{1,\text{alt}}$).
  4. Stash Overflow: If displacement fails, the item is placed into one of the segment's 4 Stash Buckets. The stash acts as an elastic safety valve, allowing segments to achieve $\gt 90\%$ load factor before triggering any segment split.

5. Dynamic Segment Splitting vs. Global Rehashing

In Redis, when the dictionary exceeds its capacity, the entire table begins an incremental rehash. Two global hash tables (ht[0] and ht[1]) exist simultaneously, doubling pointer overhead and introducing latency jitter on every command execution.

DashTable eliminates global rehashing through Dynamic Segment Splitting (similar to extendible hashing):

  • Segment-Local Saturation: A segment only splits when both its 56 regular buckets and its 4 stash buckets are 100% full.
  • Localized Splitting: DragonflyDB allocates a single new segment and increases the local depth bit. Only the keys within that single saturated segment are rehashed and partitioned between the old segment and the newly created segment.
  • Zero Global Latency Impact: Other segments remain completely untouched. Read and write operations on unaffected segments proceed at full speed without lock contention or rehash checks.

6. Segment-Anchored O(1) Eviction (2Q & LFRU)

When an in-memory database runs out of RAM, it must evict keys according to an eviction policy (e.g., LRU, LFU).

Redis performs sampling-based eviction: it picks $N$ random keys (typically $N=5$), checks their idle time or frequency counter, and evicts the best candidate. This sampling requires random memory accesses across the global keyspace and degrades under high churn.

DragonflyDB integrates its 2Q / LFRU eviction framework directly into the DashTable segment structure:

  • Segment-Bound Eviction: When memory is exhausted and a write targets a saturated segment, Dragonfly does not scan the global database. Instead, it evicts an eligible key directly from the target segment in strict $O(1)$ time!
  • 2Q Algorithm: Segments maintain lightweight circular queues categorizing keys into cold FIFO buffers and hot LRU pools. New keys enter the probationary FIFO buffer; only keys accessed multiple times graduate to the hot pool.
  • Zero Metadata Pointer Overhead: Unlike Redis which stores a 24-bit LRU clock per object, Dragonfly encodes eviction state inside the bucket slot control bits, saving tens of megabytes of memory.

8. First-Principles Summary & Design Lessons

  • Pointers Are Expensive: At cloud scale, pointer-heavy data structures waste gigabytes of physical memory on addresses rather than data. Contiguous flat arrays and bucketed memory layouts maximize density.
  • Design for CPU Cache Lines: Modern performance bottlenecks are memory-bus bound, not CPU-bound. Aligning data structures to 64-byte cache lines and utilizing 1-byte fingerprints allows SIMD filtering with single-cycle cache access.
  • Isolate Rehashing Blast Radius: Global table rehashing creates unpredictable latency spikes. Segmented, extendible hashing bounds the operational blast radius to a single segment, guaranteeing rock-solid P99 SLAs.
