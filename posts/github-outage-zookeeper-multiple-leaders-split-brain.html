Dissecting GitHub Outage: Split-Brain & Multiple Leaders in ZooKeeper

How asymmetric network packet loss breached ZooKeeper's Zab consensus invariants, creating dual simultaneous leaders that routed writes to conflicting MySQL masters.

23 min read Arpit Bhayani Outage Dissections Verified 3-Page Companion PDF
📥 Download Technical PDF (3 Pages)
📌 Primary Consensus Failure Abstract

Distributed coordination engines like Apache ZooKeeper, etcd, and Consul are mathematically engineered to guarantee that at any given moment in time, exactly one authoritative leader exists. In this critical GitHub infrastructure outage, an asymmetric network partition combined with a lease-expiration timing race condition caused a catastrophic breakdown of this invariant: two ZooKeeper nodes simultaneously believed they were the legitimate, quorum-backed cluster leader. As clients connected to both leaders, GitHub’s service discovery and database routing layers received conflicting master assignments, routing production writes to two different MySQL databases concurrently.

1. The Role of ZooKeeper in GitHub’s Core Topology

GitHub utilized an ensemble of Apache ZooKeeper nodes as the authoritative source of truth for:

  • Database Leader Registration: Recording which MySQL node was the active, writable master for each shard.
  • ProxySQL Routing Topologies: Database proxies continuously watched ZooKeeper z-nodes to dynamically update backend write pools.
  • Orchestrator Coordination: Orchestrator daemons acquired ephemeral locks in ZooKeeper to ensure only one orchestrator instance executed topology changes.
⚠️ The Absolute Prerequisite: Single Leader Invariant

ZooKeeper relies on the Zab (ZooKeeper Atomic Broadcast) consensus protocol. Zab requires that all writes pass through a single primary leader. The leader assigns a monotonically increasing 64-bit transaction ID ($zxid$), where the upper 32 bits represent the epoch and the lower 32 bits represent the counter. If multiple leaders emerge with diverging epochs, consensus collapses.

2. The Failure Cascade: How Multiple Leaders Emerged

The emergence of multiple leaders was driven by a classic combination of asymmetric network partitioning and lease timeout lag:

3. Step-by-Step Divergence Mechanism

  1. Asymmetric Flapping: A network switch dropped outbound packets from Leader 1 to Nodes 3, 4, 5, but allowed inbound packets or dropped them intermittently.
  2. Election of Leader 2: Nodes 3, 4, and 5 timed out waiting for Leader 1’s heartbeat. Because they numbered 3 out of 5 nodes, they successfully formed a strict majority quorum ($\frac{5}{2} + 1 = 3$), bumped the epoch to $e_2$, and elected Node 3 as New Leader.
  3. The Old Leader's Delusion: Leader 1 had a longer socket timeout / GC pause and had not yet acknowledged its loss of quorum. It continued accepting read queries and serving cached leadership leases to clients connected to Partition A.
  4. Client Divergence:
    • Client App Pool 1 (connected to Leader 1) read: master = db-east-01.
    • Client App Pool 2 (connected to Leader 2) read: master = db-east-02.
  5. The Result: Production writes were routed simultaneously to two different MySQL nodes, breaking referential integrity and causing massive primary key collisions.

4. The Fencing Token Solution

In distributed systems design, relying on a client or leader to "know" when its lease has expired is a fatal flaw. Networks can delay packets indefinitely, and garbage collection (GC) pauses can freeze a process for seconds after its lease expires.

📐 The Fencing Token Pattern (Martin Kleppmann)

Every time a consensus service grants a leadership lease or assigns a database master, it must issue a strictly monotonically increasing Fencing Token (e.g., ZooKeeper epoch + transaction ID):

$$T_1 = (\text{epoch}: 1, \text{tx}: 104) \quad \longrightarrow \quad T_2 = (\text{epoch}: 2, \text{tx}: 1)$$

The Storage Layer Invariant: The storage tier (MySQL, ProxySQL, or storage server) must record the highest fencing token it has ever observed. If a client submits a write request with token $T_1$, but the storage layer has already observed $T_2$ ($T_1 < T_2$), the storage layer strictly rejects the write:

$$\text{if } T_{\text{incoming}} \le T_{\text{max\_observed}} \implies \text{REJECT (STALE\_EPOCH)}$$

5. Hardening ZooKeeper in Production

1. Strict 3-Datacenter Topology:
   └── Never split a 5-node cluster evenly between 2 datacenters (e.g. 3 in East, 2 in West).
   └── If the WAN cuts, the 2-node side stalls, but if the 3-node side network flaps, multiple leaders emerge.
   └── Solution: Deploy in 3 distinct Availability Zones (e.g., 2 in AZ-1, 2 in AZ-2, 1 in AZ-3).

2. Aggressive Heartbeat Sync Limits:
   └── Set tickTime=2000, initLimit=5, syncLimit=2.
   └── Ensure leaders step down immediately (within 2 ticks) if fewer than quorum followers acknowledge ping.

3. Client Read-Only on Disconnect:
   └── When ZooKeeper client emits DISCONNECTED or SESSION_EXPIRED event,
       application web workers must immediately reject all incoming POST/PUT requests
       and enter safe read-only mode until connection is re-established.

6. Systems Engineering Takeaways

  1. Quorum Protocols Do Not Prevent Asymmetric Split-Brain on Stale Leases: While Zab and Raft guarantee that only one leader can be elected per epoch, an old leader can continue serving stale state if client leases do not check monotonic epoch tokens.
  2. Never Trust the Client to Discard Its Own Lease: A node experiencing a Java GC pause or network delay does not know that its lease expired 500ms ago. Always enforce validation at the resource endpoint via fencing tokens.
  3. Odd Nodes Must Span Odd Failure Domains: A 5-node consensus cluster distributed across only 2 data centers is an architectural trap. Any fiber cut leaves one datacenter unable to form quorums and the other vulnerable to split-brain. Consensus requires 3 independent failure domains.
