How Grab Configured Their Data Layer for Multi-Million Daily Transactions

👤 Author: Rishi Chowdhury 📅 Published: Feb 24, 2026 ⏱️ 8 min read 📁 Category: Case Studies
📄 View / Download Original PDF ← Back to Blog Index
📌 Real-World Architecture Study

Grab processes tens of millions of food delivery, ride-hailing, and mart orders every day across Southeast Asia. Spiky lunch and dinner peak hours strain database tiers with extreme concurrency. This technical note breaks down Grab's multi-tiered data layer: splitting OLTP and OLAP workloads, caching with Redis, read-write database splitting, database sharding, and an ingenious DynamoDB Partial Indexing strategy that cuts index bloat by 90%+.

1. Introduction

Grab operates an everyday super-app handling millions of bookings and food delivery orders daily. The most critical and brittle component of any high-traffic transactional architecture is the persistence tier. Spikes during meal times and promotional campaigns can easily overwhelm databases unless traffic is carefully buffered and segmented.

2. Query Types: OLTP vs OLAP

To design an optimal persistence architecture, Grab segregates workloads into two distinct categories:

  • Transactional Queries (OLTP): Real-time operations with low latency requirements (< 50ms). Examples: creating a new food order, driver location updates, order state transitions (Pending $\to$ Confirmed $\to$ Picked Up $\to$ Delivered).
  • Analytical Queries (OLAP): Heavy aggregate read operations and reporting. Examples: merchant earnings calculations, fraud detection heuristics, supply-demand modeling, daily business metrics.
⚠️ Golden Rule

Never run OLAP queries directly against the primary OLTP transactional database. A single unindexed aggregate query or large table scan can lock tables, consume buffer cache memory, and cause cascading timeouts for end-user order creation.

3. Core Design Goals

  1. High Availability: 99.99% uptime for core transactional flows.
  2. Sub-Second Latency: P99 order placement latency under 200ms.
  3. Horizontal Scalability: Ability to absorb 5x surges during monsoon rainstorms or festival holidays.
  4. Strict Isolation: Preventing analytical reporting from impacting checkout workflows.

4. Database Choices & Tiering Strategies

4.1 Redis Caching with Cache-Aside Pattern

Frequent read queries (e.g., driver coordinates, active restaurant menus, live order status) are intercepted by a Redis cluster using the Cache-Aside (Lazy Loading) pattern:

  1. Application checks Redis cache for the active order key.
  2. If cache hit: return data immediately with ~2ms latency.
  3. If cache miss: read from read replica, populate Redis with TTL, and return.

4.2 Read-Write Splitting

Grab employs connection proxies (ProxySQL / AWS RDS Proxy) to automatically route writes (INSERT, UPDATE, DELETE) to the primary database while fanning out read queries (SELECT) across multiple read replicas.

4.3 Key Optimization: Partial Indexing in DynamoDB

One of Grab's most significant optimizations involves managing order status histories in DynamoDB. A typical Grab user might have 1,000 completed orders over 3 years, but at any given minute, only 1 or 2 ongoing active orders.

Querying "Show me active orders for user X" against a massive order table requires either scanning all historical orders or maintaining a secondary index on all orders, leading to massive storage costs and slow indexing.

💡 DynamoDB Sparse / Partial Indexing

In DynamoDB, Global Secondary Indexes (GSIs) only populate items that contain the index key attribute. Grab exploits this by:

  • Adding an attribute is_ongoing = 1 only while the order is in progress.
  • When the order is delivered or cancelled, a Lambda / background worker removes the attribute.
  • Result: The secondary index contains only active orders (e.g. 10,000 active orders across the entire city instead of 500,000,000 historic orders)!
  • Read latency drops to single-digit milliseconds and GSI storage cost drops by over 95%.

5. Data Synchronization & Architecture Pipeline

To keep analytical and downstream microservices synchronized with the primary OLTP store without performance degradation, Grab utilizes Change Data Capture (CDC):

  1. Transactions write to the MySQL/Aurora primary database.
  2. Debezium captures the database binary log (binlog) and streams change events into Apache Kafka.
  3. Downstream streaming consumers ingest Kafka topics into an Amazon S3 data lake, ClickHouse, or Snowflake for analytical reporting, merchant payout processing, and real-time dashboard analytics.

6. Key Takeaways

  • Segregate ruthlessly: Keep transactional paths lean and offload analytics to asynchronous streams.
  • Optimize indexing: Use sparse indexing techniques to index only volatile, highly queried state.
  • Rely on CDC: Stream database mutations asynchronously via Kafka to prevent cross-service database coupling.
