Production Architecture Dissection

Grab's Data Layer Architecture: Scaling Multi-Million Daily Transactions

📁 Category: Distributed Databases & Real-World Architectures
← Back to All Notes
📌 Executive Summary

Grab processes tens of millions of rides, food deliveries (GrabFood), and grocery mart orders (GrabMart) across Southeast Asia daily. The core engineering challenge lies in the database tier: handling massive, unpredictable traffic spikes during lunch and dinner hours while simultaneously serving real-time transactional writes and rich analytical history queries. Grab solved this not with a single monolithic database, but through a bifurcated storage architecture pairing Amazon DynamoDB (OLTP) with MySQL (OLAP), connected via a resilient Kafka $\to$ SQS $\to$ DLQ fallback pipeline with idempotent upsert and timestamp reconciliation.

1. The Multi-Million Transaction Challenge at Grab

In Southeast Asia's hyper-dense metropolitan areas (Singapore, Jakarta, Bangkok, Manila), consumer food and transit demand follows extreme spiky curves:

  • During quiet mid-afternoon hours, the system handles baseline transactional traffic.
  • Between 11:30 AM – 1:30 PM (lunch rush) and 6:30 PM – 8:30 PM (dinner rush), queries per second (QPS) surge by 10x to 20x within minutes.
  • Special flash sales, promotional campaigns, or sudden monsoon storms trigger localized traffic avalanches in specific urban sectors.

In any high-scale web platform, the database is universally the most brittle and difficult layer to scale elastically. Unlike stateless application servers or API gateways that can spin up in containers within seconds, database clusters face physical state constraints, storage volume attachments, schema locks, buffer pool warm-ups, and replication lag.

The Monolithic Database Pitfall

Attempting to run real-time transactional order mutations (inserting new orders, updating driver GPS coordinates, dispatching delivery riders) on the same relational database engine that executes heavy historical analytical queries ("Show me all orders User X placed in 2025 grouped by cuisine") leads to rapid database failure. Long-running analytical table scans hold read locks, saturate disk I/O channels, evict hot transactional data from buffer caches, and starve critical transactional writes, causing cascading timeout outages.

2. Workload Bifurcation: OLTP vs OLAP Dual Query Model

To design a rock-solid data layer, Grab systematically classified all incoming database queries into two distinct architectural patterns:

Workload Vector Transactional Queries (OLTP) Analytical Queries (OLAP)
Operations Point writes, creates, updates, and key-based reads: CreateOrder(), UpdateOrderStatus(), AssignDriver(). Multi-row range scans, aggregations, filters: Fetch historical orders for user, Calculate merchant monthly revenue.
Latency Target Strictly sub-10 milliseconds ($p99 < 15\text{ ms}$). Tolerant: 100 ms to 2 seconds is fully acceptable.
Consistency Requirement Strong Consistency: A driver must not be assigned to an order that another driver just claimed. Financial balances must be exact. Eventual Consistency: A user's order history can be delayed by a few seconds without impacting customer experience.
Access Pattern Indexed single-key lookups via primary key (order_id). Multi-attribute filtering: by user_id, date ranges, merchant ID, status, and geographic city.
Active Lifecycle Transient: Ongoing orders remain active for only 20 to 45 minutes until delivery completion. Long-term: Historical records must be preserved for tax compliance, user history, and machine learning models for years.

3. Core Architectural Design Goals

Grab established three non-negotiable architectural requirements for the modern data layer:

  1. High Stability & Availability: The system must sustain massive QPS surges without manual operator intervention. Crucially, a partial failure must degrade gracefully: if the analytical query engine slows down or fails, transactional food orders must continue processing without interruption.
  2. Cost-Effectiveness: The infrastructure must avoid over-provisioning expensive enterprise data warehouses for simple operational history queries. Storage and compute costs must scale sub-linearly relative to business growth.
  3. Strict Isolation of Consistency Guarantees: Strong consistency where state mutations occur; eventual consistency where historical data is read.

4. Specialized Database Selection: DynamoDB & MySQL

Instead of forcing a single database engine to handle both paradigms, Grab partitioned the workload across two specialized database technologies.

4.1 OLTP: Amazon DynamoDB for Real-Time Order Management

DynamoDB was chosen as the single source of truth for all active, ongoing orders due to three critical architectural characteristics:

  • Fully Managed Serverless Scalability: DynamoDB transparently handles horizontal partitioning, hardware provisioning, replication across three Availability Zones (AZs), and SSD storage management without manual maintenance windows.
  • Strong Read Consistency: When querying by partition key (order_id), DynamoDB supports strongly consistent reads, guaranteeing that the driver dispatch service immediately sees the latest order state.
  • Automated Hot Partition Mitigation: In distributed key-value stores, sudden spikes in traffic to specific keys (e.g., thousands of orders placed at McDonald's during a lunch promotion) can overwhelm a single partition. DynamoDB automatically rebalances capacity by moving infrequently accessed partition slices to shared physical hardware and allocating dedicated SSD I/O bandwidth to hot partitions, seamlessly preventing hotkey throttling.

Key Innovation: Sparse Partial Indexing in DynamoDB

While DynamoDB handles point lookups on order_id with single-digit millisecond latency, a critical business feature required querying: "Show the user their currently active orders".

In a naïve design, an engineer would create a Global Secondary Index (GSI) on user_id. However, this creates a catastrophic index bloat problem:

  • If an active user places 200 orders a year, a standard GSI on user_id would index all 200 orders forever.
  • Over years across 50+ million users, the GSI would store hundreds of millions of dead historical orders.
  • Every single update to an active order would incur write capacity unit (WCU) costs to update an enormous GSI, and querying the user's single active order would require scanning past 199 completed orders in the index.
The Engineering Solution: Partial Indexing with user_id_gsi

Grab leveraged DynamoDB's native Sparse Index mechanics through an ingenious attribute management pattern:

  1. Instead of indexing user_id directly, Grab created a dedicated attribute named user_id_gsi and created a GSI with user_id_gsi as the partition key.
  2. When an order is created (in state PENDING, ACCEPTED, or ON_THE_WAY), the application explicitly sets user_id_gsi = user_id.
  3. As long as the order is ongoing, DynamoDB includes the record in the GSI. When the mobile app asks for active orders, it queries the GSI on user_id_gsi and instantly retrieves only the 1 or 2 ongoing orders.
  4. The moment the order transitions to a terminal state (DELIVERED or CANCELLED), the application issues an update that sets user_id_gsi = null (or removes the attribute entirely).
  5. DynamoDB's Sparse Index Rule: If an item does not possess the attribute defined as the GSI partition key, DynamoDB does not write that item to the GSI!

The mathematical and operational impact of this single architectural optimization is profound:

  • 99% Size Reduction: At any given minute, only $\approx 0.1\%$ of total historical orders are actively ongoing. The GSI size drops from hundreds of gigabytes down to a few megabytes.
  • Instant Query Latency: Scanning an index with 1 entry takes $< 5\text{ ms}$, whereas scanning an index with thousands of historical rows takes tens of milliseconds and consumes heavy read capacity.
  • Substantial Cost Savings: DynamoDB charges for GSI storage and GSI write capacity. Eliminating historical data from the GSI slashed Grab's DynamoDB infrastructure spend.
  • Automatic Lifecycle Purging via TTL: To prevent the primary table from accumulating unbounded historical rows, Grab configured a DynamoDB Time to Live (TTL) of 3 months. After 90 days, DynamoDB automatically deletes expired rows in the background at zero write cost, keeping the transactional cluster lean.

4.2 OLAP: MySQL for Operational Analytics & Order History

While massive analytical data warehouses (such as Snowflake, Google BigQuery, or Amazon Redshift) are ideal for enterprise business intelligence (BI) dashboards, they are unsuitable for serving high-concurrency end-user web traffic. Cloud warehouses have high query startup overhead ($100\text{ ms} - 2000\text{ ms}$) and charge steep pricing per terabyte scanned.

Grab chose MySQL as their operational analytical store:

  • Relational Flexibility: Supports rich SQL capabilities: joining order items, filtering by date ranges, grouping by restaurant or merchant category, and calculating user lifetime savings.
  • Smart Sharding: Tables are sharded by user_id and partitioned by created_at. When a user requests their historical order feed in the Grab app, the query hits a single shard and a single time partition, eliminating expensive cross-shard distributed joins.
  • Read Replicas: Multiple MySQL read replicas absorb read queries from customer support dashboards, merchant portals, and user apps, completely shielding the transactional write tier.

5. Data Synchronization Pipeline: Multi-Tiered Fallbacks

Because DynamoDB is the transactional source of truth, all order updates must be reliably synchronized to MySQL. Doing this via synchronous dual-writes from the application service is a known anti-pattern: if MySQL is slow or temporarily unreachable, the user's food order would fail, degrading business availability.

Grab engineered an asynchronous, event-driven ingestion pipeline designed for high availability and zero data loss.

The Primary Path: Kafka Ingestion

Under normal operational conditions:

  1. The Order Service commits the state change to DynamoDB.
  2. The service immediately emits an OrderUpdatedEvent into a partitioned Apache Kafka topic.
  3. A dedicated pool of consumer workers reads events from Kafka in real time, transforms the JSON payload into relational tuples, and writes them to MySQL.

The High Availability Fallback Architecture

Apache Kafka clusters provide an industry-standard 99.95% availability SLA. However, at Grab's scale, a 0.05% downtime allowance equals roughly 4.38 hours of potential outages per year. During a Kafka broker degradation or network split, dropping order updates would permanently corrupt the MySQL analytical store.

Grab engineered a multi-tiered failover strategy:

  • Tier 1 — Apache Kafka: Serves 99.95%+ of traffic with ultra-high throughput and sub-second replication latency.
  • Tier 2 — AWS SQS Failover: The Order Service producer wraps Kafka publishing in a circuit breaker. If Kafka emits connection timeouts, broker exceptions, or latency spikes exceeding 500 ms, the application automatically routes event messages to Amazon Simple Queue Service (SQS). SQS is a highly resilient, multi-AZ cloud queue with near-zero operational maintenance.
  • Tier 3 — Dead Letter Queue (DLQ): If an event payload is malformed or if downstream MySQL ingestion encounters repeated deadlocks, the consumer exhausts its exponential backoff retries and routes the poison-pill message to a DLQ. High-priority PagerDuty alerts notify on-call engineers to inspect and replay the message safely.

6. Out-of-Order Message Reconciliation Mechanics

In any asynchronous distributed messaging pipeline with retries, network latency variations, and multi-threaded consumer pools, messages will arrive out of order.

The Out-of-Order Race Condition

Consider this real-world scenario: An order is placed at 12:00:00 (Event $E_1$: status = CREATED). The user cancels it 2 seconds later at 12:00:02 (Event $E_2$: status = CANCELLED).

Due to consumer worker thread scheduling or a temporary network retry on $E_1$, Event $E_2$ reaches the consumer and updates MySQL first. Seconds later, Event $E_1$ arrives. If the consumer naively overwrites MySQL, the order status in MySQL will revert from CANCELLED back to CREATED! The user would see a cancelled order appear as active in their history, causing support escalations.

To guarantee eventual consistency and absolute data correctness, Grab implemented two low-level database patterns:

1. Idempotent MySQL Upserts

Consumers never execute plain INSERT or UPDATE statements. Instead, all writes to MySQL use atomic upserts via INSERT ... ON DUPLICATE KEY UPDATE:

INSERT INTO customer_orders (
    order_id,
    user_id,
    merchant_id,
    order_status,
    total_amount,
    created_at,
    updated_at
) VALUES (
    'ord_883921',
    'usr_99120',
    'mch_5541',
    'CONFIRMED',
    42.50,
    '2026-02-24 12:00:00.120',
    '2026-02-24 12:00:05.450'
)
ON DUPLICATE KEY UPDATE
    order_status = IF(VALUES(updated_at) > updated_at, VALUES(order_status), order_status),
    total_amount = IF(VALUES(updated_at) > updated_at, VALUES(total_amount), total_amount),
    updated_at   = IF(VALUES(updated_at) > updated_at, VALUES(updated_at), updated_at);

This provides two vital guarantees:

  1. If an UPDATE event arrives before the initial CREATE event has arrived, MySQL creates the row immediately with the partial update data, rather than crashing with a foreign key or row-not-found error. When the CREATE event arrives later, it updates the missing initial fields.
  2. If the exact same event is delivered twice due to Kafka's at-least-once semantics, the statement evaluates as a complete no-op, maintaining idempotency.

2. Strict Monotonic Timestamp Invariants

Notice the conditional IF(VALUES(updated_at) > updated_at, ...) logic inside the MySQL update clause:

  • Every state mutation in DynamoDB is tagged with an authoritative, microsecond-precision epoch timestamp (updated_at) generated at mutation time.
  • When applying an update to MySQL, the engine compares the incoming record's timestamp against the timestamp currently stored in the database row.
  • If a delayed older event arrives (where $\text{incoming\_timestamp} \le \text{current\_db\_timestamp}$), the SQL conditional clause rejects the overwrite and preserves the newer state.
Arrival Order Event Name Event Timestamp Existing MySQL Timestamp Database Action Taken
1st Arrival OrderCancelled 12:00:02.000 None (Row does not exist) Inserted: Row created with status CANCELLED and timestamp 12:00:02.
2nd Arrival (Delayed) OrderCreated 12:00:00.000 12:00:02.000 Conflict Detected: $12:00:00 \le 12:00:02$. Timestamp check fails! Status remains CANCELLED. Missing non-status fields (merchant, items) populated cleanly.

7. Architectural Summary & Systems Engineering Insights

Design Dimension Engineering Decision Architectural Rationale
Storage Bifurcation DynamoDB for OLTP; MySQL for OLAP. Completely isolates mission-critical transactional mutations from heavy, lock-inducing analytical queries.
Index Optimization DynamoDB Sparse GSI on user_id_gsi. Removes completed orders by setting attribute to null, shrinking GSI size by 99% and accelerating active order reads.
Data Retention DynamoDB 3-Month TTL. Automatically purges cold transactional records without CPU overhead or table locks.
Pipeline Fault Tolerance Kafka $\to$ AWS SQS $\to$ DLQ. Provides multi-tiered fallback: wire-speed Kafka streaming in steady state, automatic SQS queueing during broker downtime.
Data Consistency MySQL Upserts with Timestamp Verification. Guarantees idempotent writes and prevents delayed out-of-order events from overwriting fresh state.
Key Architectural Principles for High-Scale Data Layers
  • Right Tool for the Right Query: Do not compromise your transactional database to accommodate reporting queries, and do not buy an oversized data warehouse for simple operational history feeds.
  • Exploit Sparse Indexing: In high-throughput NoSQL databases, indexes should represent active workflows, not the entire graveyard of historical transactions. Omitting attributes removes them from secondary indexes for free.
  • Design for Asynchronous Re-ordering: Whenever data leaves a strongly consistent database and enters a messaging bus, assume message ordering will be corrupted. Enforce monotonicity via explicit database timestamp checks.
