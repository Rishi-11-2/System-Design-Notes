How JunoDB Scales Horizontally: Consistent Hashing, Virtual Shards & Online Rebalancing

Scaling a financial key-value store to 350 billion requests per day requires elastic, linear horizontal scalability. Discover how PayPal's JunoDB combines consistent hashing, fixed virtual shards, and an online four-phase migration protocol to rebalance petabytes of financial state with zero downtime, zero lock contention, and bounded network saturation.

1. The Horizontal Scaling Challenge

In a high-scale transactional platform like PayPal, traffic is notoriously spiky. Peak events such as Black Friday, Cyber Monday, and regional holidays generate 5x to 10x traffic surges within minutes. Traditional relational databases and statically partitioned systems face three critical failure modes during scale-out operations:

  • Massive Key Reshuffling: Simple hash-mod partitioning ($\text{shard} = \text{hash}(key) \pmod N$) forces $(N-1)/N$ of all cluster keys to move when the node count $N$ increments by 1. For a petabyte cluster, adding a single server causes virtually 100% data eviction and total network collapse.
  • Stop-the-World Locking: Pausing writes on active partition shards to take consistent point-in-time snapshots halts client payments, triggering shopping cart abandonment and cascading timeout storms across microservices.
  • Hotspot Skew: Non-uniform key distribution or celebrity account traffic concentrated on single physical servers exhausts IOPS and CPU, causing cascading node crashes even when cluster-wide utilization is below 40%.

JunoDB solves these fundamental challenges through a mathematically decoupled partitioning topology: Consistent Hashing mapped over a large, invariant space of Virtual Shards.

2. Consistent Hashing & Murmur3 Foundations

Consistent hashing maps both keys and storage partitions onto a continuous 64-bit integer ring spanning the interval $[0, 2^{64} - 1)$. JunoDB uses MurmurHash3 (64-bit) as its hash function due to its superior avalanche properties, sub-nanosecond computation speed, and uniform bit distribution.

Given a key $K$, its ring coordinate is computed deterministically:

$$\text{RingPosition}(K) = \text{MurmurHash3\_x64\_64}(K) \pmod{2^{64}}$$

When a cluster scales from $N$ to $N+1$ physical storage groups, consistent hashing guarantees that on average, only $1/(N+1)$ fraction of keys are relocated. The remaining $N/(N+1)$ keys stay exactly where they are, preserving cache locality and eliminating catastrophic re-shuffling storms.

3. Virtual Shards Topology: Eliminating Skew

A naive consistent hashing implementation places each physical server at a single coordinate on the hash ring. This introduces severe load variance: the random distance between neighboring tokens on the ring can vary by factors of 10x to 100x, leading to massive storage imbalances.

JunoDB eliminates this skew by decoupling Virtual Shards (Partitions) from Physical Storage Groups:

  • Fixed High Cardinality: JunoDB partitions the entire hash ring into a fixed, large number of virtual shards $S$ (typically $S = 1024$ or $S = 4096$). This number is chosen once at cluster initialization and never changes.
  • Virtual-to-Physical Mapping: The cluster management coordinator (or Etcd metadata store) assigns multiple virtual shards uniformly across available physical Storage Groups.
  • Bounded Imbalance: By assigning $V = S / N$ virtual shards per physical group, the load variance shrinks asymptotically: $$\sigma \approx O\left(\frac{1}{\sqrt{V}}\right)$$ With hundreds of virtual shards per physical node, the load disparity between any two servers stays within $\pm 2\%$.

4. Mapping Shards to the 2D Storage Grid

In JunoDB, a physical storage unit is not a single server—it is a Storage Group consisting of 3 storage replicas placed across orthogonal Availability Zones (Failure Zones).

When key $K$ is hashed to Virtual Shard $S_i$, the routing engine looks up the routing table: 

// Simplified JunoDB Proxy Partition Routing Table
type RoutingTable struct {
    numVirtualShards uint32
    shardToGroup     []uint16 // Map virtual shard ID -> Storage Group ID
    groups           map[uint16]*StorageGroup
}

func (rt *RoutingTable) Route(key []byte) (*StorageGroup, uint32) {
    hash := murmur3.Sum64(key)
    shardID := uint32(hash % uint64(rt.numVirtualShards))
    groupID := rt.shardToGroup[shardID]
    return rt.groups[groupID], shardID
}

The proxy immediately fans out the read/write request to the 3 storage nodes residing in StorageGroup[groupID] across Zone 1, Zone 2, and Zone 3. Because the routing table is an in-memory flat array of 16-bit integers, lookup time is $O(1)$ and takes less than 15 nanoseconds per request.

5. Zero-Downtime Online Shard Migration Protocol

When seasonal traffic warrants adding new Storage Groups (e.g., expanding from 10 groups to 15 groups), a subset of virtual shards must move from existing groups to new groups. JunoDB achieves this online using a Four-Phase Migration Protocol:

The Four Migration Phases

  1. Phase 1: Dual-Write & Registration: The cluster orchestrator updates the cluster configuration. The proxy enters migration mode for the migrating shards. All new write operations for these shards are dispatched to both the Source Storage Group and Destination Storage Group. Reads continue serving exclusively from the Source.
  2. Phase 2: Historical Bulk Streaming: The Source storage nodes stream historical data (SSTable chunks or in-memory snapshot segments) for the migrating virtual shard directly to the Destination nodes. To preserve line-rate payment processing, this background streaming is strictly throttled by token-bucket rate limiters (e.g., max 50 MB/s per node).
  3. Phase 3: Catch-Up Delta Log Replay: During bulk transfer, keys modified by active transactions are recorded in a temporary transfer WAL (Write-Ahead Log). Once bulk data transfer completes, the destination replays the delta log until the replication lag drops below a 5ms threshold.
  4. Phase 4: Atomic Routing Cutover: The coordinator broadcasts a routing table update version. Proxies atomically switch read routing to the Destination group. Writes to the Source are discontinued. Once all proxies acknowledge the cutover, the Source schedules background tombstoning to reclaim disk and memory space.

6. Dual-Routing & Conflict Resolution Mechanics

During Phase 1 and Phase 2, concurrent operations can theoretically interleave. For example, what happens if an update arrives at the Destination before the bulk snapshot finishes?

JunoDB prevents resurrection bugs and stale overwrite anomalies through Monotonic Record Versioning & Timestamps:

  • Every JunoDB record header carries a 64-bit creation timestamp and a monotonically increasing version counter.
  • When the Destination node ingests records from the historical bulk stream, it applies a Last-Write-Wins (LWW) check: if a record already exists with a higher version or later timestamp (injected by an active dual-write), the historical record is discarded.
  • Deletions are propagated as explicit tombstones with TTLs, preventing deleted keys from being resurrected by lagging bulk streams.

8. Key Architectural Takeaways

  • Decouple Virtual Shards from Physical Machines: By using a large, fixed virtual partition space ($S \gg N$), cluster re-sharding becomes an exercise in reassigning logical shard pointers rather than calculating new mathematical boundaries.
  • Stateless Proxies Absorb Migration Complexity: Client applications never handle MOVED or redirect loops. The stateless proxy layer encapsulates routing versioning, dual-writes, and atomic cutovers transparently.
  • Rate-Limit Administrative Bandwidth: Unchecked data migrations will saturate network interfaces and trigger false-positive heartbeats, turning a routine scale-out into a catastrophic cluster partition. Always enforce strict token-bucket bandwidth caps.
  • Versioned Writes Prevent Migration Resurrections: In-flight mutations must always supersede historical bulk copies using monotonic versions or physical timestamps to guarantee absolute financial data integrity.
