Scoping Microservices Right: Loose Coupling & High Cohesion

How to correctly draw service boundaries using Domain-Driven Design (DDD) Bounded Contexts, eliminate synchronous inter-service dependencies, and prevent the dreaded Distributed Monolith anti-pattern.

1. The Scoping Paradox: Sizing Microservices

The prefix "micro" in microservices is notoriously misleading. Many engineering teams mistakenly believe that microservices should be sized by lines of code (e.g. "under 500 lines") or by isolated CRUD entities (e.g. creating a separate service for UserPreferences, UserProfile, and UserAvatar).

This fine-grained decomposition leads to nano-services. When services are sliced too thin, single business operations require multi-hop synchronous RPC chains across 10 different network endpoints. The result is the worst of all worlds: the operational fragility and latency of a distributed system paired with the tight coupling of a monolith—commonly termed a Distributed Monolith.

The Cardinal Rule of Scoping

The size of a microservice does not matter; its boundary coherence does. A well-designed microservice can be 10,000 lines of code if it encapsulates a cohesive domain boundary, or 1,000 lines if it represents an isolated utility.

2. Loose Coupling: Independent Evolvability

Two services are loosely coupled if a modification to one service does not force a corresponding modification or coordinated deployment to another service.

There are three primary forms of coupling to aggressively eliminate:

  1. Data Coupling: Two services reading or writing to the same database schema. If Service A alters a table column, Service B crashes.
  2. Temporal Coupling: Service A requires an immediate, synchronous response from Service B to finish its work. If Service B is slow or down, Service A fails.
  3. Contract / Model Coupling: Leaking internal database entities across public APIs (e.g. returning raw ORM models rather than versioned DTOs).

3. High Cohesion: Grouping What Changes Together

Cohesion is a measure of how strongly related and focused the responsibilities of a single module or service are. A service has high cohesion when all of its internal components contribute to a single, well-defined business capability.

The acid test for high cohesion is: "When a single business requirement changes, how many services must be modified?"

  • High Cohesion: The requirement change affects exactly one service. The team writes code, runs tests, and deploys that single service.
  • Low Cohesion: Modifying a discount calculation rule requires modifying the Order Service, Cart Service, Invoice Service, and Notification Service. This is an immediate architectural smell indicating fragmented domain boundaries.

4. Applying Domain-Driven Design (DDD) Bounded Contexts

The most robust methodology for identifying microservice boundaries is Eric Evans' concept of Bounded Contexts. In a complex enterprise, the exact same word often has radically different meanings depending on the context:

Business Domain Bounded Context What "Product" Means in this Context
Catalog / Search Discovery Context Title, SEO metadata, high-res images, categories, reviews
Order Fulfillment Inventory Context SKU, warehouse bin location, weight, dimensions, units in stock
Billing / Invoicing Finance Context Price, applicable VAT/tax rate, currency code, ledger account

Attempting to create a single "Universal Product Service" that serves all three contexts results in an unmaintainable god-object table with 80 columns. Instead, each bounded context should be its own microservice, storing only the attributes relevant to its domain.

5. The Scoping Decision Matrix

Signs a Service is Too Large:

  • Multiple teams are constantly committing to the same repository.
  • A change to inventory logic breaks user authentication.
  • The database contains over 30 unrelated tables.
  • Scaling the service wastes huge memory on inactive features.

Signs a Service is Too Small (Nano-Service):

  • A single user action triggers a chain of 6+ synchronous HTTP hops.
  • Two services must always be deployed in lockstep.
  • Network latency exceeds the actual database compute time by $10\times$.
  • The service cannot fulfill any request without querying 3 other services.

6. Production Engineering Checklist

  • Enforce Independent Deployability: Can you deploy this service to production right now without coordinating with any other team? If no, it is tightly coupled.
  • Strict Domain Data Ownership: Does this service own 100% of its data tables? No shared databases, no direct cross-service SQL joins.
  • Prefer Asynchronous Events Over Synchronous RPCs: Publish domain events (e.g. OrderCreated) so downstream services react independently.
  • Expose Versioned Stable Contracts: Use Protobuf / gRPC or OpenAPI schemas with strict backward-compatibility rules.
  • Merge Nano-Services When in Doubt: It is far easier to split a cohesive service later than to debug a distributed monolith across 20 nano-services.
