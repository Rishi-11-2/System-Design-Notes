1. The CI Latency Bottleneck

Continuous Integration (CI) is the primary feedback loop of modern software engineering organizations. However, as codebases grow, CI test and build suites routinely expand into 20–45 minute slogs. Standard cloud-hosted CI runners (such as default GitHub-hosted runners running on Azure Standard_DS2_v2 or AWS EC2 instances) present severe performance ceilings.

Software compilation (e.g., rustc, cargo build, go build, tsc typechecking, Webpack/Vite bundlers) is fundamentally constrained by single-thread CPU frequency and memory latency. According to Amdahl's Law:

$$S_{\text{latency}} = \frac{1}{(1 - p) + \frac{p}{s}}$$

Where $p$ is the parallelizable fraction of the compilation pipeline, and $s$ is the speedup factor of the parallel execution units. Even in heavily multi-threaded compilers, the non-parallelizable stages ($1-p$)—such as dependency graph topological sorting, global link-time optimization (LTO), and single-threaded lock acquisition—dominate the critical path. Running these stages on high-core-count, low-frequency cloud processors introduces massive latency overhead.

2. Hardware-First: Gaming CPUs vs. Cloud Xeons

Hyperscale cloud providers optimize their data centers for server density, virtualization multi-tenancy, and high aggregate core counts. Consequently, cloud VMs typically run on server CPUs (e.g., Intel Xeon Platinum 8171M or AMD EPYC 7763) with base clock frequencies of 2.4 GHz to 2.8 GHz.

Blacksmith inverts this paradigm by deploying bare-metal nodes powered by high-performance consumer/workstation silicon (e.g., AMD Ryzen 9 7950X / 9950X or Intel Core i9-14900K) capable of sustained single-core boost clocks of 5.4 GHz to 5.7 GHz.

The ~2x increase in raw clock speed, combined with lower memory access latency, cuts compiler instruction cycles in half without requiring a single modification to the user's build scripts or source code.

3. Firecracker MicroVM Isolation

A cloud CI platform executes arbitrary, untrusted customer code. Developers demand sudo access, root Docker privileges, and kernel namespace manipulation. This introduces a major security challenge:

  • Why Docker Containers Fail for CI Isolation: Containers share the host Linux kernel. Running Docker-in-Docker (DinD) requires granting --privileged flags, exposing the host system to container escape vulnerabilities (e.g., CVE-2022-0185, kernel eBPF exploits).
  • Why Traditional QEMU VMs Fail: Traditional virtual machines (KVM/QEMU) provide strong hardware isolation, but their boot process requires emulating legacy PCI devices, IDE controllers, and complex ACPI tables, requiring 25 to 60 seconds to initialize.

Blacksmith leverages AWS Firecracker, an open-source Virtual Machine Monitor (VMM) written in Rust. Firecracker strips away all legacy PC peripherals, providing only minimal virtio devices (virtio-net, virtio-block, virtio-vsock, and serial console).

Firecracker launches a dedicated Linux kernel with complete hardware virtualization in under 150 milliseconds. Wrapped inside the jailer daemon, each microVM runs under strict Linux namespaces (chroot, cgroups v2, seccomp filters), dropping root privileges immediately after KVM ioctl binding.

4. Copy-on-Write NVMe Rootfs Snapshotting

Standard CI runners spend 30–90 seconds pulling base images and preparing the root filesystem. Blacksmith achieves near-instantaneous runner initialization through Copy-on-Write (COW) root filesystem snapshotting directly on high-speed PCIe 5.0 NVMe SSDs.

Base runner images containing pre-warmed runtimes (Ubuntu 22.04 LTS, Docker Engine, Node.js, Python, Rust toolchains, Go) are maintained in read-only golden base volumes. When a GitHub Actions workflow job is scheduled:

# Instantaneous COW snapshot creation via Linux device-mapper
# 1. Allocate a sparse COW delta device
truncate -s 100G /var/lib/blacksmith/snapshots/job_10492_cow.img

# 2. Bind loopback and initialize device-mapper snapshot
losetup /dev/loop10 /var/lib/blacksmith/snapshots/job_10492_cow.img
dmsetup create runner_snap_10492 --table \
  "0 209715200 snapshot /dev/nvme0n1p2 /dev/loop10 P 8"

# 3. Mount snapshot as the root block device for Firecracker virtio-block
# Boot time: < 45 ms

Writes made by the CI job (temporary build artifacts, apt packages, docker image layers) write exclusively to the volatile COW delta device. Upon job completion, the device-mapper target is torn down and discarded in $O(1)$ time, guaranteeing that subsequent jobs receive pristine zero-contamination environments.

5. Colocated Caching vs Remote Blob Egress

Standard GitHub Actions dependency caching (actions/cache) transfers tar archives over public WAN networks to Azure Blob Storage. This creates severe throughput bottlenecks: transfers are typically bandwidth-capped at 100–300 MB/s, subject to rate limits and 10GB archive ceilings.

The Network Hop Disadvantage: Downloading a 5 GB dependency cache over a 200 MB/s connection adds 25 seconds of idle wait time before compilation can even start.

Blacksmith resolves this by deploying a colocated caching reverse proxy situated directly on the bare-metal host network or adjacent Top-of-Rack (ToR) 100 GbE switches. Cache reads and writes bypass the public internet entirely, transferring at full PCIe/NVMe-over-Fabrics speeds:

$$\text{Throughput}_{\text{colocated}} = \min(B_{\text{NVMe}}, B_{\text{100GbE}}) \approx 3.2\text{--}4.5\text{ GB/s}$$

A 5 GB node_modules or Cargo target cache restores in 1.2 seconds instead of 25 seconds.

6. Drop-In GitHub Actions Runner Mechanics

Adoption friction is the primary barrier to infrastructure migrations. Blacksmith acts as a drop-in runner backend by implementing the GitHub Actions self-hosted runner protocol. Teams integrate Blacksmith simply by changing a single line in their workflow YAML:

.github/workflows/ci.yml 
name: Enterprise Build & Test
on: [push, pull_request]

jobs:
  build:
    # Standard GitHub-hosted runner (Slow, 2.6 GHz Xeon)
    # runs-on: ubuntu-latest

    # Drop-in Blacksmith high-clock runner (Fast, 5.7 GHz Ryzen + MicroVM)
    runs-on: blacksmith-4vcpu-ubuntu-2204

    steps:
      - name: Checkout Code
        uses: actions/checkout@v4

      - name: Setup Rust & Cargo Cache
        uses: useblacksmith/cache@v1
        with:
          path: ~/.cargo/registry
          key: ${{ runner.os }}-cargo-${{ hashFiles('**/Cargo.lock') }}

      - name: Compile and Run Test Suite
        run: |
          cargo build --release
          cargo test --all

7. Trade-offs, Core Pinning & Fleet Management

Operating bare-metal gaming silicon at cloud scale introduces unique engineering trade-offs that standard cloud hypervisors do not encounter:

1. Multi-Tenant CPU Throttling vs. Core Pinning

Consumer CPUs dynamically boost clock frequencies based on thermal headroom (Precision Boost Overdrive / Thermal Velocity Boost). If multiple tenants on the same physical chip execute AVX-512 instructions simultaneously, the CPU will throttle all cores down to prevent exceeding Thermal Design Power (TDP). Blacksmith mitigates this via strict Linux cgroups v2 cpuset pinning, assigning dedicated physical cores to active microVMs rather than hyperthreaded virtual threads.

2. Lack of Hyperscaler Elastic Autoscaling

Unlike AWS EC2, where an API call provisions 1,000 instances in minutes, bare-metal hardware must be physical racking, stacked, and managed. Blacksmith must maintain warm pools of pre-booted microVMs and predict peak customer commit spikes (typically 9 AM – 11 AM EST) using predictive time-series forecasting models.

8. Key Architectural Takeaways

  • Single-Thread IPC Trumps Core Count: CI/CD compilation is constrained by Amdahl's Law. Upgrading from 2.6 GHz server Xeons to 5.7 GHz workstation silicon delivers a 2x latency reduction out of the box.
  • Firecracker Solves the Security/Speed Dilemma: Sub-150ms microVM boot times enable ephemeral, zero-trust virtual machines that allow full root/Docker privileges without container escape risks.
  • Colocate the Cache: IO bottlenecks negate CPU speedups. Moving the cache from remote Azure Blob storage to host-local NVMe cuts cache restore times from 25s to 1.2s.
  • Zero Migration Friction: Compatibility with existing GitHub Actions workflow manifests eliminates engineering friction and accelerates organizational adoption.
