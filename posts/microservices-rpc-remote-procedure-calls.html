1. The RPC Concept: The Local Procedure Call Illusion

In traditional procedural programming, calling a function is fundamentally simple: the caller places parameters onto the CPU call stack, executes a jump instruction to the function's memory address, and reads the return value from the register.

Remote Procedure Call (RPC) was conceived to preserve this familiar abstraction across a network. An application developer writes code that appears to invoke a standard local function, while an underlying RPC framework transparently serializes the arguments, transmits them over TCP/IP to a remote machine, executes the logic, and returns the serialized result.

The Leaky Abstraction

While syntactically identical to a local call, an RPC is physically subject to network partitions, packet drops, serialization overhead, DNS resolutions, and unbounded latency. Pretending a network hop is an in-memory pointer dereference is the root cause of countless distributed system outages.

2. The Fallacies of Distributed Computing (Peter Deutsch)

Every RPC designer must explicitly confront the classic eight fallacies of network computing:

1. The Network is Reliable

Routers flap, switches drop frames, and cables get severed. RPC clients must implement retries, timeouts, and circuit breakers.

2. Latency is Zero

In-memory pointer access takes ~10 nanoseconds ($10^{-8}\text{ s}$). A cross-rack datacenter network roundtrip takes ~500 microseconds ($5 \times 10^{-4}\text{ s}$) — a $50,000\times$ latency penalty.

3. Bandwidth is Infinite

Transmitting bloated JSON payloads across thousands of internal microservice RPCs saturates network interface cards (NICs) and switches.

4. Topology Doesn't Change

Cloud containers spin up, crash, and migrate dynamically. Service discovery and client-side load balancing are mandatory.

3. Anatomy of an RPC: Stubs, Marshaling & Skeletons

How does an RPC call travel from client code to server execution?

  1. Client Invocation: Client code calls the generated local stub method.
  2. Marshaling (Serialization): The client stub serializes the in-memory object into a binary format (e.g., Protobuf) and attaches metadata headers (Tracing IDs, Auth tokens, Deadlines).
  3. Network Transport: The framed binary buffer is transmitted across a persistent TCP connection (HTTP/2 stream).
  4. Unmarshaling (Deserialization): The server-side skeleton reads the bytes, decodes them into language-native structs, and invokes the concrete service handler.

4. Binary Serialization: Protocol Buffers vs. JSON

Why does gRPC use Protocol Buffers rather than JSON over HTTP?

Metric JSON (Text-based) Protocol Buffers (Binary)
Payload Size Repeats field names in every message (e.g. "customer_id": 123). Compact Uses integer field tags (e.g. tag 1 in 1-2 bytes). Typically 3x to 10x smaller.
CPU Serialization Speed Heavy CPU cost parsing string tokens and numbers. Fast Direct binary memory layout; 5x to 8x faster serialization.
Type Safety Implicit / Loose schema; runtime validation. Strict compile-time typing enforced via .proto IDL file.
Human Readability High Easy to inspect via cURL / browser. Requires decoding tool (e.g. grpcurl) or proto schema.

5. gRPC over HTTP/2: Multiplexing & Streaming

Traditional HTTP/1.1 requires opening separate TCP connections for concurrent requests or suffers head-of-line blocking. gRPC leverages HTTP/2 primitives:

  • Single Persistent TCP Connection: All RPC requests to a server instance are multiplexed over a single TCP socket via binary streams.
  • HPACK Header Compression: Repetitive headers (User-Agent, Auth tokens) are compressed into shared connection lookup tables.
  • Four Streaming Modes:
    1. Unary RPC: Single request → Single response.
    2. Server Streaming: Single request → Stream of responses (e.g. stock ticker prices).
    3. Client Streaming: Stream of requests → Single response (e.g. file upload chunks).
    4. Bidirectional Streaming: Concurrent streams flowing both ways (e.g. chat, real-time gaming).

6. Deadlines, Cancellations & Canonical Error Codes

gRPC replaces ambiguous HTTP status codes with 16 canonical error codes (OK, CANCELLED, DEADLINE_EXCEEDED, UNAVAILABLE, RESOURCE_EXHAUSTED).

Crucially, gRPC supports Active Request Cancellation: when an edge client cancels a search request, the RST_STREAM frame propagates downstream through all intermediate microservices, allowing them to stop heavy database queries immediately and save compute resources.

7. Production Engineering Checklist

  • Strict Field Tag Immutability: Never renumber or reuse a deleted Protobuf field tag number.
  • Client-Side Load Balancing: Use Envoy sidecars or gRPC lookaside load balancing (xDS) to prevent traffic concentration on single pods over long-lived HTTP/2 TCP connections.
  • Mandatory Deadlines: Every gRPC stub invocation must pass a context with an explicit timeout.
  • Structured Error Details: Attach Google status.proto rich error details (ErrorInfo, RetryInfo, BadRequest) rather than generic strings.
