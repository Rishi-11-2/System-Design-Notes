Airbnb Himeji: Centralized Zanzibar-Inspired Authorization at Scale

Decentralized authorization logic scattered across hundreds of microservices is a catastrophic security liability. Discover how Airbnb engineered Himeji—a centralized, high-throughput authorization platform inspired by Google Zanzibar—evaluating complex transitive relational access control in under 10 milliseconds across billions of daily RPCs.

1. The Authorization Sprawl Problem

In a complex multi-sided marketplace like Airbnb, access control is inherently relational:

  • Can user $U$ edit listing $L$? Yes, if $U$ is the primary host, or $U$ is an authorized co-host, or $U$ is a property management team administrator.
  • Can user $U$ view guest check-in instructions for reservation $R$? Yes, if $U$ is the confirmed booker, or an approved trip companion added by the booker.

Historically at Airbnb, these permission checks were hardcoded across hundreds of services and Ruby on Rails monolith models. This created severe operational failures:

  • RPC Amplification: To check a single permission, Service A called Service B, which called Service C to inspect database tables, cascading into 10+ internal RPC hops.
  • Inconsistent Access Rules: Different microservices implemented subtly divergent checks for the same resource, leading to security vulnerabilities and leaked financial records.
  • High Latency & Tight Coupling: Critical user paths suffered 200ms+ authorization overhead due to network round-trips.

2. The Google Zanzibar Tuple Model

Inspired by Google's landmark Zanzibar paper, Airbnb designed Himeji around a unified relational graph represented as Entity-Relation-Entity Tuples:

$$\langle \text{Object} \rangle \# \langle \text{Relation} \rangle @ \langle \text{User or UserSet} \rangle$$

Examples of relation tuples in Himeji:

  • listing:101#host@user:55 (User 55 is the direct host of listing 101)
  • listing:101#co_host@user:88 (User 88 is an approved co-host)
  • reservation:500#parent_listing@listing:101 (Reservation 500 belongs to listing 101)
  • reservation:500#can_view@listing:101#host (Any host of listing 101 can view reservation 500)

3. Himeji System Architecture

Himeji operates as a centralized, high-throughput gRPC service backed by distributed persistence and multi-level caching:

[ Microservice Client (Java / Ruby / Node.js) ] │ gRPC Check(user, relation, object) (<10ms) ▼ ┌────────────────────────────────────────────────────────────────────────┐ │ HIMEJI AUTHORIZATION SERVICE │ ├────────────────────────────────────────────────────────────────────────┤ │ • Local L1 In-Memory Cache (Caffeine • LRU with TTL) │ │ • Graph Traversal Engine (Breadth-First Search with Cycle Detection) │ │ • Central L2 Distributed Cache (Redis Cluster) │ └───────────────────────────────────┬────────────────────────────────────┘ │ Cache Misses ▼ ┌────────────────────────────────────────────────────────────────────────┐ │ SHARDED RELATIONAL STORE (MySQL) │ │ • Primary source of truth for ACL relation tuples │ │ • Partitioned by `object_id` for deterministic locality │ └───────────────────────────────────┬────────────────────────────────────┘ │ Change Data Capture (Debezium) ▼ [ Kafka Cache Invalidator ]

4. Recursive Graph Traversal & BFS

When an application service dispatches a Check(user:X, can_edit, listing:101) query, Himeji translates permission evaluation into a directed graph reachability search:

  1. Direct Edge Lookup: Himeji queries whether the direct tuple listing:101#can_edit@user:X exists. If found, returns ALLOW immediately.
  2. Rule Expansion: The schema indicates that can_edit is satisfied by either host or property_manager#admin.
  3. Breadth-First Search (BFS): Himeji traverses outward along relation edges. To prevent infinite loops caused by accidental administrative cycles, the search incorporates a visited-set bitmask and a strict traversal depth cap (e.g., max 6 hops).

5. Multilayered Caching & CDC Invalidation

Evaluating graph traversals across millions of daily operations would overwhelm relational databases. Himeji employs a tiered caching architecture:

  • L1 In-Process Cache: Local memory cache inside each Himeji instance holding frequently checked permissions (e.g., active host IDs). Resolves checks in under 0.2ms.
  • L2 Distributed Cache: A clustered Redis layer storing pre-evaluated permission graphs and hot tuple lists.
  • CDC Invalidation Pipeline: When a user adds a co-host, MySQL writes the new tuple. Debezium captures the binlog mutation and publishes an event to Kafka. Dedicated cache invalidation workers evict affected Redis keys within 50 milliseconds.

6. Sub-10ms Latency Optimizations

To maintain strict sub-10ms p99 SLAs on auth checks:

  • Consistent Hashing by Object: Queries for the same listing or reservation deterministically route to the same Himeji service instances, maximizing L1 cache hit rates (>98%).
  • Parallel Sub-Graph Fanout: Independent branches of the relation schema (e.g., checking if user is host vs. checking if user is co-host) are evaluated concurrently using Go/Java thread pools, returning as soon as any branch yields ALLOW.

7. Fail-Closed vs. Fail-Open Semantics

When network partitions or downstream database stalls occur, authorization systems face a profound engineering trade-off:

Operation Type Enforced Semantics Failure Behavior
Mutating / Financial Actions Fail-Closed (Deny) Payout modifications, listing deletions, or refund requests are strictly rejected if Himeji times out. Safety takes precedence over availability.
Public Read Views Fail-Open / Fallback Viewing public listing descriptions or neighborhood reviews degrades gracefully to cached public visibility rather than displaying a blank error page.

8. Key Architectural Takeaways

  • Centralize Authorization as a Graph: Modeling permissions as relation tuples $\langle \text{Object} \rangle \# \langle \text{Relation} \rangle @ \langle \text{User} \rangle$ replaces thousands of brittle application queries with unified graph reachability.
  • Decouple Auth from Business Logic: Microservices should only ask: "Can user X perform action Y on resource Z?" The authorization platform encapsulates the complexity of resolving co-hosts, teams, and administrative roles.
  • Layer Caches with Event-Driven Invalidation: Combining in-memory L1 caches with CDC-driven Kafka invalidations delivers sub-10ms performance while maintaining strict data consistency.
  • Differentiate Security Semantics by Action: Financial payouts and data mutations must always fail-closed on timeout, whereas non-sensitive read paths can degrade gracefully.
