GitHub Outage Dissection: Actions Breakdown, Cascading Inconsistencies & Cache Invalidation

How a 43-second optical link severance triggered a 24-hour global outage: cross-region replication lag, split-brain write divergence, and the harrowing reality of cache pollution.

📌 Executive Post-Mortem Abstract

On October 21, 2018, routine network maintenance severed the primary 100Gbps optical backbone between GitHub’s primary US-East (Virginia) data center and secondary US-West (Seattle) data center for exactly 43 seconds. While 43 seconds of packet loss should be absorbed cleanly by distributed retry policies, it provoked a 24-hour, 11-minute catastrophic degradation. Automated orchestrators promoted out-of-sync West Coast replicas to active masters, causing write divergence across thousands of tables. As writes landed on divergent MySQL topologies, application tiers read corrupted rows and poisoned internal Redis/Memcached layers, creating widespread GitHub Actions, webhooks, and pull request failures.

2. Architectural Dissection: MySQL Replication & Orchestrator

GitHub operated a geo-distributed database architecture consisting of dozens of MySQL clusters sharded by domain (Repositories, Users, Pull Requests, Actions). Each cluster featured:

  • Primary Master in US-East: Handled all authoritative writes.
  • Local Synchronous Replicas in US-East: Replicated via semi-synchronous replication for intra-datacenter HA.
  • Cross-Region Replicas in US-West: Replicated via asynchronous MySQL binary log streaming across dedicated dark fiber.
  • GitHub Orchestrator: Automated topology management daemon configured to monitor heartbeat health and execute failovers.

3. The Dual-Master Split-Brain Nightmare

Because the cross-region link severed completely, the Orchestrator agents in US-West could not communicate with the US-East master. Concluding that US-East had died, Orchestrator initiated an automated failover: it promoted the local US-West replica to master and reconfigured local proxy layers.

⚠️ The Critical Failure: East Never Stopped Writing

US-East had not died. The local app servers in Virginia were healthy and continuously serving active users, committing thousands of writes to the East Master. When the network reconnected 43 seconds later, both data centers hosted an active, writable MySQL master with identical server IDs, diverging auto-increment keys, and incompatible binary logs. Neither master could replicate from the other without fatal duplicate key errors.

4. The Silent Threat: Cache Invalidation Poisoning

Why did it take 24 hours to recover when the network restored in 43 seconds? The answer lies in Cache Pollution:

  1. Read-Repair and Stale Lookups: When West Coast web workers processed requests against the lagging West Master, they queried records that did not yet exist (or had outdated states).
  2. Cache Ingestion: The application tier faithfully wrote these stale, incomplete records into local Memcached and Redis clusters with standard 24-hour time-to-live (TTL) headers.
  3. The Result: Even after database connections were restored, users loading pull requests, repository releases, or CI/CD runs fetched cached garbage data. Webhooks were dropped, Actions workflows stalled waiting on nonexistent parent commits, and UI dashboards displayed phantom state.

5. The Recovery Strategy: Surgical Data Reconciliation

To recover without unrecoverable customer data loss, GitHub executed a high-stakes, multi-step engineering mitigation:

Step 1: Immediate Freeze
  └── Set entire site to Maintenance / Read-Only Mode.
  └── Stop all incoming webhooks, git pushes, and Actions runners.

Step 2: Binlog Differencing & Extraction
  └── Dump MySQL binary logs from US-West Promoted Master.
  └── Filter transactions committed during the 43s blip and post-blip window.
  └── Extract divergent INSERT / UPDATE queries into idempotent SQL reconciliation patches.

Step 3: Topology Realignment
  └── Demote US-West Master back to Replica status.
  └── Re-clone lagging replicas from verified US-East snapshot.
  └── Replay missing transactions using custom conflict resolution rules.

Step 4: Global Cache Invalidation & Backlog Drain
  └── Perform flush_all across all Redis & Memcached clusters.
  └── Slowly open throttle gates on webhook queues to prevent thundering herd.
  └── Restore full read/write traffic after 24h 11m.

6. Systems Engineering Takeaways

  1. Fencing and Fencing Tokens are Non-Negotiable: A failover must never promote a replica without positive, verifiable fencing of the old master. If you cannot prove the old master has stopped accepting writes, promoting a new one guarantees split-brain.
  2. Beware of Cross-Region Automated Failover: Automated failover across wide-area networks (WAN) is fraught with false positives. Unless governed by a multi-datacenter consensus protocol (e.g., Raft or Paxos with a third witness region), cross-region failover should require human verification.
  3. Caches Magnify Database Outages 100x: If a database returns stale or erroneous data, applications will eagerly cache that corruption. Systems must implement versioned cache keys or invalidate caches proactively upon topology changes.
