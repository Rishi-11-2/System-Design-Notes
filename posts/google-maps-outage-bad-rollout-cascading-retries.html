Google Maps Global Outage Dissection: Bad Rollouts & Cascading Retries

How a buggy feature deployment in an internal dependency crippled the Map Tiles API worldwide, rendering blank grey tiles and sparking a devastating synchronous retry avalanche.

1. Executive Summary & Outage Scope

On March 18, 2022, Google Maps suffered a catastrophic global outage lasting over two and a half hours. Across mobile navigation applications, ridesharing platforms, third-party JavaScript embeds, and web browsers, users worldwide were greeted by completely blank grey map tiles.

The platform metrics during the incident were staggering:

  • Map Tiles API: Complete global failure lasting 3 hours and 45 minutes.
  • Directions API: 65% failure rate; 99th percentile latency exploded to 8,500 milliseconds.
  • Navigation SDK: 37% error rate across Android and iOS in-flight navigation sessions.

The failure originated from a routine feature rollout in an internal shared backend service. The new code contained a resource leak that exhausted memory and CPU, throwing the service into an immediate crash-reboot loop. Because the upstream tile rendering engine held a hard synchronous dependency on this service, failing requests triggered unconstrained retries, creating a cascading retry storm that overwhelmed Google's frontend rendering tiers.

3. Anatomy of the Cascading Retry Storm

In a distributed microservice architecture, synchronous RPCs create tight temporal coupling. When an internal service fails, the standard failure mode in poorly tuned clients is an immediate, unjittered retry.

When the internal service crashed, the tile renderer received RPC deadline exceeded errors after its 2.0-second timeout. Because the client was configured to retry up to 3 times before failing, every inbound tile request spawned four total RPC attempts.

The Retry Explosion Factor

If a system normally processes 100,000 requests per second with an average latency of 20ms, an unjittered retry loop with $R=3$ retries transforms standard ingress into 400,000 requests per second with 2,000ms latency. The volume of queued requests in memory expands by $200\times$, instantly inducing Out-Of-Memory (OOM) panics on the calling servers.

4. Mathematical Formalism: Traffic Amplification & Little's Law

Let $\lambda$ be the external request arrival rate, and $P_f$ be the probability of request failure at the internal dependency. If clients retry up to $K$ times:

$$\lambda_{\text{effective}} = \lambda \cdot \sum_{i=0}^{K} P_f^i = \lambda \cdot \left(\frac{1 - P_f^{K+1}}{1 - P_f}\right)$$

When the internal service is down ($P_f \to 1$):

$$\lim_{P_f \to 1} \lambda_{\text{effective}} = \lambda \cdot (K + 1)$$

With $K=3$, the effective request rate quadruples ($\lambda_{\text{effective}} = 4\lambda$).

Simultaneously, the average request duration spikes from its healthy baseline $W_{\text{healthy}} = 20\text{ ms}$ to the timeout budget $W_{\text{timeout}} = 2,000\text{ ms}$. By Little's Law, the number of concurrent in-flight requests $L$ stored in server memory queues is:

$$L = \lambda_{\text{effective}} \cdot W_{\text{timeout}} = (4\lambda) \cdot (100 \cdot W_{\text{healthy}}) = 400 \cdot L_{\text{healthy}}$$

Because memory buffers and thread pools cannot expand by $400\times$, the tile rendering service exhausted its allocated process memory and crashed sequentially across all regions.

5. The Hysteresis of Recovery: Why Outages Outlive Rollbacks

A critical insight highlighted in Google's incident post-mortem is the recovery lag. Once engineers identified the bad feature rollout and rolled back the release (taking approximately 30 minutes), the platform remained severely degraded for more than an hour.

Why does recovery lag occur?

  1. Client-Side Backlogs: Millions of mobile devices, browsers, and embedded apps had piled up unfulfilled requests, continuously retrying against edge load balancers.
  2. Cold Cache Penalties: During the crash-reboot cycle, in-memory caches and JIT compilations were flushed. Recovering instances had to warm caches from scratch while handling $4\times$ normal load.
  3. TCP Socket Saturation: Thousands of lingering TCP connections in CLOSE_WAIT or TIME_WAIT consumed OS file descriptors, preventing new healthy connections from establishing.

6. Architecture Solutions: Google's Remediation Playbook

Google outlined four fundamental architectural improvements to prevent synchronous service failures from propagating sitewide:

1. Early Request Rejection & Shedding

When a server reaches capacity, it immediately drops inbound traffic (returning HTTP 429 or 503) instead of buffering requests in memory until crashing.

2. Queue Bounding & TCP Tuning

Enforce strict limits on in-memory buffers and TCP backlog queues. Excess connection requests are rejected immediately at the socket level.

3. Traffic-Class Circuit Breakers

During degradation, automatically shed low-priority internal analytics, batch syncs, and telemetry traffic to preserve 100% of compute capacity for end-user navigation.

4. Client Retry Budgets

Enforce client-side retry budgets (e.g., maximum 10% retries) combined with Exponential Backoff and Full Jitter to break synchronized request resonance.

// Full Jitter Backoff Formula: t_sleep = rand(0, min(cap, base * 2^attempt))
func ExecuteWithCircuitBreaker(ctx context.Context, cb *CircuitBreaker, req *TileRequest) (*TileResponse, error) {
    if !cb.Allow() {
        // Circuit open: Fall back immediately to cached or empty placeholder tile
        return FallbackPlaceholderTile(req), nil
    }

    baseDelay := 100 * time.Millisecond
    maxDelay := 2000 * time.Millisecond

    for attempt := 0; attempt < 3; attempt++ {
        resp, err := callDownstreamRPC(ctx, req)
        if err == nil {
            cb.RecordSuccess()
            return resp, nil
        }

        cb.RecordFailure()

        // Calculate Decorrelated Full Jitter delay
        maxJitter := min(maxDelay, baseDelay*(1<<attempt))
        jitteredDelay := time.Duration(rand.Int63n(int64(maxJitter)))

        select {
        case <-time.After(jitteredDelay):
        case <-ctx.Done():
            return FallbackPlaceholderTile(req), ctx.Err()
        }
    }
    return FallbackPlaceholderTile(req), nil
}

7. Production Engineering Checklist

  • Never use unbounded synchronous RPCs: Always configure tight deadlines and fallback behaviors (e.g., placeholder tiles) when calling downstream services.
  • Enforce Retry Budgets: Never permit clients to retry indefinitely; cap retries to at most 10% of total outbound requests.
  • Always Apply Full Jitter: Add uniform randomness to backoff timers to prevent synchronized retry waves.
  • Classify and Prioritize Traffic: Tag requests with priority headers (Customer Interactive vs. Internal Batch) and shed lower priorities first under stress.
  • Canary Feature Rollouts: Deploy code updates to a 1% canary cohort with automated metric rollbacks before expanding globally.
