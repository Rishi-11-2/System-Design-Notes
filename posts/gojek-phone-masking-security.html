Gojek Phone Masking Architecture: Virtual Number Pooling & High-Throughput Call Routing

Allowing millions of drivers and passengers to coordinate pickups without exposing personal mobile phone numbers is a critical privacy requirement. Discover how Gojek engineered its phone masking architecture—optimizing scarce virtual number pools via bipartite graph coloring, sub-100ms telco webhook routing, and automatic TTL bridge tear-downs.

1. The Privacy & Harassment Problem

Gojek powers millions of ride-hailing trips, food deliveries, and logistical couriers across Southeast Asia daily. In an on-demand workflow, drivers and consumers frequently need to communicate directly (e.g., clarifying street landmarks, verifying building gate codes, or confirming order substitutes).

Directly displaying real phone numbers in mobile apps introduces severe security liabilities:

  • Harassment & Stalking: Drivers or customers retaining personal phone numbers after order completion.
  • Off-Platform Disintermediation: Parties bypassing platform transaction fees for future recurring services.
  • Regulatory Non-Compliance: Violation of strict national data protection laws (e.g., GDPR, Singapore PDPA, Indonesian PDP Law).

3. Virtual Number Pool Optimization & Economics

Telecom operators lease virtual DID (Direct Inward Dialing) phone numbers on a recurring monthly fee. Purchasing a dedicated virtual number for every simultaneous trip would cost millions of dollars each month.

The Core Scaling Challenge: How do we support 1,000,000 active concurrent orders using a limited pool of only 1,000 to 5,000 virtual phone numbers?

A single virtual number $V_K$ can be simultaneously assigned to Order 1 (between Customer A and Driver B) and Order 2 (between Customer C and Driver D), as long as none of the participants overlap. When Driver B calls $V_K$, the gateway uniquely identifies Order 1 because the caller's Caller Line Identification (CLI) is Driver B!

4. Graph Coloring & Bipartite Matching Allocation

Assigning virtual numbers to active orders without collision can be modeled mathematically as a Vertex Coloring Problem on an Interval Graph:

  • Conflict Condition: Two concurrent orders $O_1(C_1, D_1)$ and $O_2(C_2, D_2)$ cannot share virtual number $V_K$ if $\{C_1, D_1\} \cap \{C_2, D_2\} \neq \emptyset$. (i.e., if the same driver or customer is active on multiple simultaneous orders).
  • Least Recently Used (LRU) Pool Recycling: Available virtual numbers are indexed in a Redis Sorted Set scored by timestamp of last order completion. The system greedily selects the virtual number that has rested longest in cooldown, preventing delayed callbacks from reaching previous tenants.

5. Low-Latency Telco Webhook Gateway

Telecom carrier switches enforce strict timeouts: if the phone masking gateway does not respond within 1,500 milliseconds, the telecommunication switch drops the phone call with an audible busy tone.

Gojek's gateway delivers sub-100ms p99 responses through lean Go microservices: 

// High-performance Call Routing Handler in Go
func HandleIncomingCallWebhook(w http.ResponseWriter, r *http.Request) {
    callerPhone := r.FormValue("From")
    virtualPhone := r.FormValue("To")

    // Single O(1) Redis Hash lookup
    key := fmt.Sprintf("bridge:%s:%s", virtualPhone, callerPhone)
    targetPhone, err := redisClient.Get(r.Context(), key).Result()
    if err != nil {
        // Fallback: Play automated IVR recording
        w.Write([]byte("Order expired or invalid."))
        return
    }

    // Return immediate dial instruction to carrier switch
    resp := fmt.Sprintf("%s", targetPhone)
    w.Header().Set("Content-Type", "application/xml")
    w.Write([]byte(resp))
}

6. In-Memory State & TTL Expiration

All virtual bridge mappings are ephemeral:

  • Bidirectional Keys in Redis:
    • bridge:V_K:P_Customer -> P_Driver
    • bridge:V_K:P_Driver -> P_Customer
  • Automatic Expiration (TTL): Keys are initialized with a 2-hour TTL. Upon order completion, the TTL is shortened to 15 minutes, allowing a brief window for lost item retrieval before the bridge is reclaimed into the virtual pool.

7. Telecom Edge Failure Modes & Resilience

Failure Scenario Impact Resilience Mitigation
Redis Cluster Failure Gateway cannot resolve mapping Fallback to in-memory local cache sidecar + secondary Redis replica in under 5ms
Carrier Webhook Timeout Telco drops call In-app VoIP calling (WebRTC) offered as one-tap backup
Number Pool Exhaustion All numbers allocated to active trips Dynamic surge pool expansion via secondary telecom carrier SIP trunks

8. Key Architectural Takeaways

  • Virtual Number Multiplexing Saves Millions: By identifying active orders via the combination of Caller CLI + Virtual Number, a single virtual number can safely serve hundreds of simultaneous trips.
  • Telecom Webhooks Demand Extreme Latency SLAs: Telco switches terminate calls within 1.5s of silence. In-memory data structures (Redis) and zero-allocation Go handlers guarantee sub-100ms routing.
  • Automate Bridge Teardowns with TTLs: Enforce strict time-to-live policies to automatically expire bridges post-trip, preventing lingering harassment channels.
  • Provide VoIP Fallback Channels: Network carriers will experience regional trunk outages. In-app WebRTC calling provides a seamless, carrier-independent fallback.
