How MySQL's Midpoint Insertion Strategy Prevents Cache Pollution

By Arpit Bhayani Dissection & MySQL InnoDB Team • October 2026 • 14 min read

1. The Naive LRU & The Cache Pollution Hazard

In relational database engines, memory is the primary defense against latency. Modern disk subsystems (even NVMe SSDs) exhibit latencies measured in microseconds, whereas DRAM access operates in nanoseconds (roughly a $100\times$ to $1000\times$ difference). Consequently, MySQL's InnoDB storage engine allocates the vast majority of its RAM to the Buffer Pool—an in-memory cache holding pages (typically 16 KB each) of data tables, indexes, and undo logs.

The canonical data structure for an eviction cache is the Least Recently Used (LRU) list. In a textbook LRU implementation:

  • When a page is read from disk, it is inserted directly at the head of the doubly linked list.
  • When an existing cached page is read or updated, it is promoted to the head.
  • When memory is full and a new page arrives, the victim page sitting at the tail is evicted.
The Catastrophe of Naive LRU (Cache Pollution): Consider a primary production database handling $50,000$ transactional point-lookups per second ($QPS$). Suddenly, an analytical query, a batch report, or a daily mysqldump backup executes: 
SELECT * FROM orders WHERE created_at >= '2023-01-01';
This query performs a full table scan, reading millions of pages sequentially from disk. In a naive LRU, each one of these scanned pages is placed at the head of the list. Within seconds, hundreds of thousands of one-off, scan-only pages displace the genuinely hot transactional pages (user accounts, session records, active orders) from memory. Cache hit ratio plummets from $99.8\%$ to below $60\%$, disk I/O saturates at $100\%$, and transactional p99 latency spikes uncontrollably. This is known as Cache Pollution or Cache Thrashing.

2. InnoDB Buffer Pool Memory Anatomy

To understand how InnoDB defeats cache pollution, we must inspect the internal memory structures of the Buffer Pool. The Buffer Pool consists of three concurrent doubly-linked lists operating across the same pool of page descriptors (buf_page_t):

  1. Free List: Contains completely empty, unallocated page frames ready to store incoming disk data.
  2. Flush List (Dirty Pages): Tracks modified pages in order of their oldest unwritten LSN (Log Sequence Number) that must eventually be checkpointed to disk.
  3. LRU List: Contains all allocated pages currently mapped to table spaces, ordered by recency of access.

3. The Midpoint Insertion Algorithm

InnoDB rejects the naive textbook LRU. Instead, it employs a Midpoint Insertion Strategy (originally introduced in MySQL 5.1 and refined in MySQL 5.5+).

The Buffer Pool LRU list is conceptually bisected into two dynamic partitions:

  • New Sublist (Young Sublist): The top portion of the list, holding hot, frequently referenced pages. By default, this occupies roughly $63\%$ (or $5/8$) of the LRU list.
  • Old Sublist: The bottom portion of the list, holding colder pages that are candidates for eviction. By default, this occupies roughly $37\%$ (or $3/8$) of the list.

The boundary between the two sublists is known as the Midpoint. Crucially:

The Core Invariant: When a page is read from disk because of a query miss, InnoDB does not insert it at the head of the LRU list. It inserts the page at the head of the Old Sublist (the Midpoint)!

Because newly read pages land at the midpoint, they enter the cold partition immediately. If a table scan reads 1,000,000 pages that are never accessed again, those pages enter at the midpoint, travel down the short Old Sublist ($37\%$ of the cache), and drop off the tail. The hot pages residing in the New Sublist ($63\%$ of the cache) remain completely untouched and never get evicted!

4. New Sublist vs. Old Sublist Dynamics

Let us trace the exact state transitions of a page through the LRU list: 

stateDiagram-v2
    [*] --> DiskMiss: Query requests uncached page
    DiskMiss --> OldSublistHead: Insert at Midpoint (old_blocks_pct)
    
    state OldSublist {
        OldSublistHead --> DriftingDown: Not accessed again
        DriftingDown --> Evicted: Reaches Tail of LRU
        
        OldSublistHead --> AccessedInOld: Query re-references page
    }
    
    AccessedInOld --> Evaluated: Check innodb_old_blocks_time
    
    state Evaluated {
        [*] --> CheckTime
        CheckTime --> Ignored: Age < innodb_old_blocks_time
        CheckTime --> Promoted: Age >= innodb_old_blocks_time
    }
    
    Ignored --> DriftingDown: Burst read during same scan
    Promoted --> NewSublistHead: "Made Young" (Moved to LRU Head)
    
    state NewSublist {
        NewSublistHead --> GradualAge: Newer hot queries arrive
        GradualAge --> CrossMidpoint: Pushed past 63% boundary
    }
    
    CrossMidpoint --> OldSublistHead: Becomes part of Old Sublist
    Evicted --> [*]

Notice how the Old Sublist acts as a quarantine isolation zone. Pages must earn their place in the New Sublist through sustained, multi-turn utility rather than one-off table scan operations.

5. The "Making Young" Heuristic & Time Window

A critical flaw still existed in the initial midpoint implementation: nested-loop joins and multi-row scans of the same page.

A single 16 KB InnoDB page typically stores between 50 and 500 rows. When a query scans a table:

  1. Row 1 on Page $P$ is read. Page $P$ is fetched from disk and placed at the midpoint.
  2. Microseconds later, the query engine scans Row 2 on Page $P$. This is an in-memory hit!
  3. Under a simple "promote on hit" rule, Row 2 would trigger an immediate promotion, moving Page $P$ straight to the head of the New Sublist!

Thus, even with a midpoint insertion, a sequential scan touching multiple rows per page would instantly defeat the quarantine and pollute the hot cache.

The Solution: innodb_old_blocks_time

To neutralize this loop, InnoDB tracks the timestamp of when a page was inserted into the Old Sublist. MySQL exposes a parameter:

innodb_old_blocks_time = 1000 (Default: 1000 milliseconds / 1 second)

When an access occurs on a page sitting in the Old Sublist, InnoDB calculates: $$\Delta t = t_{\text{current}} - t_{\text{first\_access}}$$

  • If $\Delta t < \text{innodb\_old\_blocks\_time}$: The access is classified as part of the same sequential operation. The page is read, but it is not promoted to the New Sublist. Its position remains in the Old Sublist.
  • If $\Delta t \ge \text{innodb\_old\_blocks\_time}$: The page was accessed across distinct user queries separated by real time. The page is declared genuinely useful and is "Made Young", jumping to the head of the New Sublist.

6. Read-Ahead Engines: Linear vs. Random

InnoDB also features asynchronous Read-Ahead engines that predict future page requests and prefetch them into memory before the application query blocks on I/O.

Read-Ahead Type Trigger Condition Behavior Configuration
Linear Read-Ahead InnoDB detects that innodb_read_ahead_threshold pages in an extent (64 pages = 1 MB) were read sequentially. Asynchronously issues a read request for the entire subsequent extent into the buffer pool. innodb_read_ahead_threshold = 56 (default)
Random Read-Ahead InnoDB detects that 13 contiguous pages inside the same extent happen to be in the buffer pool. Prefetches the remaining pages of that extent into memory regardless of access order. innodb_random_read_ahead = OFF (disabled by default)

Because all read-ahead pages enter at the midpoint (Old Sublist), prefetching errors are harmless: if the precalculated pages are never actually requested, they evaporate silently at the LRU tail without displacing a single byte of hot application state.

7. Production Tuning: innodb_old_blocks_pct & time

How should database administrators and system architects tune these parameters in real-world high-throughput environments?

1. innodb_old_blocks_pct

Specifies the percentage of the Buffer Pool assigned to the Old Sublist. Allowed range: $5$ to $95$. Default: $37$.

  • Pure OLTP (Transactional Web Services): If the database is exclusively handling point lookups (e.g., Redis-like primary key lookups with zero analytics), reduce innodb_old_blocks_pct to 20. This gives $80\%$ of RAM to the New Sublist, packing more hot data into memory.
  • Mixed Workloads (OLTP + Reporting/ETL): Keep at 37 or increase to 50. This provides a wider absorption buffer for scans, ensuring heavy reporting jobs cannot touch the hot transactional core.

2. innodb_old_blocks_time

Specifies the retention quarantine window in milliseconds before promotion. Default: $1000$ ms.

  • Increasing this value (e.g., to $2000$ ms) strengthens protection against very slow, high-latency analytical table scans that spend more than 1 second iterating over multiple pages.
  • Setting this to $0$ disables the time gate, causing any second hit on an old page to immediately promote it to the young list (not recommended on mixed workloads).

8. First-Principles Summary & Design Lessons

The MySQL Midpoint Insertion Strategy is an archetype of systems software design:

  • Textbook algorithms rarely survive production: Naive LRU assumes uniform, randomized access distributions. Real production systems exhibit mixed modalities (Zipfian point-lookups interleaved with linear batch scans).
  • Partitioning protects the core: By dividing an eviction list into young and old partitions, systems isolate distinct access patterns with zero cross-contamination.
  • Time gates prevent algorithmic manipulation: Spatial hits (multiple rows within one page) must be decoupled from temporal utility using access timestamps ($t_{\text{access}} - t_{\text{insert}} > \text{threshold}$).
