Atlassian April 2022 Mega Outage: Why a Communication Gap Caused a 14-Day Downtime for 775 Customers

On April 5, 2022, 775 enterprise businesses logged into Jira, Confluence, and Opsgenie only to be met with dead endpoints. What began as a routine maintenance task to disable a deprecated Marketplace app cascaded into a catastrophic 14-day global outage. Explore the engineering anatomy of this disaster: how identical UUID namespaces and script parameter misunderstandings triggered irreversible multi-service deprovisioning, and why the complete absence of bulk restoration tooling forced manual database surgery across two grueling weeks.

1. Executive Summary & The 14-Day Timeline

In cloud distributed systems, most severe outages last minutes or hours—a cascading retry storm, an expired TLS certificate, or a corrupted BGP route. When an outage persists for 14 consecutive days, it indicates a structural breakdown in the fundamental lifecycle architecture of the platform.

  • Affected Scope: 775 cloud enterprise tenants (representing ~0.3% of Atlassian’s customer base, but disproportionately large enterprise organizations).
  • Products Knocked Offline: Jira Software, Jira Service Management, Confluence, Opsgenie, Statuspage, and Atlassian Access.
  • Duration: April 5, 2022 to April 19, 2022 (full restoration took 336 hours).
  • Data Loss: Zero customer data lost. All data remained encrypted and stored on Amazon EBS and RDS snapshots, yet systems were completely unreachable and non-functional.

The central paradox of the incident: If no customer data was destroyed, why did it take a world-class engineering organization two full weeks to bring 775 websites back online? The answer lies in the Asymmetry of Operational Tooling.

2. The Fatal Miscommunication & Parameter Confusion

The incident originated from a migration cleanup. Previously, Atlassian acquired a third-party asset management app called Insight - Asset Management from the Atlassian Marketplace. Over several quarters, engineering integrated Insight directly into Jira Service Management as a native core capability.

Consequently, customers who had previously installed the standalone Marketplace app now had two versions running concurrently: the legacy Marketplace add-on and the integrated native version. Engineering scheduled a cleanup script to deactivate the deprecated Marketplace add-on for 775 specific tenants.

┌──────────────────────────────────────────────────────────────────────────┐ │ THE FATAL INPUT │ ├──────────────────────────────────────────────────────────────────────────┤ │ Engineering Team A intended to pass: │ │ App_ID / Extension_ID = "com.riadalabs.jira.plugins.insight" │ │ Target Scope = [Site_1, Site_2, ... Site_775] │ │ │ │ Operating Team B executed administrative deactivation script: │ │ ./deactivate-site.sh --ids [Site_1, Site_2, ... Site_775] │ │ │ │ RESULT: The script invoked the Tenant Site Deprovisioning API, │ │ deleting all 775 cloud tenant environments instead of the app! │ └──────────────────────────────────────────────────────────────────────────┘

The administrative script accepted a generic list of IDs. Because Atlassian utilized uniform, raw UUIDs without type prefixes (e.g. b4e2f910-482a-4a88-8422-92a0e5b901a1), the script could not discern whether the parameter represented an App ID, an Organization ID, or a Customer Site ID.

3. The Automated Cascading Soft-Delete Pipeline

Atlassian’s cloud infrastructure is organized around autonomous microservices coordinated through an identity and tenant directory platform (Identity / Provisioning Engine). When the script ran, it called the internal mark_site_deleted() API endpoint.

The system operated exactly as engineered: modern cloud platforms are optimized for rapid, automated tenant cleanup to ensure GDPR/CCPA compliance and reclaim cloud resources. Within seconds, a cascading event storm propagated across the entire service fleet:

flowchart TD Script[Admin Script: Deactivate Site IDs] --> Provisioning[Identity & Tenant Provisioning API] Provisioning -->|Mark Site Tombstoned| TenantDB[(Global Tenant Directory)] Provisioning -->|Publish SiteDeactivated Event| Bus[Kafka / SQS Event Bus] Bus --> Routing[Global API Gateway / DNS Router] Bus --> Jira[Jira Microservice Fleet] Bus --> Conf[Confluence Microservice Fleet] Bus --> Auth[Atlassian Access / SAML SSO] Bus --> Storage[S3 Attachment Storage Layer] Routing -->|Drop Virtual Host Mapping| 404[Return HTTP 404 / 410 Gone] Jira -->|Detach RDS Tenant Schema| JiraDB[(RDS Multi-Tenant Shards)] Conf -->|Drop Space Permissions & Lucene Index| ConfDB[(Confluence RDS Shards)] Auth -->|Revoke OAuth / Invalidate User Tokens| SSO[Okta / Azure AD Invalidation] Storage -->|Mark S3 Objects Orphaned| S3[(Customer File Buckets)]

Within minutes, 775 customer tenants were vanished from global routing tables. DNS hosts resolved to maintenance pages, user sessions were revoked, and database schemas were marked unmapped.

4. Why Recovery Took 14 Days: Automation Asymmetry

When incident responders realized what occurred, the immediate thought was: "Just flip is_deleted = false in the database!"

This was impossible due to the Asymmetry of Lifecycle Operations:

  • Automated Deconstruction: Deletion was a fully automated, asynchronous, fan-out event with high test coverage, built to teardown resources cleanly in seconds.
  • Manual Reconstruction: "Site Undelete" had never been built as an automated bulk API. In Atlassian's entire corporate history, a site deactivation was either permanent (customer canceled subscription) or handled as a bespoke, manual, one-off ticket by support engineers once every few months.
  • Microservice State Divergence: Soft-delete wasn't a single database column. It triggered distributed side effects across dozens of independent datastores—Jira relational schemas, Confluence Lucene search indexes, S3 attachment access policies, and central Atlassian Access authentication tokens.

To restore a single site, an engineer had to stitch back together fractured relational links across 15+ microservices, ensure zero data loss, and verify that no orphaned records were leaked.

5. Multi-Tenant Database Reconstruction Mechanics

The hardest bottleneck during the 14-day recovery was the physical architecture of Atlassian's data tier: Multi-Tenant Shared RDS Shards.

Atlassian does not allocate a dedicated AWS RDS instance per customer. Instead, hundreds of customer tenants share the same Amazon Aurora PostgreSQL and MySQL database clusters, separated logically by tenant_id or dedicated schemas within the shared database.

AWS RDS Aurora Multi-Tenant Cluster (Shard 42) ┌────────────────────────────────────────────────────────────────────────┐ │ Tenant A (Active) │ Tenant B (DEACTIVATED) │ Tenant C (Active) │ │ 400,000 Jira Issues │ 2,500,000 Issues (404) │ 120,000 Issues │ ├───────────────────────┴────────────────────────┴───────────────────────┤ │ Point-In-Time Snapshot cannot be restored over live Shard 42! │ │ Overwriting Shard 42 would destroy all new writes to Tenant A and C! │ └────────────────────────────────────────────────────────────────────────┘

Why point-in-time recovery (PITR) could not be executed directly:

  1. If Atlassian restored the entire RDS snapshot from before the script execution, it would revert the database state for the thousands of active, unaffected customers sharing those same shards, destroying hours of their legitimate business transactions!
  2. Therefore, to recover Tenant B:
    • Spin up a separate, temporary Aurora RDS cluster from the historical snapshot.
    • Write custom extraction scripts to export only Tenant B's relational tables, issue histories, comments, custom fields, and foreign keys.
    • Sanitize and transform the exported dataset to match current production schema versions.
    • Import the tenant dataset into the live production cluster without taking write locks that would degrade active neighboring tenants.
    • Re-index Elasticsearch/Lucene search clusters for that tenant.

Restoring a single tenant took between 2 and 8 hours. Multiplying this by 775 tenants across a finite pool of authorized senior database administrators resulted in the grueling 14-day recovery window.

6. Root Cause Analysis & Systemic Vulnerabilities

The official post-mortem revealed several foundational distributed systems design anti-patterns:

1. Untyped Global Identifiers

When entity IDs are raw UUIDs (e.g. UUIDv4), compiler type-checking and CLI validators cannot distinguish an App ID from a Customer Site ID. A script receiving site_id when expecting app_id executed silently without raising type errors.

2. Infinite Blast Radius & Absence of Rate Limiting

The administrative script allowed unbounded array sizes. An operator could pass 1 ID or 100,000 IDs in a single invocation. There was no internal rate limiter, circuit breaker, or canary batching (e.g. "Deactivate 1 site, wait 10 minutes, evaluate metrics, then proceed").

3. Lack of Multi-Party Authorization (The 4-Eyes Principle)

A high-severity administrative action with irrevocable customer impact was executable by a single operator without requiring cryptographic dual-control or peer sign-off in the terminal workflow.

4. Neglect of Reverse-Path Engineering

Engineering teams heavily invested in fast, automated deletion paths for compliance, while entirely neglecting the reverse restoration pathway. An operational capability is only as safe as its tested rollback procedure.

7. Post-Incident Architectural Reforms

Following the outage, Atlassian implemented transformative infrastructure and cultural changes across its cloud platform:

flowchart LR subgraph Pre-2022 Vulnerability A1[Raw UUIDs] --> B1[CLI Tool] B1 --> C1[Infinite Batch Size] C1 --> D1[Single-Click Deletion] end subgraph Post-2022 Hardened Architecture A2[Prefixed Typed IDs: site_xxx] --> B2[Schema-Validated CLI] B2 --> C2[Canary Limiter: Max 5/batch] C2 --> D2[Multi-Party 4-Eyes Approval] D2 --> E2[Automated 30-Day Instant Rollback API] end

1. Prefixed, Strongly Typed Identifiers

All internal identifiers were migrated to type-prefixed formats (inspired by Stripe's ID standard). For example:

  • Tenant Site ID: site_live_9x8f2a1b...
  • App / Add-on ID: addon_insight_7c4d1e...
  • Workspace ID: wrk_prod_3b9a0c...

Any internal API receiving an ID string runs strict prefix validation at the gateway; submitting a site_ token to an addon_ endpoint fails immediately with HTTP 422 Unprocessable Entity.

2. Blast Radius Circuit Breakers

Destructive administrative APIs enforce hard operational boundaries:

  • Maximum batch limit of 10 sites per command.
  • Mandatory canary stage: deprovision 1 entity, pause execution, and require manual confirmation after monitoring tenant health signals.
  • Administrative rate limiters throttle deactivations across the global fleet.

3. Automated Tenant Reconstitution & Instant Rollback

Atlassian engineered an automated bulk restoration pipeline. "Soft-delete" was redefined: all downstream microservices retain encrypted metadata pointers and tombstoned rows in cold storage for 30 days. An automated single-click reconstitute_tenant(site_id) API can orchestrate multi-service restoration across Jira, Confluence, and Access in under 5 minutes without manual database dumps.

8. Resilient vs. Brittle Administrative Architecture

Dimension Legacy / Fragile Operations Resilient Distributed Enterprise Operations
ID Typing Raw UUIDv4 strings (Identical across domain models) Type-prefixed, schema-validated IDs (e.g. site_, addon_)
Operational Blast Radius Unbounded array inputs in scripts Strict batch limits, canary staging, and fleet rate limiters
Authorization Protocol Single-operator script execution Multi-party 4-eyes approval with cryptographically signed tokens
Restoration Tooling Manual, serialized database snapshot extraction Automated multi-service bulk tenant reconstitution APIs
Disaster Recovery Drills Focus on infrastructure failover (AZ/Region loss) Tenant-level logical disaster recovery and corruption drills

9. Key Architectural Takeaways

  • Deletion Without Tested Rollback Is Technical Debt: If your system features an automated, high-speed deletion or deprovisioning pipeline, you must invest proportional engineering effort into an automated rollback pipeline.
  • Design for Blast Radius Minimization: Administrative tooling must assume human error. Hard limits on batch sizes, canary deactivations, and circuit breakers prevent a single miskeyed argument from taking down hundreds of enterprise accounts.
  • Shared Multi-Tenant Storage Amplifies Recovery Friction: Logical tenant isolation on shared physical database shards makes point-in-time snapshot recovery exponentially complex. Design logical tenant-level snapshotting and export tools from day one.
  • Embed Semantic Type Hints in Identifiers: Raw UUIDs are an invitation to catastrophic parameter confusion. Prefixing identifiers with their entity domain (e.g. tenant_, app_) eliminates cross-parameter errors at the API gateway layer.
