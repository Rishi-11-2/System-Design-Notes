A Bug in GitHub's Rate Limiter: The Wobbling Reset Header

By Arpit Bhayani Dissection & GitHub Engineering • October 2026 • 14 min read

1. Context: GitHub's API Rate Limiting Contract

GitHub's public REST and GraphQL APIs serve billions of developer requests every day. To protect infrastructure from accidental runaway scripts and malicious abuse, GitHub enforces strict rate limits (e.g. 5,000 requests per hour for authenticated personal access tokens).

In accordance with standard HTTP API conventions, GitHub includes rate-limiting metadata in every response header: 

HTTP/1.1 200 OK
X-RateLimit-Limit: 5000
X-RateLimit-Remaining: 4982
X-RateLimit-Reset: 1724064530
  • X-RateLimit-Limit: The maximum number of requests allowed in the current window.
  • X-RateLimit-Remaining: The number of remaining requests available before throttling begins.
  • X-RateLimit-Reset: The Unix epoch timestamp (in seconds) marking the exact moment when the current 1-hour window expires and resets.

Automated client libraries, CI/CD runners, and developer SDKs rely heavily on X-RateLimit-Reset: when a client receives an HTTP 429 response, it sleeps for $\Delta t = \text{Reset} - \text{CurrentTime}$ before retrying.

2. The Anomaly: The "Wobbling" Reset Header

Several years ago, observant developers noticed strange behavior in GitHub's API responses: when issuing multiple concurrent requests within the exact same second, the X-RateLimit-Reset timestamp was not stable.

Instead of staying constant throughout the hour, the reset timestamp wobbled back and forth by one second across consecutive calls:

    Note over Client: Client SDK backoff scheduler gets confused!
The Impact: While a 1-second drift might seem trivial, to automated systems computing exponential backoffs or scheduling batch jobs, an oscillating reset timestamp caused flaky unit tests, broken retry queues, and race conditions in distributed client pools.

3. Root Cause: Dynamic TTL Arithmetic Flaws

Why would an immutable 1-hour window reset timestamp fluctuate?

The bug was rooted in how GitHub originally calculated the reset value. Rather than storing the absolute expiration timestamp when the rate-limiting key was created, the application server calculated it dynamically on every single incoming request!

The original implementation flow looked like this:

  1. The user sends a request. The application server issues an INCR to increment the user's request count in Redis.
  2. If the key was newly created, it issued EXPIRE user:12345 3600.
  3. To return the X-RateLimit-Reset header, the Ruby application server executed: 
    ttl_remaining = redis.ttl("user:12345") # Returns integer seconds e.g. 3542
reset_timestamp = Time.now.to_i + ttl_remaining

Notice the formula: $$\text{Reset} = \text{Time.now} + \text{redis.ttl}(\text{key})$$ This seemingly harmless line of code contains a catastrophic distributed systems flaw.

4. The Distributed Time & Clock Drift Trap

The calculation spans two completely separate systems and two separate clocks:

    subgraph "Distributed Components with Independent Clocks"
        APP1[App Server Node 1: Time.now = 12:00:00.450]
        APP2[App Server Node 2: Time.now = 12:00:00.520]
        REDIS[(Redis In-Memory Server: Independent TTL Clock)]
    end

    APP1 -->|1. PING redis.ttl()| REDIS
    REDIS -->|2. Returns integer: 3599s| APP1
    APP1 -->|3. Math: 12:00:00.450 + 3599s| R1[Reset = 1724064530]

    APP2 -->|1. PING redis.ttl()| REDIS
    REDIS -->|2. Crossed subsecond threshold: Returns 3599s| APP2
    APP2 -->|3. Math: 12:00:00.520 + 3599s (Rounded up!)| R2[Reset = 1724064531]

The Three Compounding Flaws:

  • Integer Truncation in Redis TTL: Redis's standard TTL command rounds remaining milliseconds down to integer seconds. A key with $3599.9\text{s}$ remaining and a key with $3599.1\text{s}$ remaining both return 3599.
  • Network Latency Jitter: The application server records Time.now either before or after the Redis network round-trip. If a network packet incurs a $5\text{ ms}$ delay that crosses an integer second boundary, the sum jumps by an entire second.
  • Distributed Clock Drift: GitHub routes API traffic across hundreds of application server nodes. Even with Network Time Protocol (NTP) synchronization, server clocks experience minor sub-millisecond drift ($\Delta t \approx 1\text{ms} - 10\text{ms}$). Consecutive requests landing on different application pods evaluate different base times, creating the oscillating "wobble".

5. The Fix: Absolute Timestamp Persistence & Lua

The fundamental rule of distributed systems debugging applies: Never compute fixed truths dynamically from moving parts.

Instead of dynamically calculating the reset timestamp on every request by querying Redis's decaying TTL, the architecture was refactored so that:

The Solution: Upon creating the rate-limiting window, the server computes the absolute expiration timestamp once: $$\text{ResetTimestamp} = \text{WindowStartTime} + 3600$$ This absolute Unix timestamp is persisted directly inside Redis alongside the request counter!

Every subsequent request during that window simply reads the pre-stored timestamp. Because the value is immutable and stored in one place, every application server returns the exact same integer timestamp to the millisecond.

6. Production Implementation: Atomic Redis Script

To ensure that initializing the window, incrementing the counter, and retrieving the reset timestamp occur with zero race conditions, GitHub utilizes an atomic Redis Lua Script: 

-- rate_limiter.lua
-- KEYS[1]: Rate limit key (e.g. "rate:user_12345")
-- ARGV[1]: Max quota (e.g. 5000)
-- ARGV[2]: Window duration in seconds (e.g. 3600)
-- ARGV[3]: Current server timestamp (Unix epoch seconds)

local key = KEYS[1]
local limit = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local now = tonumber(ARGV[3])

-- Check if key exists
local data = redis.call("HMGET", key, "count", "reset_at")
local count = tonumber(data[1])
local reset_at = tonumber(data[2])

if not count then
    -- Window does NOT exist; initialize new window
    count = 1
    reset_at = now + window
    redis.call("HMSET", key, "count", count, "reset_at", reset_at)
    redis.call("EXPIRE", key, window)
else
    -- Window exists; atomically increment counter
    count = redis.call("HINCRBY", key, "count", 1)
end

local remaining = math.max(0, limit - count)
local allowed = count <= limit and 1 or 0

-- Return: [allowed, count, remaining, reset_at]
return { allowed, count, remaining, reset_at }

7. First-Principles Summary & Design Lessons

Design Dimension The Flawed GitHub Implementation The Correct Architecture
Source of Truth Dynamic calculation: Time.now + redis.ttl() Static persisted absolute timestamp: reset_at
Clock Dependencies Depended on two clocks (App Server + Redis) Single clock timestamp persisted upon creation
Precision Loss Redis integer TTL truncation created $\pm 1\text{s}$ rounding wobble Exact integer epoch stored permanently
Atomicity Separate INCR and TTL network round-trips Atomic single-hop Lua script execution
Key Takeaway: Distributed systems bugs often hide in innocent arithmetic. Whenever a system calculates state by combining local wall-clock time with external remote TTLs across network hops, non-deterministic rounding and clock drift will inevitably corrupt the result.
