Load Balancers are Not Magic: Dissecting Atlassian's Cloud Outage

By Arpit Bhayani Dissection & Cloud Reliability Engineering • October 2026 • 15 min read

1. The "Infinite Black Box" Fallacy

In cloud-native system design, managed load balancers (such as AWS Application Load Balancers (ALBs) or Classic ELBs) are frequently treated by software engineers as magical, abstract primitives. Diagrams depict an ELB as a tiny cloud or diamond icon that absorbs infinite client queries, negotiates TLS, terminates HTTP/2, and smoothly balances requests across backend worker pods.

This mental model is dangerously flawed. Load balancers are not magic. Load balancers are computers.

Behind every managed load balancer DNS name (e.g. my-service-12345.elb.amazonaws.com) sits a dynamic fleet of standard EC2 proxy instances running customized proxies (such as Envoy or Nginx). They possess finite CPU cores, physical network interface cards (NICs), finite Linux socket buffers, connection state tracking tables, and finite RAM. If subjected to instantaneous surges or deployed improperly, they can run out of memory, crash with Out-Of-Memory (OOM) kernel panics, and trigger catastrophic platform-wide outages.

2. Anatomy of the Atlassian Incident

In 2019, Atlassian suffered a severe, confounding cloud outage affecting multiple cloud products. The operational metrics presented an eerie paradox:

  • Healthy Backend Fleets: The backend microservices (Jira and Confluence API pods) exhibited $0\%$ error rates, low CPU utilization, abundant RAM, and healthy healthcheck responses.
  • Total User Blackout: Millions of end-users were receiving connection resets, timeouts, and HTTP 502/504 errors.
  • Zero Request Ingress: Telemetry showed that incoming requests reaching the backend pods had flatlined to zero! Traffic wasn't failing in the application layer—it wasn't even reaching the front door.

3. What Actually Happens Inside an Elastic Load Balancer?

To understand why the load balancer died, we must inspect the internal operating model of AWS Elastic Load Balancing:

  1. Dynamic DNS Allocation: An ELB DNS record resolves to multiple public IP addresses. Each IP address corresponds to an individual EC2 proxy instance provisioned by the cloud provider inside each Availability Zone (AZ).
  2. Horizontal Auto-Scaling of Proxies: As traffic increases gradually, AWS monitoring daemons detect rising CPU or network bandwidth on the proxy nodes, spin up additional proxy instances, and add their new IP addresses to the Route 53 DNS round-robin pool.
  3. The Multi-Minute Scaling Lag: Provisioning new proxy instances, joining them to network VPCs, warming connection buffers, and propagating Route 53 DNS TTLs takes between 3 and 10 minutes.
The Scale-Out Rate Limit: AWS ELB cannot scale from $2\text{ proxy nodes}$ to $50\text{ proxy nodes}$ in milliseconds. It requires a sustained, gradual ramp-up curve (typically $+50\%$ traffic over 5 minutes) to trigger auto-scaling without dropping packets.

4. The Cold Deployment Trap

The root cause of Atlassian's outage was an architectural anti-pattern in their automated deployment pipeline: recreating load balancers on blue/green deployments.

Rather than keeping existing, warmed-up load balancers and shifting backend target groups, the automated pipeline:

  • Spun up a completely fresh "Green" environment, complete with a brand-new, cold ELB.
  • A brand-new ELB initializes with the minimum default footprint: typically just one or two tiny proxy instances per AZ.
  • The pipeline updated Route 53 DNS to instantly swing 100% of global production traffic (tens of thousands of requests per second with hundreds of thousands of concurrent TCP sockets) from the old, warmed cluster to the brand-new, ice-cold ELB!

5. Proxy Memory Exhaustion & TCP State Flooding

When the massive tsunami of global traffic collided with the tiny two-node proxy cluster:

The Anatomy of Proxy OOM:
  1. TLS Cryptographic Overhead: 50,000 simultaneous TLS handshakes consumed 100% of the proxy nodes' CPU cores executing asymmetric RSA/ECDHE key exchanges.
  2. TCP Socket Buffer Saturation: Every open TCP connection allocates Linux kernel socket buffers (rmem and wmem, typically 16 KB to 128 KB per socket). Hundreds of thousands of concurrent SYN packets rapidly consumed all available DRAM.
  3. Connection State Table Exhaustion: The proxy software's in-memory connection tracking tables blew past available physical memory.
  4. The Kernel OOM Killer: The Linux kernel invoked oom-killer, instantly terminating the Envoy/Nginx proxy processes. The proxies crashed, rebooted in a loop, and stopped responding entirely.

6. Mitigation: Pre-Warming, Target Shifting & Rate Gates

Following the postmortem, Atlassian and the broader systems engineering community established rigorous architectural guardrails:

1. Shift Targets, Never Recreate Load Balancers

In modern CI/CD, the load balancer tier must be treated as long-lived, persistent infrastructure:

2. Pre-Warming Load Balancers for Surges

When anticipating massive flash sales, product launches, or regional migrations, teams must coordinate with cloud support to pre-warm the load balancer fleet. Cloud engineers pre-scale the proxy cluster to dozens of high-memory instances in advance, preventing cold-start collapse.

3. Gradual DNS Weighted Shifts & Rate Limiting

If DNS-level cutovers are unavoidable, traffic must be shifted gradually over time using weighted Route 53 record sets: $$10\% \xrightarrow{5\text{ mins}} 25\% \xrightarrow{5\text{ mins}} 50\% \xrightarrow{5\text{ mins}} 100\%$$ This gradual curve grants the cloud auto-scaler sufficient observation windows to scale out proxy capacity organically.

7. First-Principles Summary & Design Lessons

Architecture Vector Naive Anti-Pattern Production Engineering Standard
Load Balancer Model Assuming managed ELBs have infinite, instant capacity Recognizing ELBs are fleets of real servers with finite CPU, RAM, and scaling lag
Deployment Strategy Destroying and recreating ELBs on every blue/green deploy Keeping pre-warmed ELBs static; shifting backend target groups dynamically
Traffic Cutover Instant 0% to 100% Route 53 DNS flips Gradual weighted percentage ramp-ups over 15–30 minutes
Surge Preparation Relying on reactive cloud auto-scaling during spikes Proactive pre-warming of proxy fleets prior to high-traffic events
