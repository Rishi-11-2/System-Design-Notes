1. The Indexing Trilemma

In data architecture, engineers have historically been forced into a rigid indexing trilemma. Every storage paradigm optimizes for one specific access pattern while degrading others:

Index Architecture Primary Strength Critical Failure Mode Representative Engines
Row Store Fast point lookups ($O(1)$) and whole-record updates/retrievals. Catastrophic IO waste on analytical aggregations; must read entire row blocks into RAM. PostgreSQL, MySQL, RocksDB
Column Store Vectorized SIMD scans and mathematical aggregations (SUM, AVG). Inefficient point lookups; reconstructing an entire entity requires multi-column stitching. ClickHouse, Snowflake, Parquet
Search (Inverted) Index High-selectivity filtering, boolean predicates, and full-text token search. Slow numeric computation and complete inability to perform distributed relational joins. Elasticsearch, Apache Lucene

To overcome this, traditional architectures stitch together three separate systems (e.g., PostgreSQL for transactions + Elasticsearch for search + Snowflake for analytics) connected by fragile ETL pipelines, causing data synchronization lag and schema drift.

2. The Converged Index™ Concept

Rockset eliminates the indexing trilemma through the Converged Index™. Rather than forcing developers to declare secondary indexes or choose between row and column storage, Rockset automatically shreds every incoming semi-structured document and constructs all three index structures simultaneously inside an embedded Log-Structured Merge-tree (RocksDB).

3. RocksDB Key-Value Layout & Encoding

At the physical storage tier, RocksDB is a byte-oriented key-value store. Rockset maps row, column, and inverted index components into sorted byte keys:

1. The Inverted Search Index Format

For every field and value, an entry is inserted into RocksDB where the value is part of the key:

Key = [CollectionID] : [FieldPath] : [ValueType] : [FieldValue] : [DocID] → Value = ∅

A query with a predicate like WHERE status = 'PAID' performs an instantaneous RocksDB prefix seek on [CollectionID]:['status']:['string']:['PAID'], scanning only the matching document IDs with zero document decoding.

2. The Columnar Index Format

Values of a field across a chunk of documents (e.g., 64 to 256 consecutive docs) are grouped contiguously:

Key = [CollectionID] : [FieldPath] : [ChunkID] → Value = [Packed Compressed Array of Values]

This layout enables SIMD (Single Instruction, Multiple Data) vectorized execution: the CPU loads a cache line containing dozens of packed numeric floats (e.g., total), computing aggregations like SUM() at memory-bus saturation speed.

3. The Row Store Format

To support whole-document queries (e.g., SELECT * FROM orders WHERE id = 'ord_101'), fields are stored by document key:

Key = [CollectionID] : [DocID] : [FieldPath] → Value = [FieldValue]

A point lookup executes a single prefix iterator seek over [CollectionID]:['ord_101'], reconstructing the entire original JSON tree in microseconds.

4. Smart Schema & Deep JSON Shredding

Semi-structured JSON documents contain nested objects, arrays, and mixed types. Rockset's Smart Schema shreds documents recursively into path-value tuples:

# Example Document Shredding Representation
# Input: {"order_id": "101", "user": {"city": "Berlin"}, "tags": ["sale", "express"]}

Shredded_Tuples = [
    ("order_id", "string", "101"),
    ("user.city", "string", "Berlin"),
    ("tags[0]",   "string", "sale"),
    ("tags[1]",   "string", "express"),
    ("tags",      "array_element", "sale"),    # Allows inverted index search over arrays!
    ("tags",      "array_element", "express")
]

Crucially, if one record contains {"age": 30} (integer) and another contains {"age": "thirty"} (string), both coexist seamlessly in RocksDB under distinct ValueType prefix bytes. The SQL query planner automatically handles type polymorphisms at execution time.

5. Query Optimizer Synergy Across Index Types

The true power of the Converged Index emerges when Rockset's cost-based query optimizer plans a complex SQL query:

-- Query combining selective filtering, aggregation, and point projection
SELECT 
    user.city, 
    SUM(total) AS total_revenue 
FROM orders 
WHERE status = 'PAID' AND created_at > 1704067200
GROUP BY user.city;

  1. Phase 1 (Inverted Index Filter): The engine uses the Inverted Index to rapidly evaluate status = 'PAID'. It performs a fast posting intersection, yielding a compressed Roaring Bitmap of qualifying document IDs.
  2. Phase 2 (Columnar Index Aggregation): Rather than scanning millions of irrelevant records, the columnar engine uses the qualifying document bitmap to perform vectorized SIMD scans exclusively on the total and user.city columnar chunks.
  3. Zero Waste: Non-relevant fields (e.g., shipping address, billing metadata) are never loaded into RAM.

6. Compression Mechanics & Storage Overhead

Building three indexes natively raises concerns regarding storage amplification. Rockset mitigates storage expansion using advanced columnar and block compression:

  • Dictionary Encoding: Low-cardinality strings (e.g., status codes, country names) are converted to 1-byte integer tokens.
  • Frame-of-Reference (FoR) Bit Packing: Monotonically increasing numbers (timestamps, auto-increment IDs) are stored as compressed deltas relative to a baseline.
  • RocksDB Prefix Compression & Zstandard: Adjacent keys in the inverted index share identical prefixes ([CollectionID]:['status']:...). RocksDB's prefix seek filter and block-level Zstandard (zstd) compression eliminate redundant byte sequences.
Storage Benchmark: Due to continuous deduplication and dictionary compression, Rockset's total storage footprint (all 3 indexes combined) is typically 1.5× to 2.0× of raw uncompressed JSON—comparable to or smaller than Elasticsearch's combined source + inverted index + doc_values footprint.

7. Trade-offs: Write Amplification vs. Query Latency

System Dimension Traditional Single-Index DB Rockset Converged Index
Index Management Overhead High (manual index creation, tuning, and monitoring). Zero (Automatic converged indexing on all fields).
Write Amplification Low (1 write → 1 row append). Higher (1 write → ~15–20 RocksDB KV mutations).
Write Throughput Ceiling High. Absorbed via LSM-tree sequential appends and batching.
Unplanned Query Latency Slow ($O(N)$ table scans on unindexed columns). Sub-50ms (every field is pre-indexed for all patterns).

8. Key Architectural Takeaways

  • Unify Row, Column, and Inverted Indexes: Building all three structures simultaneously inside RocksDB enables sub-second query performance without manual index declarations.
  • Smart Schemas Enable Polymorphic Data: Shredding nested JSON into path-value tuples handles sparse data, deep object hierarchies, and mixed types without schema migration friction.
  • Query Optimizer Exploits Hybrid Indexes: Combining Inverted Index filtering with Columnar SIMD aggregations eliminates 95% of memory and IO bottlenecks during analytical queries.
  • LSM-Trees Tame Write Amplification: RocksDB converts the multi-key index expansion into high-speed sequential appends, preserving sub-second ingestion-to-query visibility.
