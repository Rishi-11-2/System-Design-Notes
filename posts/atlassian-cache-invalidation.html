Case Study

Cache Invalidation at Atlassian: From SNS+SQS Push to S3 Pull

📁 Category: Case Studies
← Back to All Notes
📌 Primary Takeaway

Serving over 600,000 requests per second across 10,000+ compute nodes with a strict 11 μs p50 latency budget forced Atlassian's Tenant Context Service (TCS) to reject centralized L2 caches (Redis/Memcached) in favor of node-local L1 in-memory caches. However, keeping 10,000+ independent caches synchronized via an AWS-native SNS + SQS push fanout triggered an explosive $O(N)$ message storm: 100 metadata updates/sec created over 1,080,000 SQS messages/sec, racking up astronomical cloud bills and queue lag. By replacing push fanout with a batched, epoch-versioned S3 pull/polling model, Atlassian eliminated message amplification, cut cloud messaging costs by >90%, and established six-nines operational stability.

1. The Operational Challenge: Invalidation at Six-Nines Scale

Atlassian's Tenant Context Service (TCS) is the foundational security and authorization backbone for products like Jira, Confluence, and Bitbucket. Every incoming HTTP request must resolve:

  • Tenant Metadata: Tenant identification, license state, and feature toggles.
  • Permission Descriptors: Role-based access control and tenant isolation rules.
  • Cryptographic Keys: Per-tenant encryption keys for database and object stores.

Because every single API call across Atlassian's entire cloud platform depends on TCS, it operates under stringent requirements:

  • Throughput: > 600,000 requests per second globally.
  • Latency: Target p50 latency of 11 microseconds ($\mu\text{s}$); p99 under 1 millisecond.
  • Availability: Six-nines ($99.9999\%$) reliability — any downtime in TCS halts all customer applications globally.

Why Centralized L2 Caches (Redis/Memcached) Were Rejected

When architects look at caching tenant metadata, the immediate default is to deploy an ElastiCache Redis or Memcached cluster. Atlassian rigorously benchmarked and rejected this approach due to three fundamental disqualifiers:

🚫 Centralized L2 Cache Disqualifiers
  1. Network Round-Trip Penalty: Even within the same AWS Availability Zone, network hops take between $1\text{ ms}$ and $3\text{ ms}$. This is roughly 100x to 250x slower than the TCS $11\ \mu\text{s}$ target. In-memory local RAM lookups (via Caffeine in Java) complete in hundreds of nanoseconds.
  2. Catastrophic Blast Radius: If a centralized Redis cluster experiences network partitions, CPU saturation, or memory eviction storms, every upstream Jira and Confluence compute instance halts synchronously.
  3. Connection Pool & Socket Saturation: Over 10,000 compute nodes attempting to maintain persistent TCP connection pools to a Redis cluster leads to socket exhaustion, ephemeral port starvation, and connection churn.

Consequently, Atlassian chose Node-Local L1 In-Memory Caches running directly inside the JVM heap. Local L1 caching achieved a >99.5% cache hit ratio with zero network I/O. However, this introduced the fundamental distributed systems challenge: How do you invalidate stale entries across 10,000+ independent nodes when a tenant modifies their settings?

2. Invalidation Architectural Models Compared

Distributed systems offer three primary architectural strategies for cache invalidation. Atlassian evaluated each against their scale:

Architecture Model Data Propagation Mechanics Message Amplification Scaling Bottleneck & Trade-off
Short TTL Polling Local cache expires after fixed duration (e.g. 5 seconds); fetches DynamoDB on miss. Zero amplification; continuous steady backend queries. Massive database read load; serves stale data throughout the TTL window ($5\text{s}$).
SNS + SQS Push Fanout TCS publishes mutate events to SNS; SNS fans out to dedicated SQS queues on each node. $O(N)$ Amplification: 1 write event triggers 10,000+ SQS message operations. Explosive AWS API costs, queue sprawl, lingering dead queues, and consumer queue lag.
S3-Based Pull Batching TCS aggregates mutations and writes versioned epoch changelogs to S3. Sidecars periodically poll S3. Zero Queue Fanout: Bounded HTTP GET requests hitting S3 prefix caches. Slightly higher invalidation latency ($1\text{--}2\text{ s}$) balanced by extreme stability and minimal cost.

3. The Initial Design: The SNS + SQS Push Fanout Architecture

To achieve instantaneous cache invalidation, Atlassian initially built an event-driven push topology leveraging AWS Simple Notification Service (SNS) and Simple Queue Service (SQS):

The Mechanics of the Push Model

  • Every application instance booted with an embedded sidecar worker process.
  • Upon startup, the sidecar programmatically called the AWS SQS API to create a unique, ephemeral queue and subscribed it to the central regional SNS topic.
  • When a tenant administrator modified user permissions in Jira, TCS published a JSON invalidation message containing the tenant_id to SNS.
  • SNS handled the fanout, cloning the message and pushing it into every single active SQS queue.
  • The sidecars continuously long-polled their dedicated SQS queues, received the message, and evicted the corresponding keys from their local Caffeine cache.

The Mathematics of the O(N) Amplification Storm

While elegant on paper, the mathematical reality of $O(N)$ fanout broke the architecture under production load:

$$\text{Message Operations/sec} = \text{Write Rate} \times N_{\text{nodes}}$$

Atlassian's production fleet comprised approximately $10,800$ compute nodes. During business hours, tenant metadata mutations occurred at an average of $100\text{ writes/sec}$.

$$\text{Throughput} = 100 \times 10,800 = 1,080,000\ \text{SQS operations / second}$$

Every single write caused over one million message deliveries per second across AWS infrastructure!

4. The Breaking Point: The 3 Failure Modes of SQS Fanout

As the fleet grew, three critical operational bottlenecks manifested:

⚠️ The 3 Crippling Failures of SQS Push
  1. Explosive AWS Infrastructure Costs: AWS SQS billing is metered per API request (SendMessage, ReceiveMessage, DeleteMessage). At over 1 million operations per second, monthly AWS billing surged by hundreds of thousands of dollars purely to discard cache keys that many nodes had not even loaded into RAM!
  2. Ephemeral Queue Sprawl in Kubernetes: In modern containerized environments, pods constantly autoscale, roll out deployments, and terminate. When nodes crashed or pods rescheduled without clean graceful shutdowns, orphaned SQS queues remained active, accumulating messages and eventually hitting hard AWS account-level SQS limits.
  3. Consumer Queue Lag & Split-Brain Stale Reads: If a subset of nodes experienced JVM Stop-The-World GC pauses or CPU throttling, their sidecars fell behind on SQS polling. Stale permission descriptors persisted on lagging nodes, leading to inconsistent security states where a revoked user was blocked on Node A but allowed on Node B.

5. The Migration: The Bespoke S3 Pull/Polling Architecture

To eliminate the $O(N)$ fanout crisis, Atlassian made a radical architectural pivot: stop pushing individual messages to nodes; let nodes pull batched changelogs from scalable object storage (Amazon S3).

Batching & Micro-Changelogs

Instead of dispatching discrete notifications immediately, TCS introduced an in-memory Batch Aggregator:

  • Mutations occurring within a short time window (e.g., $1\text{ second}$) are buffered in memory.
  • Duplicate invalidations for the same tenant are deduplicated into a single entry.
  • The aggregator serializes the batch into a compressed JSON changelog object and writes it to S3 using an incrementing timestamp epoch: s3://tcs-invalidation-prod/changelogs/2026/10/18/epoch_1710000001.json.gz
  • Writing 1 file per second represents exactly 86,400 S3 PUT operations per day — costing fractions of a cent.

S3 HTTP Caching & Cost Collapse

Amazon S3 natively handles thousands of concurrent read requests per second per prefix. Sidecars execute a periodic HTTP request every second:

  • Sidecars send an HTTP HEAD or GET request using the If-Modified-Since or If-None-Match header with their local epoch tracker.
  • If no new changelog has been published, S3 returns a lightweight 304 Not Modified with zero payload transfer.
  • When a new epoch appears, sidecars fetch the tiny compressed file, inspect the list of modified tenant_id keys, and invalidate only those entries from their local Caffeine cache.
  • Total AWS messaging infrastructure cost dropped by over 90% immediately upon deployment.

6. Python Simulation: S3 Invalidation Pipeline

The following production simulation demonstrates the core architecture of the TCS Batch Aggregator and the Client Sidecar Poller:

atlassian_cache_invalidation.py 
import time
import json
import gzip
from typing import Set, Dict, Any, List

class S3MockStorage:
    """Simulates Amazon S3 with epoch-versioned immutable changelog objects."""
    def __init__(self):
        self.objects: Dict[str, bytes] = {}
        self.latest_epoch: int = 0

    def put_changelog(self, epoch: int, keys: Set[str]) -> str:
        payload = json.dumps({"epoch": epoch, "invalidated_keys": list(keys)}).encode("utf-8")
        compressed = gzip.compress(payload)
        key_path = f"tcs/changelogs/epoch_{epoch}.json.gz"
        self.objects[key_path] = compressed
        self.latest_epoch = epoch
        return key_path

    def get_latest_epoch(self) -> int:
        return self.latest_epoch

    def get_changelog(self, epoch: int) -> List[str]:
        key_path = f"tcs/changelogs/epoch_{epoch}.json.gz"
        if key_path not in self.objects:
            return []
        raw = gzip.decompress(self.objects[key_path])
        data = json.loads(raw.decode("utf-8"))
        return data.get("invalidated_keys", [])


class TCSBatchAggregator:
    """Gathers discrete mutations and flushes batched epoch manifests to S3."""
    def __init__(self, s3: S3MockStorage, flush_interval_sec: float = 1.0):
        self.s3 = s3
        self.flush_interval = flush_interval_sec
        self.pending_keys: Set[str] = set()
        self.last_flush = time.time()
        self.current_epoch = int(time.time())

    def record_mutation(self, tenant_id: str):
        """Called when a tenant configuration changes in Jira/Confluence."""
        self.pending_keys.add(tenant_id)

    def maybe_flush(self) -> bool:
        now = time.time()
        if now - self.last_flush >= self.flush_interval and self.pending_keys:
            self.current_epoch += 1
            flushed_count = len(self.pending_keys)
            path = self.s3.put_changelog(self.current_epoch, self.pending_keys)
            print(f"[TCS Aggregator] Epoch {self.current_epoch}: Flushed {flushed_count} invalidations -> {path}")
            self.pending_keys.clear()
            self.last_flush = now
            return True
        return False


class NodeLocalCacheSidecar:
    """Sidecar running alongside each compute instance managing L1 Caffeine cache."""
    def __init__(self, node_id: str, s3: S3MockStorage):
        self.node_id = node_id
        self.s3 = s3
        self.local_cache: Dict[str, str] = {}
        self.last_applied_epoch: int = s3.get_latest_epoch()

    def set_local(self, key: str, value: str):
        self.local_cache[key] = value

    def get_local(self, key: str) -> str:
        return self.local_cache.get(key, None)

    def poll_and_sync(self):
        """Executed periodically (e.g., every 1s) by the background daemon."""
        latest_available = self.s3.get_latest_epoch()
        if latest_available <= self.last_applied_epoch:
            return  # HTTP 304 Not Modified equivalent: Zero work

        # Replay all missed epochs up to the latest
        for epoch in range(self.last_applied_epoch + 1, latest_available + 1):
            keys_to_evict = self.s3.get_changelog(epoch)
            for k in keys_to_evict:
                if k in self.local_cache:
                    del self.local_cache[k]
                    print(f"[{self.node_id}] EVICTED stale key '{k}' from L1 cache (Epoch {epoch})")

        self.last_applied_epoch = latest_available


# Demonstration
if __name__ == "__main__":
    s3 = S3MockStorage()
    aggregator = TCSBatchAggregator(s3, flush_interval_sec=0.1)

    # 2 Compute Node Sidecars
    node_a = NodeLocalCacheSidecar("Node-Jira-1", s3)
    node_b = NodeLocalCacheSidecar("Node-Confluence-2", s3)

    # Seed L1 caches
    node_a.set_local("tenant:alpha", "v1_permissions")
    node_b.set_local("tenant:alpha", "v1_permissions")
    node_b.set_local("tenant:beta", "v1_permissions")

    # Invalidation events trigger in core TCS
    aggregator.record_mutation("tenant:alpha")
    aggregator.record_mutation("tenant:gamma")
    time.sleep(0.15)
    aggregator.maybe_flush()

    # Sidecars poll on timer
    node_a.poll_and_sync()
    node_b.poll_and_sync()

    print(f"Node A 'tenant:alpha' exists: {node_a.get_local('tenant:alpha') is not None}")
    print(f"Node B 'tenant:beta' exists:  {node_b.get_local('tenant:beta') is not None}")

7. Architectural Lessons & Key Engineering Takeaways

💡 Core Systems Engineering Maxims
  1. The Push vs. Pull Trade-Off: Push messaging (SNS + SQS) achieves sub-100ms latency but scales at $O(N)$ with respect to consumers. When consumer fleets reach $10^4$ instances, push architectures collapse under API fees and queue sprawl. Pull/polling architectures bound scale cleanly.
  2. Challenge Latency Assumptions: Engineers often reflexively design for zero-latency cache consistency. In practice, tenant permissions and administrative setting changes easily tolerate a $1\text{ to }2\text{ second}$ propagation window. Trading sub-second invalidation for a $1\text{s}$ polling lag enabled a $90\%$ reduction in system complexity and cost.
  3. Stateless Resilience via Object Storage: S3 has no message queues to deadlock, no head-of-line blocking, and no consumer group rebalances. If a compute pod restarts after hours of downtime, it simply reads the latest monotonic epoch and synchronizes its state instantly.
