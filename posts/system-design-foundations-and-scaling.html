📌 System Design Core Foundations

Extracted from 180+ pages of comprehensive engineering notes, this foundational guide breaks down the core building blocks required to architect resilient, web-scale platforms. We cover the systematic framework for tackling system design challenges, Relational vs NoSQL trade-offs, Database Scaling strategies (Replication, Sharding, Federation), Caching architectures, Layer 4/7 Load Balancing, Circuit Breakers, and Consistent Hashing.

1. What is System Design?

System Design is the art and science of defining the architecture, modules, interfaces, and data flow for a system to satisfy specified operational requirements. Rather than simply writing code, system design decides:

  • How components interact with one another across the network.
  • How the system behaves under 100x traffic spikes or partial infrastructure failure.
  • The intentional trade-offs between latency, consistency, availability, and engineering complexity.

2. How to Approach System Design Problems

When approaching any system design problem (in production or during high-stakes technical interviews), follow this structured 5-step framework:

  1. Understand the Scope & Requirements:
    • Functional Requirements: What does the user actually do? (e.g. Post a tweet, search by hashtag, view timeline).
    • Non-Functional Requirements: Scale (DAU/MAU), Latency SLA (P99 < 100ms), High Availability (99.99%), Consistency model (Strong vs Eventual).
  2. Back-of-the-Envelope Capacity Estimations: Calculate QPS (Queries per Second), Storage volume per year, Network Bandwidth, and RAM cache size (Pareto 80/20 rule).
  3. High-Level Architecture: Draw the core components (Clients, API Gateway, Services, Primary DB, Cache, Message Queues).
  4. Deep Dive into Core Bottlenecks: Sharding strategies, data schemas, concurrency race conditions, failure recovery.
  5. Resiliency & Edge Cases: Single points of failure, rate limiting, circuit breaking, backup and failover.

3. Relational Databases vs NoSQL: Picking the Right Store

Database Category Primary Characteristics Best Use Cases Popular Examples
Relational (RDBMS) Structured tabular schema, ACID guarantees, SQL joins, foreign key integrity. Financial transactions, user billing, checkout, core order management. PostgreSQL, MySQL, CockroachDB
Document Store Semi-structured JSON/BSON documents, schema flexibility, nested hierarchies. User profiles, product catalogs, content management. MongoDB, Amazon DocumentDB
Key-Value Store Extremely fast $O(1)$ reads/writes by key; simple API (GET, PUT, DEL). Session storage, caching, user shopping carts. Redis, Memcached, DynamoDB
Wide-Column Column families, high write throughput, distributed across thousands of nodes. Time-series metrics, IoT telemetry, high-volume event logs. Apache Cassandra, ScyllaDB, HBase
Graph Database Nodes and relationships (edges) as first-class citizens, fast graph traversals. Social network follower graphs, recommendation engines, fraud rings. Neo4j, Amazon Neptune

4. Database Scaling Techniques

4.1 Vertical Scaling (Scale-Up)

Upgrading CPU, RAM, and NVMe SSDs on a single machine. Simple (zero architectural changes), but has a hard physical ceiling and exponential hardware cost.

4.2 Master-Slave Replication (Read Scaling)

Writes go to a single Primary (Master) database, which asynchronously or semi-synchronously streams replication logs to multiple Read Replicas (Slaves). Slaves serve read traffic. Enables 10x read scaling, but introduces Replication Lag (users may read stale data immediately after writing).

4.3 Sharding / Horizontal Partitioning

When dataset size exceeds a single disk or write QPS overwhelms one node, data is divided across multiple independent database instances (shards):

Figure 10: Range / Hash-based database sharding architecture.
  • Range-Based Sharding: Partitioning by key ranges (e.g. User IDs 1-100K on Shard 1). Can lead to hotspotting if new sequential IDs overwhelm the latest shard.
  • Hash-Based Sharding: Applying a hash function ($\text{hash}(\text{key}) \pmod N$) to distribute data uniformly across $N$ shards.
  • Sharding Challenges: Cross-shard joins are virtually impossible; distributed transactions across shards require SAGAs; repartitioning when adding shards is complex.

5. Caching Strategies & Eviction Policies

Caching intercepts requests before they hit the database, storing hot items in RAM:

  • Cache-Aside (Lazy Loading): App reads cache. On miss, app queries DB, stores in cache, and returns. Cache only holds what is requested.
  • Write-Through: App writes data to cache, and cache synchronously writes to DB before acknowledging. Strong consistency, higher write latency.
  • Write-Behind (Write-Back): App writes to cache immediately; cache asynchronously writes batches to the DB in the background. High write speed, risk of data loss if cache crashes before sync.
  • Refresh-Ahead: Cache automatically re-fetches items from DB before expiration based on predicted access patterns.

6. Load Balancers & Proxies

Load Balancers distribute incoming traffic across application server pools to ensure high availability and responsiveness:

  • Layer 4 Load Balancing (Transport Layer): Operates at TCP/UDP level without inspecting HTTP headers or cookies. Extremely high packet throughput (millions of packets/sec). Examples: AWS NLB, IPVS.
  • Layer 7 Load Balancing (Application Layer): Inspects HTTP request content (URL path, headers, cookies). Enables path-based routing (e.g. /api/orders $\to$ Order Service, /images $\to$ CDN), TLS termination, and sticky sessions. Examples: NGINX, HAProxy, AWS ALB.
  • Algorithms: Round Robin, Weighted Round Robin, Least Connections, IP Hash.

7. Circuit Breakers & Cascading Failure Prevention

In distributed microservices, if Service C slows down, Service B's worker threads block waiting for responses. Soon, Service B exhausts its thread pool and crashes, causing Service A to crash. This catastrophic domino effect is called a Cascading Failure.

The Circuit Breaker Pattern monitors outbound calls:

stateDiagram-v2
  [*] --> Closed
  Closed --> Open: Failure threshold exceeded (e.g. > 50% errors)
  Open --> HalfOpen: Cooldown timeout expired (e.g. after 30s)
  HalfOpen --> Closed: Trial requests succeed
  HalfOpen --> Open: Trial request fails
Figure 11: Circuit Breaker state machine (Closed, Open, Half-Open).
  • Closed: Normal operation. All requests pass through.
  • Open: When error/timeout threshold is reached, the circuit trips OPEN. Requests fail immediately with a local fallback without touching the degraded dependency!
  • Half-Open: After a cooldown window (e.g. 30 seconds), a limited number of test requests are allowed through. If successful, the circuit resets to CLOSED. If they fail, it trips OPEN again.

8. Consistent Hashing

In naive modulo hashing ($\text{server} = \text{hash}(\text{key}) \pmod N$), adding or removing a single node from $N$ to $N+1$ causes almost 100% of all keys to rehash to different nodes ($\frac{N}{N+1}$ keys moved), completely invalidating caches and triggering massive database stampedes.

🔄 The Consistent Hashing Ring

Consistent Hashing maps both keys and servers to a logical Hash Ring ($[0, 2^{32}-1]$):

  • A key is routed to the first server encountered clockwise on the ring.
  • When a node is added or removed, only $\frac{1}{N}$ fraction of keys are remapped on average!
  • Virtual Nodes (vnodes): To prevent non-uniform distribution and server hotspots, each physical server is mapped to multiple virtual positions on the ring (e.g. 150 vnodes per physical machine).
