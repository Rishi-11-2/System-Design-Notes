Kafka Architecture — Part 2: Consumer Groups, Offsets & HA Replication

📁 Category: Event Streaming & Message Brokers
← Back to All Notes
📌 Architectural Blueprint

While Part 1 established the storage and ingestion foundations of Apache Kafka, Part 2 explores the consumption and high-availability mechanics: how consumers coordinate into logical groups to achieve linear read scalability, how Kafka tracks processing state via the internal __consumer_offsets topic, the exact failure modes of auto vs manual commit strategies, and how cluster-wide Leader-Follower replication provides zero-data-loss durability.

1. Consumers & Consumer Group Scaling Invariants

In distributed message processing, a system must satisfy two seemingly contradictory requirements:

  1. Horizontal Read Scalability: Multiple instances of a worker service must pool their compute power to process a high-velocity stream in parallel.
  2. Strict Entity Ordering: Concurrent processing must never cause race conditions or out-of-order execution for records belonging to the same entity.

Apache Kafka solves this dual requirement through the Consumer Group abstraction.

The Consumer Group Concept

A Consumer Group is an elastic, logical collection of one or more consumer application instances that collaborate to consume events from a set of subscribed topics. Each group identifies itself using a unique string, the group.id (e.g., "notification-workers", "fraud-detection-engine", "data-warehouse-syncer").

The Two Cardinal Rules of Kafka Consumer Groups

Every Kafka consumer group operates under two non-negotiable architectural invariants:

Invariant 1: Exclusivity Within a Group (Load-Balancing Rule)

Different consumers in the same consumer group can only read from different partitions. Multiple consumers in the exact same group can NEVER read from the same partition simultaneously.

Why is this invariant mandatory? If two consumer threads in the same group read concurrently from Partition 0, they would receive interleaved messages. If Consumer 1 processes Offset 10 while Consumer 2 processes Offset 11, Consumer 2 could complete and commit before Consumer 1, completely breaking the partition's strict sequential order guarantee. By enforcing that exactly one consumer instance within a group is assigned to any given partition, Kafka guarantees race-free sequential processing within that partition.

Invariant 2: Independence Across Groups (Pub/Sub Broadcast Rule)

Consumers in different consumer groups read from the same partition completely independently.

Each consumer group maintains its own independent reading cursor. A record published to Partition 0 is delivered to Consumer A1 (in Group A) and also delivered to Consumer B1 (in Group B). Neither group impacts the consumption rate, latency, or committed offset of the other. Kafka seamlessly provides point-to-point queuing behavior within a group and publish-subscribe broadcasting across groups.

The Concurrency Ceiling Theorem

Because no two consumers in the same group can read from the same partition, the maximum degree of read parallelism for any consumer group is strictly bounded by the number of partitions in the topic:

$$\text{Max Active Consumers per Group} = \text{Total Partitions in Subscribed Topic}$$
Topic Partitions ($N$) Consumer Group Size ($C$) Allocation Topology Operational State
$N = 4$ $C = 2$ Each consumer instance is assigned 2 partitions ($4 / 2 = 2$). Balanced utilization; high worker throughput.
$N = 4$ $C = 4$ Each consumer instance is assigned exactly 1 partition. Maximum concurrency and optimal parallelism.
$N = 4$ $C = 6$ 4 consumers each read 1 partition; 2 consumers remain idle. Idle instances act as hot standbys; they consume zero events until a rebalance occurs.

If your consumer service is falling behind and you scale its Kubernetes deployment from 4 pods to 12 pods, but your topic only has 4 partitions, the 8 new pods will sit completely idle. To increase consumption concurrency, you must provision more topic partitions.

2. Offset Tracking & The __consumer_offsets Internal Topic

How does a consumer group know where to resume reading when an instance crashes, restarts, or deploys new code? It tracks its progress via committed offsets.

Group-Wise Offset Tracking

Crucially, offsets are stored per consumer group, per partition, rather than per individual worker process. If Worker Pod 3 crashes while reading Partition 2, Kubernetes restarts the pod or Kafka rebalances Partition 2 to Worker Pod 1. The newly assigned worker queries the cluster: "What is the latest committed offset for Group A on Partition 2?" and immediately resumes processing from that exact position.

The __consumer_offsets Internal Topic

In early versions of Kafka (pre-0.9), consumer offsets were stored in Apache ZooKeeper. However, writing high-frequency offset updates from thousands of consumers to ZooKeeper's consensus tree overwhelmed ZooKeeper's write pipeline, creating a severe cluster-wide scalability bottleneck.

Modern Kafka stores all consumer offset commits directly inside a specialized internal Kafka topic named __consumer_offsets:

  • By default, __consumer_offsets has 50 partitions (configured via offsets.topic.num.partitions = 50).
  • It is configured with a replication factor of 3 (offsets.topic.replication.factor = 3) to guarantee high durability.
  • It uses Log Compaction (cleanup.policy=compact). Because an application only cares about the latest committed offset for a partition, Kafka's background cleaner thread periodically purges older offset records with duplicate keys, retaining only the most recent offset value.
Record Component Field Name Description
Message Key [Group ID, Topic Name, Partition ID] Composite key identifying the exact stream coordinate. Example: ["order-processor", "orders", 2].
Message Value [Committed Offset, Metadata, Timestamp] The 64-bit committed offset integer (e.g., 104859), custom client metadata string, and epoch commit timestamp.

Offset Partition Routing & The Group Coordinator

With 50 partitions in __consumer_offsets, how does a consumer know which partition stores its offset, and which broker manages its group?

Kafka hashes the string group.id and computes the modulo over 50:

$$\text{Offsets Partition ID} = \lvert\text{hashCode}(\text{group.id})\rvert \pmod{50}$$

3. Offset Commit Strategies: Auto vs Manual Commit & Failure Modes

When a consumer client fetches a batch of records from a broker via poll(), when and how should it inform Kafka that the records have been processed? This decision dictates the system's fault-tolerance semantics.

1. Auto-Commit Strategy (enable.auto.commit = true)

By default, Kafka consumer clients enable auto-commit. At every periodic interval defined by auto.commit.interval.ms (default: 5,000 ms / 5 seconds), the consumer's background thread automatically commits the highest offset returned by the previous poll() call.

While convenient and zero-code, auto-commit introduces two severe operational failure modes under failure:

⚠️ Failure Mode 1: Data Loss (At-Most-Once Delivery)

Suppose the consumer polls 500 records (offsets 1,000 to 1,499). While the worker thread is slowly executing record 1,050, the 5-second auto-commit timer fires in the background. The consumer library automatically commits offset 1,500 to __consumer_offsets. Immediately thereafter, the JVM crashes or encounters an unhandled OutOfMemoryError.

When a replacement consumer restarts and queries the Group Coordinator, Kafka reports the committed offset as 1,500. Records 1,051 through 1,499 were never processed by any business logic, yet they are permanently skipped. Data is silently lost.

⚠️ Failure Mode 2: Massive Duplicate Processing (At-Least-Once Delivery)

Suppose the consumer polls 500 records (offsets 1,000 to 1,499). The worker thread successfully processes all 500 records and writes side-effects to an external database. However, before the 5-second timer fires, the consumer pod suffers a network partition or hardware failure.

Because the offset was never committed, the replacement consumer boots up, reads the stale committed offset (1,000), and re-executes all 500 records from scratch. If downstream operations (e.g., charging credit cards, sending SMS alerts) are not strictly idempotent, duplicate real-world actions occur.

2. Manual Commit Strategy (Recommended for Production)

To eliminate silent data loss, enterprise production systems disable auto-commit (enable.auto.commit = false) and trigger manual commits only after the application has fully verified and persisted record side-effects.

Manual Commit Method Execution Behavior Throughput vs Safety Trade-Off
commitSync() Blocks the consumer thread synchronously until the broker returns an ACK or retries fail. Highest safety; guarantees no subsequent records are processed until the current batch is acknowledged. Slower throughput due to blocking network round-trip.
commitAsync() Non-blocking; fires an offset commit request over TCP with an optional callback and immediately proceeds to poll next batch. High throughput; avoids blocking the event loop. Does not retry on failure to prevent stale commit overwrites.
Hybrid Batch Commit Pattern Use commitAsync() inside the high-throughput processing loop, wrapped in a finally block that executes commitSync() on shutdown. Industry Best Practice: Combines wire-speed asynchronous execution with deterministic synchronous guarantees on consumer teardown or rebalance.

Production Manual Commit Implementation

Properties props = new Properties();
props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "broker1:9092,broker2:9092");
props.put(ConsumerConfig.GROUP_ID_CONFIG, "payment-audit-service");
// 1. Disable auto-commit to prevent premature offset progression
props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, "false");
props.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG, "earliest");

KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props);
consumer.subscribe(Collections.singletonList("customer.payments"));

try {
    while (running) {
        ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
        
        for (ConsumerRecord<String, String> record : records) {
            // Process record business logic (e.g. database insertion)
            processPaymentRecord(record);
        }
        
        // 2. Commit synchronously only AFTER all records in batch are persisted
        consumer.commitSync();
    }
} catch (CommitFailedException e) {
    logger.error("Offset commit rejected due to consumer rebalance", e);
} finally {
    try {
        consumer.commitSync(); // Final clean commit
    } finally {
        consumer.close();
    }
}

4. Cluster Architecture & High Availability Invariants

A Kafka cluster is a decentralized collection of brokers operating cooperatively. The cluster guarantees that the failure of any individual broker, rack, or availability zone will not cause data loss or cluster downtime.

The Replication Factor Invariant

High availability is governed by the Replication Factor ($R$) configured per topic:

  • A replication factor of $R = 1$ means exactly one copy of each partition exists. If the hosting broker crashes, that partition becomes immediately unavailable.
  • A replication factor of $R = 2$ means 1 Leader and 1 Follower replica.
  • A replication factor of $R = 3$ (the standard enterprise baseline) means 1 Leader and 2 Follower replicas distributed across three distinct physical brokers.
The Physical Broker Constraint

A topic's replication factor can NEVER exceed the total number of active brokers in the cluster ($R \le B$). Kafka will refuse to place two replicas of the same partition on the same physical broker node, as that would eliminate fault isolation.

5. Leader-Follower Replication & In-Sync Replicas (ISR)

For every partition in the cluster, one broker is elected as the Leader, while the remaining replica brokers act as Followers.

Leader vs Follower Responsibilities

Role Client Traffic Responsibilities Internal Operational Duties
Leader Handles 100% of read and write requests from producers and consumers for that partition. Maintains the active log segments, assigns monotonically increasing offsets, monitors follower fetch lag, and manages the High Watermark.
Follower Never serves external clients (acts purely as a passive backup replica in standard Kafka architectures). Continuously sends internal FetchRequest RPCs to the Leader (acting identical to a consumer), appends received record bytes to its local disk log, and reports its latest offset to the Leader.

Symmetric Multi-Role Broker Distribution

Crucially, Kafka does not designate dedicated "leader servers" and "slave servers." Instead, leadership is distributed evenly at the partition level across all cluster brokers.

Physical Broker Topic "Orders" Role Topic "Payments" Role Topic "Inventory" Role
Broker 101 Leader: Partition 0 Follower: Partition 1 Follower: Partition 0
Broker 102 Follower: Partition 0 Leader: Partition 0 Follower: Partition 1
Broker 103 Follower: Partition 1 Follower: Partition 0 Leader: Partition 0

Every broker serves as the Leader for some partitions and simultaneously serves as the Follower for others. This symmetric design distributes CPU, network socket I/O, and disk load uniformly across the hardware fleet.

The In-Sync Replicas (ISR) Set & High Watermark Mechanics

How does the cluster know which followers are eligible to take over if the Leader crashes?

The Leader tracks a dynamic set of replicas called the ISR (In-Sync Replicas):

  • A Follower is considered "in-sync" if it has fetched and caught up with the Leader's log within the threshold defined by replica.lag.time.max.ms (default: 30,000 ms / 30 seconds).
  • If a Follower network-stalls, suffers garbage collection pauses, or falls behind, the Leader automatically evicts it from the ISR set.
  • Log End Offset (LEO): The offset of the next record to be written in a replica's log.
  • High Watermark (HW): The highest offset that has been successfully replicated across all members of the ISR set.
The Consumer Read Boundary

Consumers are only permitted to read records up to the High Watermark (HW). Even if the Leader has written records up to LEO 105 in its local log, if followers have only replicated up to LEO 102, the HW remains 102. Records between 103 and 105 are invisible to consumers until replicated. This prevents dirty reads in the event that the Leader crashes and an un-replicated record is lost.

Automatic Leader Election & Failover

When Broker 101 (hosting the Leader of Partition 0) crashes:

  1. The Kafka cluster controller (KRaft / ZooKeeper) detects heartbeat timeout.
  2. The controller selects an active member from the partition's ISR set (e.g., Broker 102) and promotes it to become the new Leader.
  3. The controller broadcasts updated cluster metadata to all brokers and connected clients.
  4. Producers and consumers instantly reconnect their sockets to Broker 102 and resume I/O with zero data loss because Broker 102 was fully caught up to the High Watermark.

6. Group Coordination & Consumer Rebalancing Mechanics

When consumer instances join, leave, or crash, Kafka triggers a Consumer Rebalance to reassign partitions among active group members.

Rebalance Trigger Conditions

A rebalance is initiated whenever group topology changes:

  • Instance Join: A new consumer pod boots up and calls subscribe().
  • Instance Clean Shutdown: A consumer executes consumer.close(), sending a LeaveGroupRequest to the coordinator.
  • Heartbeat Timeout (Crash): The consumer fails to send a heartbeat within session.timeout.ms (default: 45 seconds).
  • Processing Stall: The consumer takes longer than max.poll.interval.ms (default: 5 minutes) to process a batch and invoke the next poll() call. The coordinator assumes the consumer thread is deadlocked and forcibly ejects it.
  • Topic Expansion: A cluster administrator adds partitions to the subscribed topic.

Eager vs Cooperative Sticky Rebalancing

  • Legacy Eager Rebalance (Stop-the-World): In early Kafka clients, a rebalance required all consumers to give up all assigned partitions, halt processing entirely, rejoin the group, and wait for re-assignment. In high-partition topics, this caused 10- to 30-second processing freezes across the entire service fleet.
  • Modern Cooperative Sticky Rebalancing (Kafka 2.4+): Uses the CooperativeStickyAssignor. Consumers do not revoke all partitions. Instead, consumers continue reading unaffected partitions while only the specific migrating partitions are safely revoked and reassigned over two lightweight rebalance phases. This eliminates processing freezes in modern microservice deployments.

7. Architectural Summary & Production Best Practices

Architecture Invariant System Mechanism Production Engineering Rule
Exclusive Read Invariant One consumer per partition within a group. To scale consumer throughput, you must increase topic partition count ($C \le N$).
State Tracking Compacted __consumer_offsets topic. Coordinator broker is derived via $\text{hash}(\text{GroupID}) \pmod{50}$.
Offset Commits Manual commit (commitSync / commitAsync). Always set enable.auto.commit = false for critical business transactions to prevent silent data loss.
Replication HA Leader handles client traffic; Followers fetch passively. Set replication.factor = 3 and min.insync.replicas = 2 with producer acks = all for zero-loss durability.
High Watermark Max offset acknowledged by all ISR members. Guarantees that consumers never read uncommitted or potentially lossy leader records.
Rebalancing CooperativeStickyAssignor protocol. Tune max.poll.interval.ms higher than your slowest external API call to avoid cascading group rebalances.
