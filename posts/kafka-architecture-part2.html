📌 Consumer Groups & Cluster Reliability

Part 2 of the Kafka Architecture series explores how consumers cooperate to process vast volumes of data. We analyze Consumer Groups, partition reassignment semantics, offset commit management via __consumer_offsets, delivery semantics (At-Least-Once vs Exactly-Once), In-Sync Replicas (ISR), and broker leader election.

1. Consumers and Consumer Groups

A Consumer Group is a logical collection of consumers collaborating to ingest and process records from a set of topics. Consumer Groups allow Kafka to seamlessly unite queueing and publish-subscribe models:

📏 The Two Fundamental Partition Rules
  • Rule 1 (Within a Single Group): Each partition can be assigned to at most one consumer instance in that group. Two consumers in the same group can never read from the same partition concurrently! If you have 4 partitions and 6 consumers in a group, 2 consumers will remain completely idle.
  • Rule 2 (Across Different Groups): Multiple consumer groups operate completely independently. A consumer in Group 1 and a consumer in Group 2 can read the same partition simultaneously without interfering with each other's progress.

2. Offset Management (__consumer_offsets)

How does Kafka know where a consumer left off if it restarts? Every consumer periodically commits its current offset position.

In early Kafka versions, offsets were stored in ZooKeeper. Modern Kafka stores committed offsets in an internal, high-throughput, compacted Kafka topic named __consumer_offsets. When a consumer fails, the new assigned consumer simply reads the latest committed offset from __consumer_offsets and resumes processing without skipping records.

3. Offset Commit Strategies & Delivery Semantics

The timing of when an offset is committed determines the delivery semantics of your application:

Strategy Configuration / Mechanism Pros & Cons Delivery Guarantee
Automatic Commit enable.auto.commit = true (commits periodically, e.g. every 5s) Simple; risk of data loss if process crashes after commit but before processing finishes At-Most-Once / At-Least-Once
Manual Sync Commit commitSync() (commits after batch finishes) Safe; blocks consumer thread until broker confirms commit, slight throughput penalty At-Least-Once
Manual Async Commit commitAsync() High throughput; non-blocking, but requires careful error callback handling At-Least-Once
Transactional Processing Kafka Transactions API (initTransactions, sendOffsetsToTransaction) Atomic write of output events + consumed offsets across Kafka topics Exactly-Once Processing (EOS)

4. Kafka Cluster & High Availability

A production Kafka cluster consists of multiple brokers to provide scalability, load balancing, and fault tolerance:

  • Replication Factor: Topics configure a replication factor (typically 3 in production). For each partition, 1 broker is designated as the Leader and the remaining 2 are Followers.
  • Leader Partitions: Handle 100% of incoming produce and consume requests (ensuring total linear order).
  • Follower Partitions: Never serve client writes. They continuously fetch log records from the leader to stay synchronized.

5. In-Sync Replicas (ISR) and Leader Election

Followers that are actively keeping up with the leader partition's latest records are categorized in the In-Sync Replicas (ISR) pool:

  • If a follower node experiences high network latency or hardware failure and falls behind the leader (configurable via replica.lag.time.max.ms), the broker is evicted from the ISR pool.
  • Producer Durability (acks):
    • acks=0: Fire-and-forget; producer does not wait for any broker ack (fastest, lowest durability).
    • acks=1: Leader writes locally to disk and acks immediately without waiting for followers.
    • acks=all (or acks=-1): Leader waits until all replicas in the ISR confirm persisting the write. Combined with min.insync.replicas=2, this prevents data loss even if the leader immediately crashes!
  • Leader Election: When a leader broker crashes, the cluster controller selects a replacement leader exclusively from the healthy ISR pool.
