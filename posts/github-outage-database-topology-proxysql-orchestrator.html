Managing Production Databases at Scale: ProxySQL, Orchestrator & Anti-Flapping

How hyperscale architectures manage hundreds of sharded MySQL clusters: L7 multiplexing, automated topology repair, and the engineering of anti-flapping dampeners.

25 min read Arpit Bhayani Outage Dissections Verified 3-Page Companion PDF
📥 Download Technical PDF (3 Pages)
📌 Production Operations Executive Takeaway

Running relational databases at the scale of GitHub, Shopify, or Slack requires decoupling client applications from direct database hostnames. Operating hundreds of MySQL clusters requires a cooperative two-tier infrastructure: ProxySQL sits at Layer 7 to multiplex connections, route reads/writes, and buffer transient stalls, while GitHub Orchestrator operates as the automated control plane, monitoring replication topology, detecting host crashes, and executing sub-second promotions. However, during network instability, automated failover can devolve into topology flapping—repeatedly electing and deposing masters. Preventing this requires robust Anti-Flapping Dampening Mechanisms.

1. The Two-Tier Architecture: ProxySQL & Orchestrator

Direct application-to-database connections fail at scale. If 5,000 Rails Puma workers each open a connection to MySQL, the server spends more CPU cycles managing OS context switches and thread locks than executing SQL. The production architecture decouples these tiers:

2. ProxySQL: L7 Connection Multiplexing & Query Rules

ProxySQL intercepts all database communication, acting as an intelligent protocol-aware proxy:

  • Connection Multiplexing: ProxySQL maps 10,000 client frontend connections to just 50–100 persistent backend connections, keeping MySQL within its optimal performance sweet spot.
  • Query Rule Splitting: Using regex query matching, ProxySQL automatically routes read-only queries to replicas while funneling writes to the master: 
    -- ProxySQL Query Routing Rule Definition
INSERT INTO mysql_query_rules (rule_id, active, match_pattern, destination_dataset)
VALUES (1, 1, '^SELECT.*FOR UPDATE', 10); -- Route to Master Hostgroup (10)

INSERT INTO mysql_query_rules (rule_id, active, match_pattern, destination_dataset)
VALUES (2, 1, '^SELECT', 20);            -- Route to Replica Hostgroup (20)
  • Transparent Failover Rewiring: When a failover occurs, ProxySQL pauses client queries in-flight for 200–500ms, swaps the backend master IP, and resumes execution without the application ever seeing an exception.

3. GitHub Orchestrator: Automated Crash Recovery

GitHub created and open-sourced Orchestrator to manage the physical lifecycle of MySQL topologies. Orchestrator continuously discovers cluster relationships via SHOW SLAVE HOSTS and SHOW SLAVE STATUS:

  1. Detection: If a master dies, Orchestrator gathers evidence across multiple probe agents to verify the master is truly dead (preventing false alarms on single probe network drops).
  2. Candidate Selection: Evaluates all replicas and identifies the replica with the most advanced GTID (Global Transaction Identifier) coordinates.
  3. Promotion: Stops replication on the chosen replica, promotes it to read-write mode, and repoints sibling replicas using GTID auto-positioning.
  4. Proxy Notification: Calls ProxySQL APIs or Consul/etcd key-value pairs to immediately update the active write target.

4. The Threat of Topology Flapping

Automated failover is dangerous when a server is not cleanly dead, but flapping (periodically disconnecting and reconnecting due to power supply faults, packet loss, or heavy swap memory thrashing):

⚠️ The Anti-Flapping Nightmare Scenario

Suppose Master A flaps. Orchestrator detects the death and promotes Replica B. 15 seconds later, Master A rejoins and begins accepting residual connections. Then Replica B suffers a blip, causing Orchestrator to promote Replica C. Within 2 minutes, three different nodes have acted as master, binary logs have diverged beyond repair, and replication chains are severed. This is Topology Flapping.

5. Engineering Anti-Flapping Dampeners

To eliminate topology churn, Orchestrator enforces strict algorithmic dampeners:

1. Recovery Cooldown (RecoveryGracePeriod):
   └── Once a failover is executed on cluster X, automated failover is BLOCKED
       for cluster X for the next 10 minutes (configurable).
   └── If another failure occurs within the cooldown, Orchestrator REFUSES to act
       and raises a PagerDuty alert for human intervention.

2. Anti-Flapping Master Acknowledgments:
   └── A deposed master is forcefully fenced (read-only mode set, MySQL port blocked via iptables).
   └── A returning ex-master is automatically demoted to a read-only follower; it is NEVER
       allowed to re-assume master status automatically.

3. Failure Dampening via Multi-Probe Consensus:
   └── Failover requires corroboration: at least 3 independent Orchestrator nodes
       across distinct racks must confirm that the master is unreachable.

6. Systems Engineering Takeaways

  1. Decouple Apps from Database Hostnames: Hardcoding database master IPs into application configurations is an antipattern. Use an L7 proxy like ProxySQL or a service mesh to make database endpoints completely dynamic.
  2. Rate Limit Your Automated Recoveries: Automated systems can destroy a cluster faster than any hardware failure if left unbounded. Always configure strict grace periods that halt automated actions if failovers repeat in rapid succession.
  3. GTID is Indispensable for Modern HA: Position-based replication (log file and byte offset) makes automated replica re-pointing brittle and prone to errant transactions. Modern automated failover requires MySQL GTID auto-positioning.
