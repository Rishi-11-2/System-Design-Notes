Storage Engine

Bitcask Explained: A Log-Structured Fast Key/Value Store

📁 Category: Storage Engines
← Back to All Notes
📌 Primary Takeaway

Traditional disk storage engines rely on in-place updates via B-Trees, incurring high write amplification, locking contention, and multi-level disk seeks. Bitcask flips this paradigm by decoupling directory metadata from storage payloads: it marries pure append-only sequential disk writes with an in-memory hash table called KeyDir that indexes the exact byte offsets of active records. This guarantees exactly 1 sequential write per mutation and at most 1 disk seek per read ($O(1)$ random access). Space reclamation is managed through asynchronous background merge compactions that produce lightweight Hint Files, slashing crash recovery and cold-start times from minutes to seconds.

1. The Problem Space: Why B-Trees & Random Writes Fail at Scale

Storage hardware — both traditional mechanical hard disks (HDDs) and solid-state drives (NAND flash SSDs) — exhibits an unavoidable physical invariant: sequential I/O throughput is orders of magnitude faster than random I/O.

  • On HDDs, random writes require mechanical actuator arm movement (seek time) and platter spin (rotational latency), capping throughput around $100\text{--}200\ \text{IOPS}$.
  • On SSDs, random updates trigger block erase cycles, heavy garbage collection, and write amplification that deteriorates flash endurance.
⚠️ Classical B-Tree Bottlenecks
  • In-Place Page Modification: B-Trees update $4\text{ KB}$ or $16\text{ KB}$ pages in-place. Modifying a 10-byte column forces an entire block to be rewritten.
  • Double-Buffering & WAL: To survive mid-write crashes, engines must write changes twice: first to the sequential Write-Ahead Log (WAL), then to the dirty page buffer, and finally flushed out to the tablespace.
  • Concurrency Latches: Modifying nodes in a tree requires coarse- or fine-grained read/write latches, creating heavy lock contention on root and internal branches under write-heavy loads.
  • Protracted Crash Recovery: After an unclean shutdown, the engine must replay large WAL files from the last checkpoint, freezing database startup.

Bitcask Core Design Objectives

Engineered by Justin Sheehy and David Smith at Basho for Riak (and subsequently adopted in high-throughput production at companies like Uber), Bitcask targeted a strict set of systems constraints:

  1. Ultra-Low Read Latency: Predictable, sub-millisecond p99 latency requiring at most one disk seek per read.
  2. Maximized Write Throughput: All write paths must be strictly sequential append operations to disk.
  3. Crash Friendliness: Zero recovery corruption; interrupted partial writes are safely discarded without replaying WALs.
  4. Single-Process Lockless Writer: A single process coordinates disk appends, eliminating thread synchronization and distributed locks.

2. Storage Engine Architecture Comparison

How does Bitcask compare against modern alternative storage paradigms?

Storage Engine Write Path Mechanics Read Path Mechanics Primary Architectural Trade-off
Bitcask Direct sequential append to active log; in-memory KeyDir updated. $O(1)$ in-memory hash lookup $\to$ at most 1 direct disk seek. RAM Bound: All keys must permanently fit in memory. Range queries unsupported.
LSM-Tree (RocksDB, LevelDB) Sequential append to WAL + in-memory MemTable; background tiered SSTable compactions. MemTable $\to$ Bloom filters $\to$ multiple SSTable levels. Higher read amplification (multiple file reads); write stalls during heavy compactions.
B+ Tree (InnoDB, PostgreSQL) Random write to memory buffer pool + sequential append to WAL; periodic dirty flushes. Tree traversal (root to leaf); page hits cache or seeks disk block. Heavy write amplification; page splits and expensive random dirty page flushing.

3. The Dual-Plane Architecture: Append Log & In-Memory KeyDir

A Bitcask instance operates over a dedicated directory containing multiple segmented files. At any point in time, exactly one file is the Active File (open for writing). All past files are marked Immutable (opened read-only for concurrent reads).

On-Disk Record Layout

Every write appends a contiguous binary entry formatted with a fixed 16-byte header followed by variable-length key and value bytes:

Field Size Description
crc 4 Bytes IEEE 802.3 CRC32 checksum computed over the rest of the record for corruption detection.
tstamp 4 Bytes 32-bit Unix timestamp representing mutation time (used for conflict resolution during merges).
ksz 4 Bytes Unsigned integer denoting the byte length of the key.
value_sz 4 Bytes Unsigned integer denoting the byte length of the value payload.
key $K$ Bytes Raw binary key bytes ($1 \le K \le 2^{32}-1$).
value $V$ Bytes Raw binary value bytes ($0 \le V \le 2^{32}-1$).

KeyDir Hash Entry Anatomy

The in-memory KeyDir structure is a hash map whose entries are lightweight metadata pointers:

KeyDir[key] = {
    file_id:   uint32,   // Which segmented data file holds this entry
    value_pos: uint64,   // Absolute byte offset where record starts in file
    value_sz:  uint32,   // Length of value bytes to read
    tstamp:    uint32    // Mutation timestamp
}

Because values are never stored in KeyDir, memory consumption scales solely with the number of unique keys and their lengths, not the size of stored values.

4. Core Execution Workflows: Write, Read, and Delete Paths

1. The Write Path: Put(K, V)

  1. The active writer serializes the record: computes CRC32, packs the 16-byte header, and appends the key and value.
  2. The bytes are written to the end of the Active File via a sequential write() / append() syscall.
  3. The writer notes the byte offset where the record was written.
  4. The writer updates the in-memory KeyDir[K] with {file_id, value_pos, value_sz, tstamp}.
  5. If the active file exceeds a configured threshold (typically $2\text{ GB}$), it is closed and converted to an Immutable Data File, and a new active file is opened.

2. The Read Path: Get(K)

  1. Look up $K$ in the in-memory KeyDir.
  2. If $K$ is not found, return None immediately ($0\text{ disk I/O}$).
  3. If present, extract file_id, value_pos, and value_sz.
  4. Issue a single positional read using pread(fd, buffer, record_size, value_pos) at the designated offset.
  5. Verify the CRC32 checksum over the retrieved bytes. If valid, return the value slice to the client.

3. The Delete Path: Delete(K)

Because files are append-only, Bitcask never removes records on disk in-place. Instead, it appends a record with a special sentinel Tombstone value (or value_sz = 0 with a tombstone flag). Immediately upon appending the tombstone, the key is evicted from KeyDir, rendering it inaccessible to subsequent reads.

5. Background Compaction and the Hint File Innovation

Because overwrites and deletions simply append new records, older versions and tombstones accumulate on disk, causing disk bloat. Bitcask reclaims space through an asynchronous Merge Process:

The Cold Boot Bottleneck

Because KeyDir lives entirely in volatile RAM, restarting the database requires rebuilding the hash table from disk. Without optimization, the engine must sequentially read and parse every gigabyte of raw data across all files. For a 100 GB database, cold-start recovery can take several minutes.

How Hint Files Solve Recovery

During the merge process, Bitcask writes a companion Hint File alongside each compacted data segment. The Hint File contains the exact same record headers and keys, but omits the value payloads entirely:

Hint File Field Size Description
tstamp 4 Bytes Mutation timestamp.
ksz 4 Bytes Key length.
value_sz 4 Bytes Value length in the data file.
value_pos 8 Bytes Absolute byte offset of the record inside the corresponding .data file.
key $K$ Bytes Key bytes.

Upon restart, the engine only reads the compact hint files. Because hint files contain no value blobs, they are tiny (typically $<1\%$ of data file size) and are read sequentially at hardware memory bus speeds, reconstructing KeyDir in seconds.

6. Crash Guarantees & Production Trade-Offs

Engineering Analysis: When to Use (and When to Avoid) Bitcask
  • Crash Resilience: Writes are atomic sequential appends. If an unexpected power loss or kernel panic halts a write midway, the trailing record fails its CRC32 check and is cleanly truncated during bootstrap without affecting prior historical entries.
  • Ideal Workloads:
    • Key-value stores where the entire key set comfortably fits in RAM (e.g. driver coordinates at Uber, active user sessions, API rate-limiting tokens).
    • High-write ingestion systems requiring predictable sub-millisecond p99 latencies without B-Tree lock contention.
  • Disqualifying Constraints:
    • RAM Limit: If key cardinality exceeds physical RAM, Bitcask cannot operate. LSM-Trees (RocksDB) or B+ Trees (InnoDB) must be chosen.
    • Range Scans: Because the append log is ordered chronologically by insertion time rather than lexicographically by key, range queries (e.g., scan("user:001".."user:100")) require scanning the entire disk and are strictly unsupported.
