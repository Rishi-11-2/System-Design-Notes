How OpenAI Handles 800 Million ChatGPT Users on a Single PostgreSQL Primary

By Arpit Bhayani Dissection & OpenAI Engineering • October 2026 • 15 min read

Source Attribution: This deep-dive synthesizes Arpit Bhayani's engineering dissection on OpenAI's database scaling and OpenAI's engineering disclosure, "Scaling PostgreSQL to power 800 million ChatGPT users".

1. Hypergrowth & The Monolith Counter-Narrative

When ChatGPT launched in late 2022, it became the fastest-growing consumer application in internet history, surging to over 800 million active users. During this multi-order-of-magnitude demand explosion, conventional industry wisdom dictated that an infrastructure team must immediately migrate to distributed NewSQL databases (e.g., CockroachDB, Spanner, YugabyteDB) or execute complex horizontal database sharding.

OpenAI chose an audacious counter-narrative: keep the core relational database on a single monolithic PostgreSQL primary instance and scale everything around it through extreme application-layer discipline, connection pooling, and aggressive read-replica fanout.

2. Topology: 1 Primary Writer + 50 Read Replicas

Hosted on Azure Database for PostgreSQL Flexible Server, OpenAI’s relational database topology relies on a strict segregation between transactional state modifications and high-throughput conversational reads:

Structural Dynamics of the Cluster:

  • Single Primary Writer: Handles all relational mutations (user accounts, billing organizations, subscription entitlements, API keys, rate-limit allocations). Running one primary eliminates distributed cross-shard two-phase commit (2PC) coordination.
  • Synchronous Hot Standby: Maintains synchronous replication with an automated failover partner to ensure zero Recovery Point Objective ($RPO = 0$) during hardware faults.
  • 50 Asynchronous Read Replicas: Absorb 95%+ of global read traffic, distributed across availability zones and regional clusters to minimize user latency.

3. PgBouncer & Connection Lifecycle Management

PostgreSQL uses a process-per-connection concurrency model: every client TCP connection spawns a separate OS process, consuming ~10 MB of RAM plus internal buffer caches. If OpenAI allowed tens of thousands of container pods to connect directly to PostgreSQL, the database would crash from memory exhaustion and OS context-switch thrashing.

Transaction-Level Pooling via PgBouncer
OpenAI placed a dedicated cluster of PgBouncer proxies between the application fleet and PostgreSQL, operating in transaction pooling mode:
  • Ephemeral Backend Attachment: A physical database server connection is assigned to a client only for the exact duration of a single database transaction. The instant the transaction issues COMMIT or ROLLBACK, the connection returns to the idle pool.
  • Compression Factor: Tens of thousands of application client connections are multiplexed down into a lean pool of ~300 to 500 active PostgreSQL backend connections, keeping CPU context switches low and cache hit rates high.

4. Read/Write Segregation Architecture

To keep the primary database from melting under 800 million users, the application layer strictly segregates write queries from read queries:

# Application routing decorator for Database Router
class DatabaseRouter:
    @classmethod
    def execute(cls, query, is_write=False, user_id=None):
        if is_write:
            # Direct to Single Primary Writer via PgBouncer Write Pool
            return cls.primary_pool.execute(query)
        else:
            # Distribute across 50 Read Replicas using consistent client hashing
            replica = cls.select_healthy_replica(user_id)
            return replica.execute(query)

Managing Replication Lag:

Because read replicas receive updates via asynchronous WAL streaming, they experience a typical lag of 10–100ms. If a user updates their billing subscription and immediately reads their profile, querying a replica could show stale data (violating Read-Your-Own-Writes Consistency). OpenAI solves this by tracking the user's last mutation timestamp: if an edit occurred within the last 5 seconds, reads for that user are temporarily pinned to the primary.

5. Application-Layer Hardening & Lazy Writes

The primary database survived because OpenAI ruthlessly optimized query patterns in the application codebase:

Eliminating N+1 ORM Joins

Default ORMs often generate massive, unindexed Cartesian product joins. OpenAI banned unindexed ORM queries, replacing them with hand-crafted SQL statements targeting explicit composite indexes.

Lazy & Batched Writes

Non-critical updates (e.g., last_active_at timestamps, usage telemetry) are not written synchronously. They are buffered in memory and flushed in coalesced bulk-upsert batches every 60 seconds.

6. Offloading Write-Heavy Telemetry

OpenAI’s critical architectural rule was: PostgreSQL is only for core relational data that requires strong transactional consistency.

  • Conversation Message Payloads: Long conversation histories and token completions are not stored in PostgreSQL tables. They are directed to horizontally scalable document stores (Azure Cosmos DB) and blob storage.
  • Vector Embeddings: Vector search and RAG embeddings are routed to specialized vector indexes (Qdrant, Milvus), keeping the PostgreSQL buffer pool unpolluted.

7. Real-World SEVs: Cache Storms & Retries

Operating a single primary at this scale exposed critical failure modes during major incidents (SEVs):

Anatomy of the Cascading Outage Loop
  1. The Cache Stampede: An operational glitch in the Redis caching layer caused an eviction of popular tenant metadata. Suddenly, 50,000 requests/sec bypassed the cache and hit the PostgreSQL primary simultaneously.
  2. Connection Queue Saturation: Query latencies spiked from 2ms to 800ms. PgBouncer queues filled up, causing API endpoints to time out.
  3. The Cascading Retry Storm: Upstream microservices and web clients automatically retried timed-out requests with aggressive retry policies. This multiplied the incoming write load by 3x, locking CPU utilization at 100% until upstream circuit breakers tripped and load shedders dropped traffic.

The Fix: OpenAI implemented jittered exponential backoff across all clients and deployed aggressive load shedding at the API gateway, instantly dropping non-essential requests when database query latencies exceed safe thresholds.

8. Engineering Takeaways: When NOT to Shard

  1. Exhaust Monolithic Optimizations First: Sharding introduces severe distributed complexity: loss of cross-shard foreign keys, complex distributed transactions, and split-brain hazards. A tuned PostgreSQL primary with PgBouncer can handle hundreds of millions of users if reads are segregated.
  2. Read Scaling Buys Time: If your workload is >90% reads, 50 read replicas will absorb nearly all user traffic, letting a single writer focus entirely on state transitions.
  3. Defend the Database with Circuit Breakers: The database must never be the component that handles traffic surges. Rate limiters, request coalescing, and load shedding must protect the database at the edge.
