Microservices Design Patterns — Strangler Fig, SAGA, CQRS & Transactional Outbox

👤 Author: Rishi Chowdhury 📅 Published: Jan 9, 2026 ⏱️ 14 min read 📁 Category: Microservices
📄 View / Download Original PDF ← Back to Blog Index
📌 Microservices Architectural Blueprint

Deconstructing monoliths and orchestrating distributed microservices introduces complex failure modes. This detailed technical guide synthesizes battle-tested microservice design patterns: Monolith migration via the Strangler Fig Pattern, Database-per-Service isolation, distributed transactions via the SAGA Pattern, read/write segregation with CQRS, and solving the distributed dual-write crisis using the Transactional Outbox Pattern & Change Data Capture (CDC).

1. The Strangler Fig Pattern

1.1 Context & Anti-Pattern

Attempting a "Big Bang" rewrite of a mission-critical legacy monolith is notoriously risky. Rewrites take years, during which business requirements shift, features drift, and the eventual cutover frequently results in massive downtime.

The Strangler Fig Pattern (inspired by vines that slowly envelop and replace a host tree) provides a safe, incremental migration methodology by gradually replacing monolithic features with microservices until the monolith disappears.

    Gateway -->|"New Feature Routes / Migrated (Canary 10% -> 100%)"| NewService["New Order Microservice"]

1.2 Step-by-Step Execution

  1. Insert an API Gateway / Reverse Proxy: Place an API gateway (e.g. Kong, Envoy, NGINX) in front of the existing monolith. All client traffic passes through the gateway.
  2. Carve Out a Domain Boundary: Identify a distinct, self-contained business domain (e.g., Order Service) and build it as an independent microservice.
  3. Route Traffic Incrementally: Configure the gateway to route a small canary fraction of traffic (10%) to the new microservice. Monitor error rates and latency.
  4. Ramp Up and Deprecate: Gradually increase traffic to 50%, then 100%. Once stable, decommission the corresponding legacy code inside the monolith.
  5. Repeat: Iterate domain by domain until the entire monolithic codebase is retired.

2. Data Management: Shared DB vs. Database-per-Service

Approach Description Trade-offs & Verdict
Shared Database (Anti-Pattern) Multiple distinct microservices connect directly to a single central database instance and share tables. Dangerous: Creates hidden tight coupling. A schema modification in Service A breaks Service B without warning. Contention on database connections and lock escalation.
Database-per-Service (Best Practice) Each microservice owns and encapsulates its own private data store. No outside service can query or touch the tables directly; all access is via public service APIs or domain events. Recommended: Complete domain autonomy, independent scaling, choice of polyglot databases (e.g. Postgres for billing, Mongo for catalogs, Redis for sessions). Challenge: Distributed transactions require SAGAs.

3. The SAGA Pattern for Distributed Transactions

3.1 The Failure of 2-Phase Commit

Traditional ACID transactions rely on 2-Phase Commit (2PC) to coordinate transactions across multiple databases. However, 2PC is synchronous, blocking, and vulnerable to coordinator crashes, severely reducing scalability and availability in cloud microservices.

A SAGA is a sequence of local transactions where each local transaction updates the database inside a single service and publishes a message/event. If a subsequent step in the sequence fails, the SAGA coordinates a series of Compensating Transactions that roll back previous modifications in reverse order.

  participant OrderSvc as Order Service

  Orchestrator->>OrderSvc: 1. Create Order (Pending)
  OrderSvc-->>Orchestrator: Order Created OK
  Orchestrator->>PaymentSvc: 2. Process Credit Card Payment
  PaymentSvc-->>Orchestrator: Payment Authorized OK
  Orchestrator->>InventorySvc: 3. Reserve Product Inventory
  InventorySvc-->>Orchestrator: ERROR: Out of Stock!
  Note over Orchestrator,InventorySvc: SAGA Failure Triggered -> Begin Compensating Transactions
  Orchestrator->>PaymentSvc: 4. Refund / Void Payment (Compensating Tx)
  PaymentSvc-->>Orchestrator: Payment Refunded OK
  Orchestrator->>OrderSvc: 5. Mark Order CANCELLED (Compensating Tx)
  OrderSvc-->>Orchestrator: Order Cancelled OK
Figure 7: Orchestration-based SAGA executing compensating rollback transactions.

3.2 Choreography vs Orchestration

  • Choreography (Event-Driven): Services listen to domain events and execute local transactions independently without a central coordinator. Best for simple workflows (2-3 services). Becomes hard to trace and debug at scale due to cyclic dependencies.
  • Orchestration (Central Coordinator): A dedicated orchestrator state machine coordinates the flow, tells participants which actions to take, and manages compensation upon failure. Recommended for complex multi-step enterprise workflows.

4. CQRS (Command Query Responsibility Segregation)

In standard architectures, the same relational data model is used for both writes (commands) and reads (queries). As scale grows, complex joins and aggregates choke transactional tables.

CQRS strictly bifurcates the application model into two distinct paths:

  • Command Side: Handles state modifications (CreateOrder, CancelItem). Optimized for validation, business logic, write throughput, and consistency.
  • Query Side: Handles read requests (GetCustomerDashboard). Uses denormalized, read-optimized Materialized Views (often stored in Elasticsearch or Redis) updated asynchronously via domain events.

5. The Transactional Outbox Pattern & CDC

5.1 The Distributed Dual-Write Problem

A classic bug in microservices occurs when a service must perform two actions atomically: update its local database AND publish an event to Kafka:

Java Antipattern: Dual-Write Bug
// ANTI-PATTERN: Prone to silent data corruption
@Transactional
public void completeOrder(Order order) {
    orderRepository.save(order);        // Step 1: Saves to DB
    kafkaTemplate.send("orders", order); // Step 2: Can crash or fail network!
}

If the application crashes or network times out after saving to the DB but before publishing to Kafka, Kafka never receives the event. If you reverse the order, the event publishes but the DB transaction could roll back. Distributed systems cannot guarantee atomic operations across two independent network resources without distributed transactions.

5.2 The Solution: Outbox Table + Change Data Capture

(id, event_type, payload)"]
    end

  end

  subgraph CDCTier["Change Data Capture (Debezium)"]
    Debezium["Debezium Connector
(Tails DB Binlog)"]

  end

  subgraph BrokerTier["Message Broker"]
    Debezium -->|"Guaranteed Publish"| Kafka["Kafka Topic: 'orders'"]
  end
Figure 8: Transactional Outbox Pattern with Change Data Capture (CDC / Debezium).
  1. Along with the primary business table, create an outbox table in the same database.
  2. When a business action occurs, write the domain state to orders AND insert the event payload into outbox inside the same single local ACID database transaction!
  3. A Change Data Capture tool (such as Debezium or a lightweight transaction log tailer) asynchronously monitors the database binary log (WAL / binlog), extracts records inserted into the outbox table, and reliably publishes them to Apache Kafka.
  4. This guarantees At-Least-Once event delivery without distributed locking or data loss!
