Distributed Architecture Patterns

Microservices Design Patterns: Strangler Fig, Data Topology, SAGA & CQRS

📁 Category: Software Architecture & Distributed Systems
← Back to All Notes
📌 Architectural Blueprint

Decomposing monolithic architectures into microservices replaces a single codebase and unified database with distributed independent network services. This architectural shift introduces critical challenges around zero-downtime migration, data ownership, distributed transactions, and cross-boundary querying. This technical deep dive analyzes the four foundational architectural patterns that resolve these challenges: the Strangler Fig Pattern for risk-free evolutionary migration, Database-per-Service vs the Shared DB anti-pattern, the SAGA Pattern for distributed eventual consistency without 2PC deadlocks, and CQRS for high-performance read projections.

1. The Strangler Fig Pattern & Legacy Migration

When an enterprise decides to migrate a massive monolithic legacy codebase to microservices, software leaders face a fundamental choice between two strategies:

Strategy Execution Model Risk Profile & Failure Modes
"Big Bang" Rewrite A separate team spends 18–36 months rebuilding the entire system from scratch in parallel, followed by a cutover weekend. Catastrophic Failure Rate: Requirements drift continuously, legacy business logic is lost, cutover creates unprecedented failure blast radius, and rollbacks are nearly impossible.
Strangler Fig Pattern Gradual, incremental migration: new microservices are built at the edges of the legacy monolith, intercepting slices of traffic until the monolith is retired. Low Risk: Small, independently deployable iterations, instant canary traffic shifting, guaranteed zero-downtime rollbacks, and immediate business value delivery.

The pattern takes its name from the tropical strangler fig tree, which seeds in the upper branches of a host tree, sends roots down to the soil, gradually envelops the host, and eventually stands independently after the host tree rots away.

The Five-Phase Strangler Fig Lifecycle

  1. Deploy the Edge Facade (Interception Controller): Place an API Gateway (e.g., Envoy, Kong, AWS API Gateway) or reverse proxy in front of the monolithic application. All client traffic hits the facade first, which transparently proxies 100% of requests to the monolith.
  2. Identify & Carve Out an Edge Bounded Context: Identify a high-value, loosely coupled domain module (e.g., the "Product Search" or "Notification" domain). Implement this capability as a standalone, production-ready microservice with its own private data store.
  3. Canary Traffic Shifting: Reconfigure the facade routing table:
    • Initially route 90% of search requests to the monolith and 10% to the new microservice.
    • Compare latency, error rates, and CPU utilization across both endpoints.
  4. Zero-Downtime Rollback Protection: If the new microservice encounters unexpected concurrency bottlenecks or database deadlocks, the facade instantly re-routes 100% of traffic back to the legacy monolith with zero client disruption.
  5. Total Strangulation & Code Elimination: Gradually ramp traffic ($10\% \to 50\% \to 100\%$). Once the new service is validated in production, the obsolete search code and database tables inside the monolith are permanently deleted. The team then repeats the cycle for the next domain module.

2. Data Topology: Shared DB vs Database-per-Service

Before implementing distributed transactions, an engineering team must define its data persistence boundaries.

A. Shared Database (The Microservices Anti-Pattern)

In a shared database architecture, multiple distinct microservice processes connect directly to a single shared relational database cluster.

⚠️ Why Shared Database Inevitably Fails at Scale
  • Runtime Coupling & Lock Contention: A slow analytical query or table lock initiated by the Reporting Service blocks row writes from the mission-critical Order Service, triggering cascading thread exhaustion.
  • Schema Fragility: Because multiple services read from the same tables, altering a single column or adding a constraint requires cross-team synchronization and coordinated deployments, destroying deployment independence.
  • Technology Lock-In: Every microservice is forced to use the same underlying storage engine, preventing teams from selecting specialized storage solutions (e.g., NoSQL for session caching, Neo4j for social graphs, or Elasticsearch for search).

B. Database-per-Service (The Recommended Architectural Standard)

In the Database-per-Service pattern, each microservice owns, controls, and encapsulates its own private data store.

Architectural Invariant Technical Implication Business Benefit
Zero Direct Cross-DB Access No service may ever connect to or read another service's database directly. Communication occurs strictly over documented APIs (REST/gRPC) or asynchronous events. Guarantees complete internal schema autonomy and encapsulation.
Polyglot Persistence Each service chooses the optimal database technology for its domain model (e.g., relational for ledger transactions, document store for product catalogs). Maximizes hardware efficiency and developer velocity.
Independent Scaling The Order DB can scale up CPU and read replicas independently without inflating the cost of the Customer DB. Linear, predictable cloud infrastructure costs.

The Two Grand Challenges of Database-per-Service

Decoupling databases solves modularity but immediately creates two profound distributed systems dilemmas:

  1. The Distributed Transaction Challenge: How do you maintain data consistency across multiple databases without 2-Phase Commit (2PC) bottlenecks? $\implies$ Solved by the SAGA Pattern.
  2. The Distributed Join Challenge: How do you execute complex queries that join data living in three distinct databases without creating $O(N)$ HTTP network waterfalls? $\implies$ Solved by CQRS.

3. The SAGA Pattern & Distributed Transactions

In a monolithic architecture, executing a multi-step business process (e.g., Order Checkout $\to$ Deduct Inventory $\to$ Process Payment) relies on classical relational database ACID transactions (Atomicity, Consistency, Isolation, Durability) wrapped in a single BEGIN TRANSACTION ... COMMIT block.

In a microservices architecture, this single business action spans three autonomous services with three distinct databases. Classical distributed transaction protocols like Two-Phase Commit (2PC) are completely unsuitable for cloud-scale architectures:

  • 2PC Blocking Invariant: 2PC holds global row locks across all participating databases across the network throughout both prepare and commit phases. If a single network packet drops or one node stalls, all locks remain held, causing cluster-wide connection pool exhaustion.
  • CAP Theorem Trade-Off: Under network partitions, 2PC sacrifices availability completely to maintain strict consistency.

The SAGA Solution: Sequences of Local Transactions

A SAGA decomposes a global transaction into a sequence of local transactions. Each local transaction updates its private database, commits immediately, and emits a domain event or message to trigger the next local transaction in the chain.

The Compensating Transaction (Semantic Undo)

Because each local transaction commits immediately, a subsequent failure cannot be "rolled back" at the database level. Instead, the SAGA relies on Compensating Transactions: forward-correcting semantic undos executed in reverse order.

For example, if the Payment Service fails after the Inventory Service has committed a stock reservation, the SAGA does not execute a rollback. Instead, it invokes a compensating transaction on the Inventory Service that adds the reserved items back into the stock pool, returning the system to a clean, consistent state.

3.1 Choreography-Based SAGA (Decentralized)

In a Choreographed SAGA, there is no centralized coordinator. Participating microservices subscribe to domain events published to a message broker (such as Apache Kafka or RabbitMQ) and independently trigger local transactions based on incoming events.

Choreography Trade-Off Analysis

  • Advantages:
    • Simplicity for Small Workflows: Easy to implement for workflows spanning 2 to 3 services.
    • Loose Coupling: Services only depend on shared event contracts; there is no centralized orchestrator bottleneck.
  • Disadvantages:
    • Cyclic Dependencies: As workflows grow to 6+ services, tracking event flow becomes cognitive overhead. Services risk entering circular event loops.
    • Invisible State Machine: Understanding the current end-to-end status of an order requires stitching together logs across multiple distributed systems.

3.2 Orchestration-Based SAGA (Centralized)

In an Orchestrated SAGA, a dedicated Saga Orchestrator (implemented using tools like Temporal, AWS Step Functions, or custom state machines) manages the entire lifecycle. The orchestrator explicitly commands participating services to execute local transactions and listens for their command acknowledgments.

Orchestration Trade-Off Analysis

  • Advantages:
    • Centralized State Visibility: The orchestrator's state table provides a single source of truth for the real-time execution status of any distributed transaction.
    • Deterministic Error Handling: Timeouts, exponential backoff retries, and compensation cascades are configured centrally in a state diagram rather than scattered across dozens of event listeners.
    • Elimination of Cyclic Event Webs: Participating services remain simple command processors without requiring knowledge of upstream or downstream business flows.
  • Disadvantages:
    • Central Coordinator Risk: The orchestrator service must be architected for high availability; if the coordinator fails, ongoing transactions pause.

4. CQRS: Command Query Responsibility Segregation

In standard application design, the same data model is used to handle both writes (insert, update, delete) and reads (fetch, search). In microservices with Database-per-Service, this approach breaks down when handling complex cross-service queries.

The "Join Problem" in Microservices

Consider an e-commerce dashboard query: "Display the latest 50 orders for Customer X, including shipping status, ordered product thumbnails, payment method, and warehouse dispatch ETA."

Because data is sharded across Customer DB, Order DB, Inventory DB, and Shipping DB, an application cannot execute a SQL JOIN. The naive alternative—querying the Order Service, then issuing 50 concurrent HTTP requests to the Product Service, and 50 requests to the Shipping Service—results in catastrophic $N+1$ network request storms, extreme latency, and cascading service outages.

The CQRS Architecture: Decoupling Command & Query Models

CQRS resolves this by splitting the application into two completely independent architectural models:

Command Model vs Query Model

Architectural Vector Command Model (Write Tier) Query Model (Read Tier)
Primary Responsibility Validates incoming business commands, enforces business domain invariants, mutates state, and guarantees atomic commits. Returns pre-aggregated, read-optimized data payloads directly to client interfaces with zero real-time joins.
Data Structure Strictly normalized (3NF) relational tables or append-only event logs to prevent write anomalies. Heavily denormalized flat documents or JSON views designed specifically for single-query retrieval.
Storage Engine ACID-compliant relational store (PostgreSQL, MySQL) or distributed key-value store. Search engines (Elasticsearch), in-memory caches (Redis), or document stores (MongoDB).
Consistency Model Strong Consistency on local entity boundaries. Eventual Consistency: Asynchronously catches up with the write model within milliseconds.

4.1 Asynchronous Projections & Eventual Consistency

How does the Query Model stay synchronized with the Command Model?

  1. Change Data Capture (CDC): A tool like Debezium tails the transaction write-ahead log (WAL) of the Write Database and streams insert/update records into an Apache Kafka topic.
  2. Projection Workers: Background projection services consume the Kafka stream. When an OrderCreated or PaymentReceived event arrives, the worker fetches related customer and product details, constructs a denormalized JSON document: 
    {
  "order_id": "ord_9941",
  "customer_name": "Alice Smith",
  "customer_email": "alice@example.com",
  "items": [
    {"name": "Mechanical Keyboard", "price": 120.00, "thumbnail": "https://img/kb.png"}
  ],
  "shipping_status": "DISPATCHED",
  "payment_status": "PAID"
}
  3. Zero-Join Querying: When the web dashboard queries the order, the Query Handler performs a single $O(1)$ point lookup against the Read Database. No cross-service network calls or database joins are required.
Handling Read-Your-Own-Writes Lag

Because the projection pipeline is asynchronous, a user who immediately refreshes the page after placing an order might read stale data from the Query Model. Production systems mitigate this by:

  • Optimistic Client Updates: The client UI immediately inserts the newly created order into local client state without waiting for the read model projection.
  • Version / ETag Routing: The client passes the mutation timestamp or version number. If the read model's projected version is behind, the query handler routes the read directly to the primary write model for that single request.

5. Architectural Summary & Decision Matrix

Design Pattern Core Problem Solved When to Apply Key Trade-Off / Risk
Strangler Fig High failure rate of "Big Bang" legacy monolithic rewrites. Migrating existing production monoliths without downtime. Requires maintaining routing facades and data synchronization during transition.
Database-per-Service Shared DB runtime lock contention, schema coupling, and blast radius. All greenfield microservice architectures. Breaks cross-service ACID transactions and cross-database SQL joins.
SAGA Pattern Executing distributed business transactions across multiple databases. Workflows spanning multiple bounded contexts (e.g., Checkout, Fulfillment). Requires writing complex compensating transactions; isolation anomalies (dirty reads).
CQRS High query latency and $N+1$ network calls when querying across services. High-read platforms, complex dashboard views, rich full-text search requirements. Increased infrastructure complexity and inherent eventual consistency lag.
Final Synthesis

Microservices architecture is not merely about splitting code into smaller repositories—it is fundamentally a reorganization of state boundaries. By combining the Strangler Fig for evolutionary migration, Database-per-Service for state encapsulation, SAGA for eventual transaction consistency, and CQRS for optimized query projection, software architects build distributed systems that scale linearly across both organizational headcount and compute infrastructure.
