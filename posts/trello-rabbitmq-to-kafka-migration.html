Real-Time Messaging

Why and How Trello Moved from RabbitMQ to Kafka for WebSocket Real-Time Updates

By Arpit Bhayani Dissection & Trello Infrastructure • October 2026 • 15 min read

1. Context: Real-Time Collaboration at Trello Scale

Trello is one of the world's most popular visual project management platforms. At the core of Trello's user experience is instantaneous multiplayer synchronization: when a teammate drags a card across columns, attaches a label, or checks off a task, every other user viewing that board must see the UI update instantly without refreshing the browser.

To maintain real-time bidirectional communication, Trello manages millions of concurrent persistent WebSocket connections distributed across dozens of frontend socket servers.

The underlying messaging backbone has evolved over three distinct architectural eras:

  1. Era 1 (Redis Pub/Sub): Simple in-memory pub/sub; quickly hit memory limits and lacked persistence.
  2. Era 2 (RabbitMQ Clusters): Enterprise AMQP message broker cluster utilizing transient queues and exchange routing.
  3. Era 3 (Apache Kafka): Distributed, immutable partitioned commit log feeding dedicated Socket Master consumers.

2. The Legacy RabbitMQ Mesh Architecture

During Era 2, Trello deployed a complex 15-node RabbitMQ cluster divided into two tiers:

  • Inbound Cluster: Ingested user action events from web servers and API endpoints.
  • The Shovel Plugin: Mirrored and forwarded messages between the inbound and outbound clusters.
  • Outbound Cluster: Fanned out events to transient, ephemeral queues bound to specific WebSocket worker instances.

3. The Three Pain Points: Split-Brain, Queues & GC

While RabbitMQ worked well at moderate scale, operating it under millions of active WebSocket sessions exposed three catastrophic failure modes:

1. The Split-Brain Catastrophe

RabbitMQ relies on Erlang Mnesia distributed clustering. During transient cloud network partitions, the 15-node cluster would partition into separate sub-clusters. In a split-brain state, queues diverged, metadata became inconsistent, and the cluster could not automatically reconcile. Recovering required full manual cluster restarts, dropping all real-time events and degrading board synchronization across millions of users.

2. Ephemeral Queue Churn & Erlang GC Pressure

Because WebSocket clients constantly connect, disconnect, and roam across Wi-Fi/mobile networks, Trello's architecture continually created and destroyed thousands of transient queues per minute:

The Erlang Process Table Bottleneck: In RabbitMQ, each queue is an Erlang process backed by internal Mnesia table entries. Constantly spinning up and tearing down thousands of ephemeral queues created massive garbage collection churn, memory fragmentation, and periodic CPU latency freezes.

3. Fan-out Binding Explosion

When a card update occurred on a board with 50 active collaborators, RabbitMQ's exchange had to evaluate routing keys and copy the message into 50 distinct queue buffers in memory, ballooning memory usage and broker load.

4. The Kafka Paradigm: The Socket Master Topology

To eliminate transient queues and split-brain failures, Trello migrated its entire messaging core to Apache Kafka.

The Socket Master Mechanics:

  • Decoupled Ingestion: Board mutations are published into a persistent, partitioned Kafka topic (board-updates). Kafka doesn't know or care about individual WebSocket connections.
  • The Socket Master Pool: A lean pool of stateless workers consumes from Kafka in parallel batches.
  • Direct Targeted Forwarding: The Socket Master inspects an in-memory routing table mapping active user IDs to specific WebSocket server hosts. Instead of broadcasting to all nodes, it forwards the event directly over a persistent TCP/HTTP loop to the exact server holding the user's socket.

5. Message Queues vs. Distributed Logs: Structural Analysis

Trello's journey illustrates the fundamental architectural difference between traditional message brokers and log-centric streaming engines:

Architecture Dimension RabbitMQ (AMQP Message Broker) Apache Kafka (Distributed Commit Log)
Core Data Structure Discrete message queues in Erlang memory; messages deleted upon consumption. Sequential, append-only disk segments; immutable log with offset pointers.
Consumer Tracking Broker tracks delivery state for every message and consumer; heavy stateful broker. Consumers track their own read offsets; broker remains stateless and ultra-lean.
Ephemeral Client Handling Creates transient queues per client; severe GC and process allocation tax. Zero queue creation; decoupled consumers read from static partitions.
Cluster Consensus Erlang Mnesia; vulnerable to split-brain network partitions. Raft / KRaft (formerly ZooKeeper); strict quorum consensus, split-brain immune.

6. Production Impact: 5x Cost Reduction & 2x CPU Gain

The migration from RabbitMQ to Kafka delivered transformative operational improvements across Trello's production systems:

Metric / Dimension Legacy RabbitMQ Architecture Modern Kafka Architecture System Improvement
Infrastructure Operational Cost 15-node heavy broker cluster footprint Lean Kafka cluster + lightweight Socket Masters 5x direct cost reduction (~80% savings)
CPU Utilization Efficiency High CPU churn from Erlang GC and queue lifecycle High-throughput batch sequential I/O 2x improvement in CPU efficiency
Memory Footprint Millions of message copies across transient queues Zero-copy page cache OS buffers 33% reduction in memory usage
Major Outage Frequency Recurring split-brain manual cluster resets Zero split-brain cluster crashes Near-zero major real-time outages

7. First-Principles Summary & Design Lessons

  • Do Not Map Ephemeral Client State to Broker Infrastructure: Creating a queue in a message broker for every short-lived client connection causes resource exhaustion. Use immutable partition streams and handle connection dispatch in an application proxy tier.
  • Append-Only Logs Outscale Stateful Queues: Brokers that maintain state per message (RabbitMQ) hit scaling ceilings under massive fan-out. Append-only logs that offload offset tracking to consumers (Kafka) scale linearly with zero broker memory bloat.
  • Targeted Routing Beats Indiscriminate Broadcast: Pushing events through a Socket Master with connection location awareness reduces internal network bandwidth by orders of magnitude compared to blindly flooding every socket server.
