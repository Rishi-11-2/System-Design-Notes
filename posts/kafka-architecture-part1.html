Event Driven Architecture

Kafka Architecture — Part 1: Distributed Streaming, Partitioning & Storage Mechanics

📁 Category: Event Streaming & Message Brokers
← Back to All Notes
📌 Architectural Blueprint

Apache Kafka fundamentally redefines enterprise data transport by replacing transient message queues with a distributed, partitioned, immutable append-only commit log. This technical breakdown dissects Kafka from first principles based on the foundational system architecture notes: the distributed streaming paradigm versus classical pub/sub, the anatomy of topics and broker topology, the partition-level ordering invariant, segment rolling and sparse index binary search, and deterministic producer partition allocation strategies.

1. Introduction: Distributed Streaming vs Traditional Pub/Sub

To understand why Apache Kafka was created, one must examine the operational bottlenecks of classical message-oriented middleware (MOM) such as RabbitMQ, ActiveMQ, or IBM MQ.

Traditional message brokers are designed around transient message queues. In these systems:

  • Producers push messages to an exchange or queue.
  • The broker maintains complex in-memory state tracking which consumers have received and acknowledged each message.
  • Once a consumer sends an acknowledgment (ACK), the broker immediately purges the message from disk/RAM to conserve space.

This design introduces three major architectural limitations at internet scale:

  1. Destructive Consumption: Once consumed and acknowledged, data disappears. If a downstream fraud analytics service, data warehouse ingest pipeline, or machine learning model needs to process that same stream of events hours or days later, it cannot do so unless the original publisher re-transmits the data.
  2. Queue Degradation Under Backlog: Because classical brokers track individual message states and acknowledgement trees in memory, when consumers slow down and millions of messages accumulate in queues, RAM exhausts and brokers swap to random-access disk storage, causing catastrophic throughput collapse.
  3. Tight Fan-Out Coupling: Adding five new microservices as consumers requires duplicating queues or placing heavy replication and state-tracking burdens on the centralized broker.

The Distributed Event Streaming Model

Kafka departs from ephemeral message queuing by implementing a persistent, distributed event streaming platform. In Kafka, an event is simply a recorded fact: a business interaction (e.g., "User 104 placed Order 991") stored with an immutable timestamp, key, payload, and headers.

Architectural Vector Classical Message Queue (e.g., RabbitMQ) Distributed Commit Log (Apache Kafka)
Data Retention Model Transient: Messages are deleted upon consumer ACK. Persistent: Events are retained for a configurable retention window (e.g., 7 days, 1 year, or forever) regardless of consumption status.
Consumer State Tracking Broker-centric: The broker tracks delivery state, inflight ACKs, and redelivery queues per consumer. Client-centric: Consumers track their own reading position via a lightweight integer pointer called an offset. The broker remains stateless regarding consumer buffer windows.
Replayability Impossible without manual upstream republishing. Native and zero-overhead: Any consumer can reset its offset pointer backwards in time to re-process historical logs.
Throughput Profile $10^4$ to $10^5$ messages/sec (bound by random I/O and state maintenance overhead). $10^6$ to $10^7$ events/sec (bound strictly by sequential disk I/O and network saturation via OS zero-copy).
Multi-Subscriber Scalability Queue replication per subscriber consumes storage and broker CPU. Single shared log read by multiple independent consumer groups simultaneously without data duplication.

By treating events as an append-only sequence of immutable records on disk, Kafka provides historical replayability, high horizontal scalability, and true temporal decoupling between producers and consumers.

2. Core Architecture: Producers, Topics, and Brokers

The core Kafka cluster topology consists of three fundamental entities: Producers, Topics (and their underlying Partitions), and Brokers.

1. The Producer

A producer is a client application that constructs and emits event records to Kafka. Producers operate under a decoupled publish model:

  • Decoupled Publishing: The producer sends an event into a logical topic without knowing, caring, or waiting to see which consumer services will read it, when they will read it, or whether any consumer is currently online.
  • Batching & Compression: Rather than sending individual network packets per event, Kafka producers accumulate records destined for the same partition in local memory buffers (controlled by batch.size and linger.ms) and transmit them as compressed batches (using LZ4, Snappy, or zstd), maximizing network utilization and disk write throughput.
  • Cluster Metadata Discovery: The producer connects to any single "bootstrap" broker, downloads the complete cluster metadata map (identifying which brokers are leaders for which topic partitions), and thereafter routes write requests directly to the socket connection of the designated leader broker.

2. The Topic

A Topic is a logical category, channel, or feed name to which events are published. In conceptual terms, think of a topic as a structured table in a relational database or a directory in a filesystem:

  • Producers only specify the topic name (e.g., orders.v1, telemetry.gps) when writing records.
  • Topics are strictly multi-producer and multi-consumer: dozens of microservices can write to the same topic concurrently, while completely unrelated consumer groups (e.g., billing, fraud detection, push notifications) read from the same topic independently at their own pace.
  • A topic itself is purely a logical abstraction. Under the hood, a topic does not exist as a single file on a single disk; instead, every topic is physically sharded into one or more Partitions.

3. The Broker

A Broker is an individual, self-contained Kafka server process (a JVM daemon running on bare metal, virtual machines, or containerized nodes). A collection of brokers forms a Kafka cluster:

  • Physical Storage: Brokers receive serialized record batches over TCP, append them to local disk files, and serve read requests to consumers.
  • Partition Hosting: A single broker physically stores a subset of partitions from various topics across the cluster. For example, Broker 101 might store Partition 0 of the orders topic and Partition 2 of the payments topic.
  • State Isolation: Brokers maintain no per-consumer cursor states in memory. A read request from a consumer is simply: "Send me $K$ bytes starting at byte offset $B$ in partition log $P$." The broker reads the requested slice using kernel-level zero-copy and flushes it straight to the network card.

3. Partitions & Offset Mechanics: The Ordering Invariant

The partition is the fundamental unit of scalability, parallelism, and physical storage in Apache Kafka.

Physical Partition Structure

When you create a topic with $M$ partitions, Kafka allocates $M$ separate directories on disk across the cluster brokers. If a broker hosts Partition 0 of topic orders, its local filesystem contains a directory named orders-0/.

A partition is strictly an append-only, immutable commit log:

  • Events can only be written to the tail (end) of the log. Once written, an event cannot be modified or reordered in place.
  • Sequential appends eliminate random disk arm movements on mechanical HDDs and avoid random-write erase-block wear on SSDs, achieving write speeds that approach hardware bus limits.

Offsets: Monotonic Identifiers

Every event that enters a partition is assigned an incrementing 64-bit integer called an Offset:

  • Offsets are assigned sequentially by the partition leader at ingestion time.
  • Each partition maintains its own independent offset counter. Partition 0 starts at offset 0, 1, 2, ... and Partition 1 also starts at offset 0, 1, 2, ...
  • An offset has no global meaning across the topic; an event is uniquely identified in a Kafka cluster only by the tuple: $$\text{Global Unique ID} = (\text{Topic}, \text{Partition ID}, \text{Offset})$$
  • Consumers read events sequentially in ascending offset order. Because the offset is monotonically increasing, consumer state reduces to a single integer: "My current committed position on Partition 0 is offset 54."

The Crucial Ordering Rule: Partition vs Global Order

⚠️ The Fundamental Ordering Invariant

Order is guaranteed strictly within a single partition. Kafka does NOT guarantee global ordering across multiple partitions in the same topic.

Why is global ordering across partitions mathematically and architecturally impossible in a horizontally scalable system?

  1. Distributed Consensus Bottleneck: To guarantee total, strict global ordering across 100 partitions hosted on 20 different servers, every write would require a centralized, synchronized global timestamp oracle or distributed lock manager (such as a 2PC or atomic broadcast). This centralized coordinator would immediately serialize all traffic, collapsing cluster write throughput down to the capacity of a single coordinator node.
  2. Network Transit Skew: Even if events $E_1$ and $E_2$ are emitted concurrently by two client threads, network interleaving, packet retries, and socket buffering mean they can arrive at Broker A and Broker B in arbitrary order.

How Systems Achieve Correct Ordering Without Global Locks

In real-world distributed architectures, global ordering across an entire system is almost never required. You do not care whether User A's coffee order in Seattle is processed before or after User B's pizza order in London. What you do care about is that all state transitions for the same entity are processed in strict chronological order:

  • User 104 creates account $\to$ updates profile $\to$ adds credit card $\to$ places order.
  • Order 991 created $\to$ paid $\to$ packed $\to$ shipped.

By routing all events belonging to the same entity (e.g., all events with key = order_id) to the exact same partition, Kafka guarantees that those events are written sequentially to the exact same log and read by a consumer in the exact order they occurred.

4. Storage Engine: Segments, Sparse Indexing & Binary Search

If a partition were implemented as a single, monolithic file on disk, two severe operational failures would occur:

  1. Unbounded File Growth: In an active topic receiving billions of events, a single log file would quickly grow to hundreds of gigabytes or terabytes. Modifying, reading, or truncating a multi-terabyte file causes severe OS file system lock contention.
  2. Inability to Expire Old Data: Kafka enforces data retention policies (e.g., delete data older than 7 days). Operating systems cannot delete bytes from the beginning of a flat file without rewriting the entire remaining contents of the file—an impossibly expensive $O(N)$ disk write operation.

Segment Files: Breaking Down the Log

To solve this, Kafka breaks each partition log into smaller, immutable disk chunks called Segments. A partition directory contains a collection of segment files:

File Name Pattern File Type Purpose and Internal Content
00000000000000000000.log Data Log Stores the actual serialized event records (magic byte, CRC32, timestamp, key size, key, value size, payload).
00000000000000000000.index Sparse Offset Index Maps logical relative offsets to physical byte positions within the companion .log file.
00000000000000000000.timeindex Timestamp Index Maps record timestamps to logical offsets to support temporal range queries (e.g., rewind to 08:00 AM).
00000000000000000500.log Active / Next Data Log The new active segment file created once the previous segment reached size limit or rolling window.

Segment Naming Convention

Segments are named based on their base offset (the offset of the first record stored in that segment), padded with leading zeros to exactly 20 digits:

  • 00000000000000000000.log: Contains records from offset 0 up to 499.
  • 00000000000000000500.log: Contains records starting from offset 500 onwards.

When does a segment roll over? Kafka closes the current "active" segment (which is write-only) and opens a new one when:

  1. The segment size reaches segment.bytes (default: 1 GB).
  2. The segment age reaches segment.ms (default: 7 days).
  3. The index file reaches segment.index.size.bytes (default: 10 MB).

Because historical segments are immutable, data expiration becomes an $O(1)$ filesystem operation: Kafka simply calls the OS system call unlink() to delete obsolete segment files whose records have passed the retention threshold.

Sparse Indexing: Why Kafka Does Not Index Every Record

If Kafka maintained an index entry for every single message, the index file would consume massive amounts of disk space and RAM. For a topic with billions of small 100-byte events, the index overhead would equal or exceed the size of the raw data.

Instead, Kafka implements a Sparse Index:

  • Kafka only appends an entry to the .index file after a configurable number of bytes of payload have been appended to the .log file.
  • This interval is controlled by index.interval.bytes (default: 4096 bytes / 4 KB).
  • Each entry in the .index file is a compact 8-byte binary tuple:
    • Relative Offset (4 bytes): The offset of the record relative to the segment's base offset (allowing 32-bit integer storage instead of 64-bit).
    • Physical Position (4 bytes): The absolute byte position within the .log file where that record begins.

Step-by-Step Read Execution: Locating an Arbitrary Offset

Suppose a consumer requests records starting at offset 542 from Partition 0:

  1. Step 1: Locate the Segment File ($O(\log S)$):

    Kafka keeps a memory-resident sorted list (or ConcurrentSkipListMap) of all segment base offsets. By performing a floor lookup on 542, Kafka determines that offset 542 falls inside the segment starting at base offset 500 (files: 00000000000000000500.log and 00000000000000000500.index).

  2. Step 2: Binary Search in Sparse Index ($O(\log N)$):

    The base offset is 500, so the relative target offset is: $$\text{Relative Offset} = 542 - 500 = 42$$ Kafka memory-maps (mmap) the .index file into OS virtual memory and executes a binary search to find the largest indexed relative offset that is $\le 42$. Suppose the nearest index entry is: $$\text{Index Entry} = (\text{Relative Offset: } 40, \text{Physical Position: } 8192)$$

  3. Step 3: Direct File Seek and Sequential Scan:

    Kafka jumps directly to byte offset 8192 in 00000000000000000500.log. Because index entries are created every 4 KB, the target record is guaranteed to be within the next 4 KB block. Kafka scans sequentially forward past offset 40 and 41 to reach offset 42 (absolute offset 542).

This design strikes an optimal balance: binary search operates over a tiny, RAM-resident 10 MB index, and the subsequent linear scan is executed entirely inside the CPU cache line and OS page cache without causing expensive random disk seeks.

5. Producer Partitioning Strategies & Distribution Algorithms

When a producer publishes a record, how does it choose which partition of the topic to send the event to? The producer client runs an algorithmic decision pipeline before sending network requests.

MurmurHash2(key) % TotalPartitions"] Q2 -- No --> RoundRobin["Uniform Distribution:
Round-Robin / Sticky Partitioner"] HashKey --> Verify["Send batch to Leader Broker of Partition"] RoundRobin --> Verify UseExplicit --> Verify

Strategy 1: Key-Based Partitioning (Deterministic Hash Routing)

When business requirements require all events for a given entity to remain strictly ordered, the producer provides an explicit record key (e.g., user_id, order_id, or device_serial).

Kafka computes a 32-bit hash of the key using the MurmurHash2 algorithm, masks the sign bit, and performs a modulo operation over the total number of partitions $P$:

$$\text{Partition ID} = (\text{toPositive}(\text{MurmurHash2}(\text{key}))) \pmod{P}$$
Record Key MurmurHash2 Output Partitions ($P = 4$) Computed Partition Destination
order_abc_100 1,489,201,156 4 $1489201156 \pmod 4 = \mathbf{0}$
order_xyz_200 2,109,842,501 4 $2109842501 \pmod 4 = \mathbf{1}$
order_abc_100 (retry/next event) 1,489,201,156 4 $1489201156 \pmod 4 = \mathbf{0}$ (Deterministic Guarantee)
⚠️ The Partition Count Mutation Hazard

The key-based hashing formula is strictly dependent on the divisor $P$ (the partition count). If you increase the partition count of an existing topic from 4 to 8, then $\text{hash}(\text{key}) \pmod 8$ will evaluate to a completely different partition for future writes. Entity ordering will break across the repartition boundary because newer events will land on Partition 4 while older historical events reside on Partition 0. Never increase partition counts dynamically for topics where key ordering is vital without an architectural migration plan.

Strategy 2: Round-Robin & Sticky Partitioning

If no key is provided (key = null):

  • Classical Round-Robin: The producer cycles sequentially through available partitions ($0 \to 1 \to 2 \to 0 \to 1 \dots$), ensuring mathematically even load distribution across all brokers.
  • The Micro-Batching Inefficiency: In early Kafka clients, strict round-robin caused high latency when publishing small records: each event was assigned to a different partition, resulting in dozens of half-empty record batches waiting for linger.ms to expire.
  • Modern Sticky Partitioner (Kafka 2.4+): To optimize throughput, the producer sticks to a single partition until its batch fills up to batch.size (or linger.ms triggers), sends the complete batch over TCP, and then immediately picks the next partition in a pseudo-round-robin manner. This reduces CPU usage, lowers network packet overhead, and maintains overall cluster balance.

Strategy 3: Custom Partitioning Logic

Kafka allows developers to implement the org.apache.kafka.clients.producer.Partitioner interface to enforce domain-specific routing rules:

public class RegionCustomPartitioner implements Partitioner {
    @Override
    public int partition(String topic, Object key, byte[] keyBytes,
                          Object value, byte[] valueBytes, Cluster cluster) {
        List<PartitionInfo> partitions = cluster.partitionsForTopic(topic);
        int numPartitions = partitions.size();
        
        // Extract geographic country code from payload or key
        String countryCode = extractCountry(key, value);
        
        // Pin regional traffic to dedicated partitions for regulatory compliance
        if ("IN".equalsIgnoreCase(countryCode)) {
            return 0; // Domestic India partition
        } else if ("US".equalsIgnoreCase(countryCode)) {
            return 1; // United States partition
        } else if ("EU".equalsIgnoreCase(countryCode)) {
            return 2; // European Union partition (GDPR boundary)
        }
        
        // Fallback: Hash remaining global countries across remaining partitions
        return Math.abs(countryCode.hashCode()) % (numPartitions - 3) + 3;
    }
}

Custom partitioning is widely adopted in enterprise systems for:

  • Data Residency & Sovereignty: Directing data from specific jurisdictions to brokers hosted in compliant regulatory zones.
  • VIP Tenant Isolation: Routing high-volume enterprise clients to dedicated partitions so that sudden volume surges do not choke standard tier customers (noisy neighbor prevention).

6. Systems Engineering: Sequential I/O, Page Cache & Zero-Copy

How does Apache Kafka sustain multi-gigabyte per second throughput on standard enterprise hardware? The answer lies in three low-level operating system optimizations.

1. Mechanical Sympathy: Sequential I/O vs Random I/O

Modern operating systems and storage hardware are fundamentally optimized for sequential data access:

  • On spinning magnetic disks (HDDs), sequential writes achieve over 100 MB/s, whereas random writes crawl at under 1 MB/s due to mechanical seek times and rotational latency.
  • On solid-state drives (SSDs), random writes trigger continuous background garbage collection, write amplification, and block erasures, degrading throughput over time. Sequential writes bypass flash translation layer friction.

Because Kafka partitions are strictly append-only, all disk operations are sequential writes to the end of segment files, matching the raw physical bandwidth of the storage controllers.

2. Bypassing JVM Garbage Collection: Relying on the OS Page Cache

Traditional message brokers run caching layers inside the Java Virtual Machine (JVM) heap. This leads to two critical problems:

  1. Garbage Collection Pauses: Allocating tens of gigabytes of short-lived byte arrays in the JVM heap inevitably triggers Stop-The-World (STW) GC pauses that cause unpredictable latency spikes.
  2. Memory Duplication: An object cached in JVM heap is also cached by the OS kernel in the filesystem page cache, consuming twice the physical RAM.

Kafka does not maintain an internal in-memory object cache. Instead, it delegates all caching directly to the Linux OS Page Cache:

  • When a producer writes a batch, Kafka writes it directly to the OS page cache. The OS kernel flushes dirty pages to physical disk asynchronously in the background.
  • When a consumer reads the stream shortly after it was published (the common real-time streaming path), the data is read directly from physical RAM via the OS page cache without any physical disk read operation.
  • Restarting a Kafka broker does not flush the cache: because page cache resides in OS kernel memory, a JVM process restart retains a warm cache immediately.

3. Zero-Copy Network Transfer via sendfile(2)

In standard network socket programming, reading data from a file and transmitting it over a network socket requires four context switches and four memory copies between user space and kernel space.

Step Standard Network Read/Write Path Kafka Zero-Copy Path (sendfile)
Step 1 OS reads file data from disk to kernel page cache via DMA. OS reads file data from disk to kernel page cache via DMA.
Step 2 Kernel copies data from page cache into JVM user-space application memory (Context Switch: Kernel $\to$ User). Kernel directly transmits page cache data to network socket buffer via DMA (Zero User-Space Copy).
Step 3 JVM application copies data from user space back into kernel socket buffer (Context Switch: User $\to$ Kernel). Network interface card (NIC) reads data directly from kernel memory via DMA.
Step 4 OS transmits data from socket buffer to network card via DMA. Result: 2 context switches, 0 CPU data copies, 100% DMA transfer.

By leveraging the Linux sendfile(2) system call (exposed via Java's FileChannel.transferTo()), Kafka delivers data straight from the OS page cache to the network interface card without ever copying the payload into JVM application memory. The CPU never touches the payload bytes, eliminating CPU cache thrashing and achieving wire-speed networking.

7. Architectural Summary & Production Best Practices

Component / Concept Core Invariant Key Architectural Implication
Log Persistence Events are immutable and stored on disk. Enables non-destructive, decoupled multi-consumer reads and historical replay.
Partitions Unit of horizontal parallelism and physical disk mapping. Throughput scales linearly with partition count; order is strictly local to a partition.
Segments Partition logs are split into small, bounded files. Enables $O(1)$ retention expiration via file deletion without log rewriting.
Sparse Index Offset entries recorded every 4 KB. Allows fast $O(\log N)$ binary search in compact RAM-mapped memory before a micro linear scan.
Key Partitioning $\text{MurmurHash2}(\text{key}) \pmod P$. Guarantees that all events for a given entity land in the same partition in strict chronological order.
Zero-Copy sendfile(2) transfers page cache directly to NIC. Bypasses JVM heap, prevents GC pauses, and saturates 10/25/100 Gbps network cards.
Production Design Rules
  • Sizing Partitions: Choose partition count based on target throughput. Rule of thumb: a single partition can support roughly $10\text{ MB/s}$ write throughput and $20\text{ MB/s}$ read throughput. If your service requires $100\text{ MB/s}$ ingest, provision at least 10 partitions.
  • Preserving Ordering: Always provide a consistent business key (e.g., customer_id or order_id) for events that must be processed sequentially. Never dynamically alter topic partition counts without planning for re-hash divergence.
  • Tuning Index Interval: Keep index.interval.bytes at default (4 KB) for general workloads. Decreasing it increases index memory usage with marginal lookup gain; increasing it saves negligible RAM at the expense of longer sequential scans.
