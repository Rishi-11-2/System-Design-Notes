Apache Kafka Architecture Part 1 — Event-Driven Architecture & Storage Fundamentals

📁 Category: Streaming & Kafka
← Back to All Notes
📌 Event-Driven Architecture Fundamentals

Apache Kafka is a distributed event streaming platform designed for high-throughput, fault-tolerant ingestion and storage of event streams. This first installment covers Kafka's fundamental building blocks: the difference between Pub/Sub and Streaming, Producers, Topics, Partitions, Segment Files, Indexing, and how horizontal scalability is achieved through sequential append-only disk storage.

1. Introduction to Kafka

  • What is Kafka? A distributed, horizontally-scalable, fault-tolerant event streaming platform that enables applications to publish, store, and consume streams of records in real time.
  • Streaming Model vs Simple Pub/Sub: Traditional message queues (e.g., standard RabbitMQ or JMS) delete messages as soon as a consumer acknowledges receipt. Kafka uses an append-only commit log: events are persisted to disk for a configurable retention window (e.g., 7 days or indefinitely), allowing multiple independent consumers to read and replay events at their own pace.

  • Producer: Applications that create and publish events to Kafka topics. Producers decide which partition an event belongs to.
  • Consumer: Applications that subscribe to topics and process records. Consumers maintain their own position (offset) in each partition log.
  • Broker: A single Kafka server process. A collection of coordinated brokers forms a Kafka cluster.
  • Topic: A logical channel or category to which records are published (e.g., user-signups, payment-events).
  • Partition: The fundamental unit of scalability in Kafka. Topics are divided into one or more partitions distributed across different brokers.
  • Offset: A sequential integer ID assigned to each record as it is appended to a partition. Offsets are immutable and unique within a specific partition.

3. Partitions and Scalability

Partitions enable Kafka to achieve horizontal scalability and high throughput:

  • Parallelism: A single topic can handle gigabytes of data per second by splitting load across 50+ partitions hosted on different physical servers.
  • Ordering Guarantees: Kafka guarantees total ordering of records only within a single partition, NOT across the entire topic! If an application requires strict causal ordering (e.g., all balance updates for Account #1042 must execute sequentially), all events for Account #1042 must be mapped to the exact same partition.

4. Segments and Index Files

To prevent partition logs on disk from becoming massive monolithic files that are slow to manage and clean up, Kafka divides every partition into smaller Segment Files:

📂 Partition Storage Structure

Inside the broker filesystem, a partition directory contains paired log and index files:

  • 00000000000000000000.log — Contains the actual raw serialized message payloads.
  • 00000000000000000000.index — Maps message logical offsets to physical byte offsets in the log file ($O(\log N)$ binary search).
  • 00000000000000000000.timeindex — Maps timestamps to logical offsets for time-based seeking.

When the active segment reaches a size limit (default 1GB) or time threshold (default 7 days), Kafka rolls the segment: it closes the current segment file, marks it read-only, and opens a new active segment. This makes log retention and cleanup (deleting old segments or compaction) lightning-fast via simple filesystem file deletions.

5. How Producers Assign Partitions

When a producer publishes a record, Kafka chooses the target partition using one of three strategies:

  1. Key-Based Partitioning: If the producer provides a message key (e.g., userId), Kafka hashes the key using the Murmur2 algorithm: $$\text{partition} = \text{murmur2}(\text{key}) \pmod{\text{numPartitions}}$$ This guarantees that all messages sharing the same key always land on the identical partition in exact order!
  2. Round-Robin / Sticky Partitioner: If no key is provided, Kafka distributes messages evenly across available partitions. Modern Kafka clients use the Sticky Partitioner, which batches records destined for the same partition to reduce network RPCs.
  3. Custom Partitioner: Developers can implement custom routing logic based on geographic region, tenant priority, or payload attributes.
