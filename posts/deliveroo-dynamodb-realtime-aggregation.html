Deliveroo Real-Time DynamoDB Aggregations: Sharded Counters & Stream-Processed Sliding Windows

Calculating live restaurant kitchen loads and delivery zone capacity across thousands of restaurants in sub-5 milliseconds requires eliminating SQL COUNT(*) scans and DynamoDB hot partition write throttling. Discover how Deliveroo engineered real-time aggregations—combining sharded counters, bucket-tiled temporal windows, and DynamoDB Streams CDC with zero-cost TTL eviction.

1. The Logistics Dispatch Dilemma

In an on-demand food logistics marketplace like Deliveroo, matching algorithms make critical decisions every second:

  • Kitchen Throttling: If Restaurant $R$ received more than 20 orders in the last 15 minutes, temporarily increase estimated delivery time or pause new orders to prevent kitchen meltdowns.
  • Rider Balancing: How many active couriers are en route to Zone $Z$ within the trailing 10-minute window?
  • Dynamic Delivery Fees: Surge fees dynamically adjust based on live order volume vs. active courier supply.

Executing queries like SELECT COUNT(*) FROM orders WHERE restaurant_id = ? AND created_at >= NOW() - INTERVAL 15 MINUTE across millions of orders locks database tables, inflates database CPU to 100%, and results in 500ms+ latency spikes that bring down matching dispatch loops.

2. The Hot-Partition Write Ceiling in DynamoDB

Migrating to Amazon DynamoDB provides horizontal scalability, but introduces strict partition throughput boundaries:

DynamoDB strictly caps single-partition throughput at 1,000 Write Capacity Units (WCU) per second.

If 2,000 orders or status updates per second hit a single trending restaurant or high-density delivery zone using restaurant_id as the partition key, DynamoDB rejects mutations with ProvisionedThroughputExceededException, causing failed orders and dropped telemetry.

3. Sharded Counters Architecture

To bypass the 1,000 WCU partition limit, Deliveroo implements Sharded Counters:

┌────────────────────────────────────────────────────────────────────────┐ │ SHARDED COUNTER WRITE PATH │ ├────────────────────────────────────────────────────────────────────────┤ │ 1. New Order Placed for Restaurant R101 │ │ 2. Worker generates random integer: S = rand(0, M-1) (e.g., M = 10) │ │ 3. Atomic Increment in DynamoDB: │ │ UPDATE counters_table │ │ SET count = count + 1 │ │ WHERE PK = "R101#2026-01-16T19:30" AND SK = "shard#3" │ └────────────────────────────────────────────────────────────────────────┘ ┌────────────────────────────────────────────────────────────────────────┐ │ SHARDED COUNTER READ PATH │ ├────────────────────────────────────────────────────────────────────────┤ │ 1. Query all M shards for the time bucket: │ │ SELECT count FROM counters_table WHERE PK = "R101#2026-01-16T19:30" │ │ 2. Parallel batch fetch returns M items in < 4ms │ │ 3. Total Count = SUM(shard[0] + shard[1] + ... + shard[M-1]) │ └────────────────────────────────────────────────────────────────────────┘

By spreading writes across $M = 10$ independent physical partitions, maximum write throughput scales linearly to 10,000 WCU per second per restaurant, completely eliminating write throttling.

4. Bucket Tiling & Sliding Window Aggregations

Calculating rolling 15-minute windows without continuous re-computation is achieved through Bucket Tiling:

  • Discrete Time Slices: The timeline is divided into fixed 1-minute discrete buckets: $T_0, T_1, T_2, \dots, T_{14}$.
  • Rolling Window Sum: To compute the orders in the last 15 minutes, the application issues a single parallel batch read fetching the counts of the last 15 1-minute buckets and sums them in memory: $$\text{TotalOrders}_{15m} = \sum_{i=0}^{14} \text{BucketCount}(T_{\text{now} - i})$$
  • Sub-5ms Execution: Because each bucket is a tiny pre-computed integer record, reading 15 items by primary key completes in under 4ms.

5. DynamoDB Streams CDC Pipeline

Counters are updated asynchronously using event-driven Change Data Capture (CDC):

6. Zero-Cost TTL Expiration Mechanics

Generating millions of 1-minute bucket records daily would quickly bloat database storage costs and require expensive background deletion queries.

Deliveroo leverages DynamoDB's native Time-to-Live (TTL):

  • Every aggregate record is tagged with an attribute ttl_timestamp = unix_epoch(now + 2 hours).
  • DynamoDB's internal background sweep identifies expired records and purges them automatically from storage.
  • Zero Cost & Zero WCU Consumption: Native TTL deletions consume 0 Write Capacity Units and carry zero financial cost, keeping the aggregations table lean and high-performing indefinitely.

8. Key Architectural Takeaways

  • Shard Hot Keys to Scale Past Partition Limits: When write traffic to an individual entity exceeds 1,000 WCU/sec, randomize writes across $M$ sub-shards and sum them on read.
  • Tile Continuous Time into Discrete Buckets: Replace expensive sliding window range scans with discrete 1-minute bucket reads, summing the last $K$ buckets in memory in sub-5ms.
  • Decouple Aggregation from Transaction Paths: Use CDC streams (DynamoDB Streams / Debezium) to update counters asynchronously, keeping user checkout latency isolated from analytical processing.
  • Use Native TTLs for Automatic Data Pruning: Tag ephemeral temporal buckets with TTL timestamps to let cloud databases clean up expired state without paying for deletion write capacity.
