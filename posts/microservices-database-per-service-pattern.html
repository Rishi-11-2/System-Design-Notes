1. Database per Service Rationale & Domain Encapsulation

In a true microservices architecture, loose coupling is impossible if services share access to a single monolithic database. The Database per Service Pattern mandates that each microservice must privately and exclusively own its datastore. No external service is permitted to query, join, or mutate another service's tables directly.

Instead, all cross-service data access must occur strictly through well-defined, versioned public APIs (gRPC/REST) or asynchronous domain events.

The Encapsulation Invariant

Treating internal database schemas as private implementation details frees teams to optimize data structures, rewrite schemas, or migrate database engines without coordinating release trains with other teams.

2. Polyglot Persistence: Choosing the Right Engine

In a monolith, developers are forced to shoehorn every data access pattern into a single relational database (e.g. MySQL or PostgreSQL), whether storing graph relationships, time-series telemetry, or full-text documents.

Database per service unlocks Polyglot Persistence: selecting the ideal storage paradigm tailored to the specific query characteristics of each bounded context:

Relational (PostgreSQL / MySQL)

Use Cases: Ledger, Invoicing, Billing, User Accounts.
Strength: ACID compliance, multi-record foreign keys, structured consistency.

Document Store (MongoDB / DynamoDB)

Use Cases: Product Catalog, Order Snapshots.
Strength: Schemaless flexibility, hierarchical JSON nesting, linear horizontal partitioning.

Graph Database (Neo4j / Amazon Neptune)

Use Cases: Social Graph, Fraud Ring Detection, Recommendation Networks.
Strength: Index-free adjacency, recursive $N$-hop path traversals.

Search Engine & Cache (Elasticsearch / Redis)

Use Cases: Full-text autocomplete, low-latency session state, rate limiters.
Strength: Inverted indexes, sub-millisecond in-memory lookups.

4. Overcoming Distributed Joins: API Composition & CQRS

The primary engineering consequence of separating databases is the elimination of SQL JOIN operations. How do you render an Order Details page that requires Customer info, Order items, and Shipping tracking status?

1. API Composition Pattern

An API Gateway or Aggregator service invokes each microservice in parallel via RPC, parses the JSON responses, and executes an in-memory hash join. Simple to build, but bounded by tail latency.

2. CQRS Materialized Read Models

Command Query Responsibility Segregation (CQRS) subscribes to Kafka domain events and pre-joins data into an optimized, denormalized read-optimized view in Elasticsearch or MongoDB.

5. Event Sourcing & Change Data Capture (CDC)

To keep distributed databases synchronized without fragile dual-writes, production architectures use Change Data Capture (CDC). Engines like Debezium monitor the Postgres write-ahead log (WAL) or MySQL binlog and stream row-level change events to Apache Kafka.

In Event Sourcing, state changes are stored as an append-only sequence of immutable domain events (AccountCreated, MoneyDeposited, MoneyWithdrawn). Current state is reconstructed by replaying the log, providing full historical auditing and point-in-time recovery.

6. Consistency Models & Operational Trade-offs

Architecture Metric Monolithic Shared Database Database per Service
Transactional Consistency Immediate ACID Instant cross-table rollbacks. Eventual Consistency Managed via Sagas.
Schema Autonomy Zero; cross-team release coordination. Complete Deploy schema migrations independently.
Disaster Recovery Single point of failure; unified backup. Isolated backups; complex multi-db point-in-time recovery.

7. Production Engineering Checklist

  • Network Boundary Fencing: Put each database in a private subnet accessible only to its owning service pod.
  • Outbox + CDC for Sync: Prohibit dual-writing from application code; mandate Transactional Outbox + Debezium.
  • Zero Cross-DB Joins: Run automated CI queries to detect and block cross-database connection attempts.
  • Backup Alignment: Coordinate snapshot strategies across polyglot stores to support disaster recovery simulations.
