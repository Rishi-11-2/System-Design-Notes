📌 Primary Takeaway: Hardware Symbiosis Over Algorithmic Dogma

DragonflyDB is an ultra-high-throughput, drop-in replacement for Redis offering up to 25x total throughput. While Redis has historically implemented its critical Sorted Set (zset) using a pointer-heavy SkipList, DragonflyDB replaces SkipLists with an in-memory B+ Tree featuring fixed 256-byte leaf nodes. This architectural shift slashes structural metadata overhead from ~37 bytes down to ~3.2 bytes per entry (an 11x reduction), yielding a 40% reduction in memory consumption and a 500% (5x single-thread, 24x multi-thread) improvement in throughput by aligning perfectly with CPU L1/L2 cache line boundaries.

1. Executive Summary & The Core Dilemma

In distributed in-memory data systems, the Sorted Set is one of the most heavily exercised primitives. Historically, software engineers accepted the SkipList as the de facto standard implementation for in-memory sorted sets because of its conceptual simplicity and lock-free concurrent navigation properties.

However, modern computer hardware has evolved. CPU execution frequencies have reached physical limits, while memory access latencies have remained comparatively stagnant—a phenomenon known as the memory wall. In this hardware reality, pointer-heavy data structures that induce random heap indirection waste significant CPU clock cycles on memory pipeline stalls. DragonflyDB proves that by substituting SkipLists with an in-memory B+ Tree optimized for 64-byte CPU cache lines, an in-memory database can dramatically reduce both RAM footprint and execution latency simultaneously.

2. Redis Sorted Set Mechanics

2.1 Uniqueness & Score Ordering

The Redis Sorted Set (zset) is an essential data structure used across modern web-scale architectures for real-time leaderboards, priority scheduling queues, rate-limiting token buckets, and geographic proximity lookups. It provides two fundamental invariants:

  • Set Uniqueness: Every member string in the set must be unique. Inserting an existing member updates its score rather than creating a duplicate.
  • Score Ordering: Every member is paired with a 64-bit IEEE 754 floating-point score. All reads and range extractions (such as ZRANGEBYSCORE or ZREVRANK) retrieve elements strictly ordered by score. If two members share identical scores, they are sorted lexicographically by member byte string.

2.2 The Dual-Engine Threshold: Listpack vs. SkipList

Redis implements Sorted Sets using an internal dual-engine threshold controlled by the configuration parameter zset-max-listpack-entries (default 128) and zset-max-listpack-value (default 64 bytes):

  • Small Sets (≤ 128 elements): Redis encodes elements using a contiguous memory structure called a Listpack (which replaced the legacy ziplist in Redis 7.0). Members and scores are serialized consecutively into a single flat byte array. While updates require memory reallocation and $O(N)$ scanning, the absolute memory overhead is virtually zero, making Listpack ideal for small sets.
  • Large Sets (> 128 elements): When a Sorted Set exceeds 128 elements (or any member exceeds 64 bytes), Redis transitions the data structure into a dual-engine architecture:
    1. A Hash Table (dict): Maps member strings to their corresponding scores, providing $O(1)$ lookups for ZSCORE and member existence.
    2. A SkipList (zskiplist): Organizes the member-score tuples in sorted order, providing $O(\log N)$ insertions, deletions, rank calculations, and ordered range scans.

3. How SkipLists Work: The "Express Lane" Model

A SkipList is a probabilistic multi-level linked list originally designed by William Pugh in 1989. To avoid the $O(N)$ search penalty of standard linked lists, a SkipList builds successive "express lanes" on top of a base linked list:

  • Base Level ($L_0$): A standard doubly-linked list containing every element sorted in ascending score order.
  • Hierarchical Express Lanes ($L_1, L_2, \dots, L_k$): Upper levels contain a subset of nodes chosen probabilistically. In Redis, each node is assigned a random level using a geometric distribution where the probability of ascending to the next level is $p = 0.25$ (up to a maximum level of 32). On average, level $L_{i+1}$ contains roughly one-fourth (or one-half under $p = 0.5$) the elements of level $L_i$.
  • Traversal Execution: To search for a score, the algorithm starts at the header of the highest active level. It steps forward along the express lane as long as the next node's score is less than the target score. When the next node exceeds the target (or points to NULL), the pointer drops down one level to a denser lane and resumes forward scanning. This hierarchical skipping enables lookups, rank searches, and range iterations to complete in $O(\log N)$ time.

4. The Pointer Overhead Crisis in Redis SkipLists

4.1 C Source Anatomy of zskiplistNode

To identify the fundamental flaw of SkipLists in high-density in-memory stores, let us examine the actual C struct definition used inside the Redis engine (server.h):

server.h (Redis zskiplistNode Definition) 
typedef struct zskiplistNode {
    sds ele;                            /* 8 bytes: Member string pointer */
    double score;                       /* 8 bytes: 64-bit IEEE float score */
    struct zskiplistNode *backward;     /* 8 bytes: Reverse traversal pointer */
    struct zskiplistLevel {
        struct zskiplistNode *forward;  /* 8 bytes: Forward lane pointer */
        unsigned long span;             /* 8 bytes: Nodes spanned by this link */
    } level[];                          /* Flexible array member: 1 to 32 levels */
} zskiplistNode;

Let us analyze the bare minimum data payload versus the metadata tax:

  • Essential Payload: Storing a Sorted Set entry requires only the member string pointer (8 bytes) and the numeric score (8 bytes). Thus, the essential data payload is exactly $8 + 8 = \mathbf{16\text{ bytes}}$.
  • Structural Metadata Tax:
    • *backward pointer: 8 bytes.
    • *forward pointer per level: 8 bytes.
    • span integer per level: 8 bytes.
    • Each allocated level costs $8 + 8 = \mathbf{16\text{ bytes}}$.

4.2 The Empirical 37-Byte Metadata Tax

Because node levels are randomly generated up to level 32, every node allocates a variable-length level[] array on the heap. When measured in production across millions of active entries, the geometric distribution ($p = 0.25$) results in an average structural overhead of ~37 bytes per node.

Adding this structural metadata to the 16-byte payload yields:

$$\text{Total Memory Per Redis Entry} = 16\text{ bytes (payload)} + 37\text{ bytes (metadata)} \approx \mathbf{53\text{ bytes}}$$

This means that nearly 70% of the memory consumed by a Redis SkipList node is pure structural overhead dedicated solely to maintaining backward pointers, forward pointers, and level span counters!

5. DragonflyDB's Innovation: In-Memory B+ Tree

5.1 Architecture of 256-Byte Leaf Nodes

DragonflyDB fundamentally re-engineers Sorted Sets by ditching the SkipList entirely and introducing an in-memory B+ Tree:

  • Non-Binary High Branching Factor: Unlike binary search trees or SkipLists, a B+ Tree has a wide branching factor ($B \gg 2$, typically 7 to 15 for inner nodes). This ensures the tree remains exceptionally shallow—rarely exceeding 2 to 3 levels even when storing millions of items.
  • Separation of Routing & Data: Inner nodes store only routing keys and child pointers. All actual member-score payloads reside exclusively in the Leaf Nodes.
  • Fixed 256-Byte Contiguous Leaf Nodes: Instead of allocating individual heap objects for every entry, DragonflyDB allocates leaf nodes as uniform, contiguous 256-byte memory chunks.
  • 16 Entries Packed Per Leaf: At 16 bytes per entry (8B member pointer + 8B score), exactly 16 entries pack into a single 256-byte leaf node: $$\frac{256\text{ bytes per leaf}}{16\text{ bytes per entry}} = 16\text{ entries per leaf node}$$

6. The Mathematical Overhead Proof (1,000-Entry Model)

In his technical engineering dissection, Arpit Bhayani provides a rigorous mathematical derivation proving why DragonflyDB's B+ Tree achieves an 11x reduction in metadata overhead. Consider a production Sorted Set holding 1,000 entries:

Mathematical Step-by-Step Derivation
  1. Leaf Nodes Calculation: Storing 1,000 entries with 16 entries per leaf node requires: $$\text{Leaf Nodes} = \left\lceil \frac{1,000}{16} \right\rceil \approx 63 \text{ to } 67 \text{ leaf nodes}$$
  2. Inner Routing Nodes Calculation: With a branching factor between 7 and 15, routing across ~67 leaf nodes requires approximately 10 inner nodes.
  3. Total Nodes Allocated: $$\text{Total Nodes} = 67 \text{ (leaf)} + 10 \text{ (inner)} = \mathbf{77 \text{ total nodes}}$$
  4. Total Memory Footprint: $$\text{Total Memory} = 77 \text{ nodes} \times 256 \text{ bytes/node} = \mathbf{19,712 \text{ bytes}}$$
  5. Average Memory Consumed Per Entry: $$\text{Memory Per Entry} = \frac{19,712 \text{ bytes}}{1,000 \text{ entries}} = \mathbf{19.2 \text{ bytes per entry}}$$
  6. Net Structural Metadata Overhead: $$\text{Overhead} = 19.2 \text{ bytes (total)} - 16.0 \text{ bytes (essential payload)} = \mathbf{3.2 \text{ bytes per entry}}$$

Comparing the two data structures directly reveals a stark contrast:

Data Structure Essential Payload Structural Metadata Overhead Total Allocation Per Entry Relative Metadata Tax
Redis SkipList (zskiplist) 16.0 bytes ~37.0 bytes ~53.0 bytes 231% of payload
DragonflyDB B+ Tree 16.0 bytes ~3.2 bytes ~19.2 bytes 20% of payload (11.5x lower!)

7. Hardware Symbiosis: CPU Cache Lines vs. Pointer Chasing

Why does DragonflyDB's B+ Tree deliver a 500% (5x) throughput increase in addition to saving memory? The secret lies in hardware sympathy with modern CPU cache architectures:

  • The 64-Byte CPU Cache Line Invariant: Modern x86-64 and ARM processors do not fetch individual bytes from system RAM. Instead, they fetch data in fixed 64-byte chunks called cache lines. Fetching data from L1 cache takes ~1 nanosecond, while fetching from main memory (DRAM) takes 60 to 100 nanoseconds—two orders of magnitude slower.
  • The SkipList Pointer-Chasing Trap: In Redis, every zskiplistNode is allocated independently on the heap via jemalloc. These nodes are scattered across disparate virtual memory addresses. When traversing a SkipList across 10 levels, the CPU must dereference 10 separate pointers. Almost every pointer dereference misses the L1/L2/L3 cache, forcing the CPU execution pipeline to stall for hundreds of cycles waiting for DRAM fetches.
  • B+ Tree Cache Locality & SIMD Symbiosis: A DragonflyDB leaf node is exactly 256 bytes, which maps perfectly to exactly four 64-byte CPU cache lines ($4 \times 64 = 256\text{ bytes}$):
    • When the CPU accesses the start of a leaf node, hardware cache prefetchers automatically load the entire 256-byte chunk into L1/L2 cache.
    • Performing a binary search across the 16 elements inside the leaf node executes entirely within ultra-fast L1 cache registers with zero DRAM stalls.
    • Modern compilers can vectorize searches inside a 256-byte block using SIMD (AVX2 / NEON) comparison instructions, finding the target element in a fraction of a clock cycle.

8.2 Memory Consumption Scaling

Memory benchmarks validate the mathematical overhead derivations:

  • For sets ≤ 128 elements: Redis stores data using compact Listpacks, keeping memory consumption competitive with DragonflyDB.
  • For sets > 128 elements: The moment a Sorted Set crosses the 128-element threshold, Redis converts the set into a SkipList plus Hash Table. Memory consumption surges dramatically due to the ~37-byte metadata tax per entry. In contrast, DragonflyDB continues packing entries into 256-byte leaf nodes, achieving an overall ~40% memory saving on large-scale datasets.

9. First-Principles Engineering Takeaways

Core Systems Engineering Principles
  1. Big-O Notation Hides Constant Hardware Costs: Both SkipLists and B+ Trees share identical theoretical time complexities: $O(\log N)$ for lookups, insertions, and deletions. In production systems, however, Big-O tells only half the story. CPU cache miss latencies (60–100ns) dwarf ALU instruction execution times (0.3ns). A cache-conscious $O(\log_B N)$ tree consistently outperforms an $O(\log_2 N)$ pointer chain.
  2. Pointers Are Expensive on 64-Bit Hardware: Every pointer consumes 8 bytes of physical RAM. In an in-memory data store where record payloads are small (e.g. an 8-byte pointer and an 8-byte score), a data structure that requires multiple forward pointers, backward pointers, and span counters per node will spend more memory on structural metadata than on actual user data.
  3. Cache-Line Granular Allocations: By sizing leaf nodes to 256 bytes (an exact multiple of four 64-byte CPU cache lines), DragonflyDB guarantees that memory reads load full batches of contiguous records into processor cache, maximizing spatial and temporal locality.
  4. Modern In-Memory Architecture: DragonflyDB demonstrates that modernizing database internals requires rethinking foundational data structures from first principles to align with modern multi-core, cache-stratified server hardware.
