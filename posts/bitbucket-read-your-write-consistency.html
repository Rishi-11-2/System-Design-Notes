How Bitbucket Solved Read-Your-Writes Consistency & Cut Master DB Load by 50%

By Arpit Bhayani Dissection & Bitbucket Database Engineering • October 2026 • 15 min read

1. The Master Bottleneck & Replication Lag

At Bitbucket—Atlassian's source code management and CI/CD platform—the database tier is the foundational source of truth for millions of repositories, pull requests, code reviews, and permissions. Like most relational systems, Bitbucket is backed by a Primary-Replica (Master-Follower) PostgreSQL cluster.

In theory, read replicas provide horizontal scalability:

  • All state mutations (INSERT, UPDATE, DELETE) are handled exclusively by the single Primary (Master) node.
  • The Primary streams Write-Ahead Log (WAL) records asynchronously to multiple Read Replicas.
  • All read queries (SELECT) are routed to the replica fleet, offloading work from the primary.

However, in production reality, asynchronous replication lag (even just 50 to 200 milliseconds) causes devastating user experience bugs. To avoid these bugs, engineers often route all "critical" read queries back to the Primary database. Over time, the Primary becomes saturated with reads, causing CPU spikes, connection pool starvation, and database-wide slowdowns.

2. The Read-Your-Writes Consistency Anomaly

The core user-facing bug that prevented Bitbucket from using read replicas is known as the Read-Your-Writes Consistency Anomaly (or Read-After-Write Inconsistency): 

sequenceDiagram
    autonumber
    actor Dev as Developer
    participant Web as Bitbucket App Server
    participant Primary as PostgreSQL Primary
    participant Replica as PostgreSQL Read Replica (Lag = 150ms)

    Dev->>Web: 1. Submit Pull Request Comment ("LGTM, merging now")
    Web->>Primary: 2. INSERT INTO pr_comments (id, text, ...)
    Primary-->>Web: 3. Commit Successful (t = 0ms)
    Web-->>Dev: 4. HTTP 200 OK
    Note over Primary,Replica: WAL Streaming in flight... (150ms lag)
    Dev->>Web: 5. Page Auto-Refreshes / Fetches Comment List (t = 20ms)
    Web->>Replica: 6. SELECT * FROM pr_comments WHERE pr_id = 42
    Note over Replica: Replica has NOT replayed the comment yet!
    Replica-->>Web: 7. Returns empty list / missing comment
    Web-->>Dev: 8. Renders page without the comment!
    Note over Dev: Developer panics: "Did my comment post fail?!"

This anomaly completely undermines user trust. If a user merges a pull request, updates branch protection rules, or comments on an issue, and the UI immediately renders stale data, users resubmit forms, duplicate comments, or assume the platform dropped their data.

3. Why Naive Fixes (Sticky Routing & Sleeps) Fail

Before finding the optimal solution, teams frequently experiment with naive heuristics that break down at scale:

Heuristic Strategy How It Works Why It Fails in Production
Artificial Client Sleep Frontend waits 500ms before refreshing the view. Terrible user UX; fragile. During large batch writes, replication lag can spike to 2 seconds, still returning stale data.
Time-Based Sticky Routing After any write, force all reads from that user to hit Primary for $N$ seconds (e.g. 10s). Overloads the Primary! Active developers who commit code frequently end up having 100% of their reads pinned to the Primary, defeating replication offload.
Route Everything to Primary Primary handles all writes and all sensitive reads. Primary CPU hits 100% saturation; catastrophic database failure during peak traffic.

4. The LSN Solution: PostgreSQL WAL Mechanics

Bitbucket solved this elegantly by grounding routing in the physical mechanics of the PostgreSQL engine: Log Sequence Numbers (LSNs).

In PostgreSQL, every database modification appends a record to the Write-Ahead Log (WAL). The position in the WAL is represented as a monotonically increasing 64-bit integer called the Log Sequence Number (LSN) (e.g. 16/B374D848).

The Mathematical Invariant: Let $\text{LSN}_{\text{write}}$ be the WAL position generated when User $U$ commits a write on the Primary. Let $\text{LSN}_{\text{replay}}^{(R)}$ be the current WAL position successfully replayed by Read Replica $R$. $$\text{If } \text{LSN}_{\text{replay}}^{(R)} \ge \text{LSN}_{\text{write}} \implies \text{Replica } R \text{ is GUARANTEED to have User } U\text{'s write!}$$

If $\text{LSN}_{\text{replay}}^{(R)} \ge \text{LSN}_{\text{write}}$, the query can safely execute against Replica $R$ with 100% mathematical guarantee of read-your-writes consistency, without touching the Primary!

5. End-to-End Dynamic Replica Routing Architecture

Bitbucket implemented an intelligent proxy and session tracking middleware:

        USER[User Browser / Git Client]
    end

    subgraph "Application & Routing Layer"
        ROUTER[Smart Database Router]
        COOKIE[(Client Cookie / Token: last_written_lsn)]
    end

    subgraph "Database Cluster"
        PRI[(PostgreSQL Primary)]
        R1[(Read Replica 1)]
        R2[(Read Replica 2)]
        R3[(Read Replica 3)]
    end

    USER -->|1. Write Mutation| ROUTER
    ROUTER -->|2. Execute Write| PRI
    PRI -->|3. Return LSN: 16/B374D848| ROUTER
    ROUTER -->|4. Return Response + Set LSN Cookie| USER

    USER -->|5. Subsequent Read + Pass LSN Cookie| ROUTER
    ROUTER -->|6. Poll pg_last_wal_replay_lsn| R1 & R2 & R3
    ROUTER -->|7. Replica 2 has replayed >= LSN!| R2
    R2 -->|8. Fresh Data Returned| USER

PostgreSQL Queries Used Under the Hood:

1. On the Primary after committing a write transaction: 

SELECT pg_current_wal_lsn();
-- Returns e.g.: '0/15E8438'

2. On each Read Replica during connection health check / telemetry: 

SELECT pg_last_wal_replay_lsn();
-- Returns e.g.: '0/15E8500' (Replay position)

3. Fast comparison using PostgreSQL native diff: 

SELECT pg_wal_lsn_diff(pg_last_wal_replay_lsn(), '0/15E8438'::pg_lsn);
-- If result >= 0, replica is strictly synchronized with the user's write!

6. Handling Edge Cases, Lag Spikes & Fallbacks

What happens when a large bulk write stalls replication across all replicas?

  • Replica Selection: The router maintains real-time telemetry on the replay LSN of all replicas. It immediately selects a replica whose $\text{LSN}_{\text{replay}} \ge \text{LSN}_{\text{user}}$.
  • Micro-Wait / Catch-up: If all replicas lag by a few milliseconds, the router can optionally wait up to a configurable threshold (e.g. 50 ms) for the closest replica to catch up before falling back.
  • Graceful Fallback to Primary: If no replica catches up within the safety window (due to a network partition or heavy DDL lock), the router routes the query to the Primary database as a safe fallback.
  • Token Expiration: The user's LSN token is given a short TTL (e.g. 10 to 30 seconds). Once replication has undeniably surpassed that LSN everywhere, the token is discarded and the user resumes normal round-robin read balancing.

7. Production Impact: 50% Master Load Reduction

By implementing LSN-based read-your-writes routing, Bitbucket transformed its database capacity:

Architecture Metric Before (Heuristic / Primary Reads) After (LSN Replica Routing) System Impact
Primary DB Query Load 100% saturation during peak hours 50% reduction in query QPS Freed massive CPU headroom for write throughput
Read-Your-Writes Inconsistencies Frequent customer reports of "missing data" Zero reported consistency anomalies Mathematically guaranteed causal consistency
Replica Utilization Underutilized; rejected for sensitive reads Evenly loaded across read fleet Full return on investment for replica infrastructure
Database P99 Latency Spiked on primary connection contention Smooth, predictable sub-10ms response times Improved end-to-end user experience

8. First-Principles Summary & Design Lessons

  • Ground Routing in Storage Engine Primitives: Never guess replication state with arbitrary timers or thread sleeps. Databases already track write order with physical precision (Postgres LSNs, MySQL GTIDs, MongoDB cluster times).
  • Causal Consistency at Low Cost: Full serializability across distributed replicas is expensive, but Read-Your-Writes (Causal) consistency can be achieved almost for free by passing transaction progress tokens to clients.
  • Session-Scoped Tokens Preserve Scalability: Storing the user's latest write LSN in a lightweight client cookie or header prevents global state coordination, letting stateless routers make instant local decisions.
