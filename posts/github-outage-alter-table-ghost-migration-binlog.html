How an ALTER TABLE Caused a Massive GitHub Outage: gh-ost & Cascading Replica Collapse

Online schema migration on a multi-terabyte MySQL table triggered replication replay deadlocks, throwing database read replicas into crash-recovery loops and sparking a classic cascading pool failure.

1. Executive Summary & Outage Scope

On November 27, 2020, GitHub suffered a widespread outage affecting GitHub Actions, Codespaces, pull requests, Git SSH/HTTPS operations, and API queries. The incident originated during a routine online schema migration on a massive, business-critical MySQL table.

GitHub relies heavily on gh-ost (GitHub Online Schema Transformations), an open-source triggerless migration tool developed in-house to alter petabyte-scale tables without locking writers. During this migration, an atypical concurrency pattern produced an unhandled InnoDB deadlock inside the replication SQL applier thread on read replicas. This deadlock forced replica nodes into sudden crash-recovery states.

When the initial replicas rebooted, load balancers automatically redirected 100% of read traffic across the surviving nodes. The surviving replicas were immediately overwhelmed by traffic exceeding 150% of capacity, crashing sequentially in a textbook cascading failure that wiped out GitHub's database read tier.

2. Why ALTER TABLE is Lethal at Scale: The gh-ost Architecture

In a production relational database, executing a direct DDL statement such as: 

-- Dangerous in high-volume production!
ALTER TABLE pull_requests ADD COLUMN reviewer_state VARCHAR(32);

locks metadata and table pages, stalling all concurrent writes. Furthermore, in MySQL replication topologies, DDL statements replicate sequentially, causing massive replication lag across read replicas.

3. The Failure Mechanism: Deadlocks & Crash Recovery

gh-ost operates by acting as a fake MySQL replica: it connects to the primary, streams binlog events, and rewrites ongoing DML operations into the ghost table. Concurrently, it migrates existing rows in range-based chunks (e.g., WHERE id BETWEEN x AND y).

During the November 27 incident, a high rate of production concurrent updates clashed with the row-copy operations and binlog replay on the ghost table. While MySQL handles standard client deadlocks by rolling back one transaction, this specific condition triggered a severe bug inside the replication applier on the replicas:

The Replication Applier Crash Loop

When a replica's single-threaded SQL applier encounters an unhandled deadlock during multi-statement binlog transaction replay, MySQL marks the replication state corrupt and terminates the mysqld daemon to preserve data integrity. Upon automatic container/daemon restart, InnoDB enters Crash Recovery Mode—scanning redo logs and rolling back uncommitted transactions before opening network ports.

4. Mathematical Anatomy of Cascading Failure

To understand why the entire read tier collapsed, let us analyze the load distribution across a replica pool.

Suppose an active cluster has $N$ read replicas handling total query ingress $R_{\text{total}}$. Each replica handles a baseline load of:

$$L_{\text{baseline}} = \frac{R_{\text{total}}}{N}$$

Suppose each replica is provisioned with capacity $C_{\text{max}} = 1.25 \cdot L_{\text{baseline}}$ (a 25% safety headroom).

When $k$ replicas crash due to replication replay deadlocks, the proxy load balancer immediately drains the failing nodes and distributes the entire load across the remaining $(N - k)$ replicas:

$$L_{\text{remaining}} = \frac{R_{\text{total}}}{N - k} = L_{\text{baseline}} \cdot \left(\frac{N}{N - k}\right)$$

The condition for a self-propagating cascading failure is:

$$L_{\text{remaining}} > C_{\text{max}} \implies \frac{N}{N - k} > 1.25 \implies k > 0.2 N$$

If merely 20% of replicas crash, every surviving replica instantly experiences load exceeding its maximum provisioned capacity. In GitHub's case, with $N=3$ replicas per partition, a single replica crashing shifted load from $33\%$ to $50\%$ ($1.5\times$ overload), causing the second replica to exhaust connections and crash, leaving the final replica with $3.0\times$ traffic ($100\%$ of all load).

6. Architecture Solutions & Pool Segregation

GitHub implemented several major architectural remediations to prevent schema migrations from destabilizing user-facing reads:

1. Dedicated Migration Replicas

Schema migrations no longer run against production-facing read replicas. GitHub provisions dedicated, isolated replication targets for gh-ost to inspect and apply chunked writes, shielding user traffic pools.

2. Strict Pool Segregation

Production read traffic is strictly isolated from internal batch analytics, reporting services, and database backups. If an internal batch query triggers a crash, production traffic is completely unaffected.

3. Dynamic Throttling & Heartbeat Caps

gh-ost was updated with enhanced throttling: it monitors replication lag on all production replicas via a heartbeat table. If lag exceeds 1 second, migration chunks are paused immediately.

4. Adaptive Load Shedding in ProxySQL

When a replica fails, the proxy limits maximum load routed to surviving nodes rather than blindly forwarding 100% of traffic. Surplus queries are gracefully degraded or rejected at the edge with HTTP 429.

7. Production Engineering Checklist

  • Never run migrations directly on user-serving replicas: Direct online schema tools to dedicated replica nodes isolated from client traffic.
  • Cap load redistribution during node outages: Configure proxies to shed excess traffic rather than overloading surviving replicas beyond safe operating limits.
  • Throttle migrations on replica lag: Configure tools like gh-ost to throttle aggressively whenever replica lag exceeds sub-second thresholds.
  • Enforce pool segregation: Physically partition replica clusters between latency-sensitive customer traffic and batch analytics.
  • Simulate replica failover under peak load: Conduct chaos engineering drills where random replica nodes are killed while the cluster runs at peak traffic.
