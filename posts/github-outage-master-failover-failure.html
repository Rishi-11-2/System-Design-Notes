Dissecting GitHub Outage: When Automated MySQL Master Failover Fails

The catastrophic mechanics of promotion deadlocks: semi-sync fallbacks, errant transaction collisions, and why automated topology failover halted replication across entire clusters.

23 min read Arpit Bhayani Outage Dissections Verified 3-Page Companion PDF
📥 Download Technical PDF (3 Pages)
📌 Primary Failover Deadlock Abstract

Automated database failover is designed to turn a physical server crash into a brief, transparent promotion of a replica. However, when the automated failover process itself fails mid-execution, the resulting state is often far worse than a dead server: the database enters a failover deadlock. In this GitHub incident, an automated promotion occurred while semi-synchronous replication was degraded. The newly promoted master lacked transactions that existed on other surviving replicas, creating Errant Transactions in MySQL's Global Transaction Identifier (GTID) sets. When replicas refused to replicate from the new master, replication broke across the entire cluster, leaving the platform without an authoritative database.

1. The Promise and Peril of Automated Master Failover

In high-throughput MySQL architectures, automated master failover involves four coordinated steps:

  1. Crash Detection: Orchestrator confirms the primary master is dead via multi-probe consensus.
  2. Candidate Evaluation: Identify the healthiest replica with the most up-to-date binlog coordinates.
  3. Promotion: Set read_only = 0 on the candidate and execute promotion hooks.
  4. Replica Repointing: Repoint all other replicas in the cluster to replicate from the newly promoted master.

The entire operation hinges on a fundamental assumption: the promoted candidate must be a superset of all committed data in the cluster. If this invariant fails, catastrophic replication deadlocks occur.

2. The Catch: Semi-Synchronous Replication Fallbacks

To prevent data loss, GitHub used MySQL Semi-Synchronous Replication. Under semi-sync, the master waits for at least one replica to write each transaction to its relay log before returning success to the client:

⚠️ The Silent Killer: rpl_semi_sync_master_timeout

By default in standard MySQL configurations, if no replica acknowledges a transaction within rpl_semi_sync_master_timeout (e.g. 1,000ms), MySQL silently falls back to asynchronous replication to prevent writes from blocking. During this incident, a transient network hiccup caused semi-sync to time out. The master continued committing transactions asynchronously. Moments later, the master crashed. The replica selected for promotion had not received those asynchronous transactions!

3. The Errant Transaction Nightmare

In MySQL GTID replication, an Errant Transaction is a transaction executed on a replica that never existed on the master. When Orchestrator attempted to repoint Replica C to Promoted Master B, MySQL compared their GTID sets:

$$\text{Master B GTID Set} = \{ 1 \dots 100 \}$$ $$\text{Replica C GTID Set} = \{ 1 \dots 103 \}$$

Because Replica C contained transactions $101, 102, 103$ which Master B did not possess, Replica C immediately aborted replication with:

Last_IO_Error: Got fatal error 1236 from master when reading data from binary log: 
'The slave is connecting using a GTID that is not known to the master'

Every surviving replica in the cluster halted. The cluster was now completely fractured: one master accepting writes, but zero replicas receiving updates, causing read replicas to lag indefinitely and database monitoring to light up in red.

4. Surgical Remediation: Errant GTID Injection

Resolving this deadlock required database administrators to execute manual, low-level binary log surgical repairs:

  1. Isolate Errant Transactions: Run gtid_subtract(Replica_GTID, Master_GTID) to identify the exact missing transactions ($101, 102, 103$).
  2. GTID Injection (Empty Transaction Forging): On Promoted Master B, inject empty placeholder transactions corresponding to the errant transaction IDs: 
    -- Inject empty placeholder transaction on Master B to satisfy GTID set
SET GTID_NEXT = '3E11FA47-71CA-11E1-9E33-C80AA9429562:101';
BEGIN; COMMIT;
SET GTID_NEXT = '3E11FA47-71CA-11E1-9E33-C80AA9429562:102';
BEGIN; COMMIT;
SET GTID_NEXT = '3E11FA47-71CA-11E1-9E33-C80AA9429562:103';
BEGIN; COMMIT;
SET GTID_NEXT = 'AUTOMATIC';
  3. Resume Replication: Issue START SLAVE on Replica C. Because Master B now contains matching GTID entries in its history, Replica C accepts Master B as valid and replication resumes.

5. Hardening Automated Failovers Against Deadlock

To eliminate promotion deadlocks permanently, modern production architectures implement three foundational safeguards:

1. Strict Semi-Sync Without Fallback:
   └── Set rpl_semi_sync_master_timeout = 1000000000 (effectively infinite).
   └── Set rpl_semi_sync_master_wait_no_slave = 1.
   └── If no replica confirms write receipt, writes BLOCK rather than silently
       falling back to asynchronous lossy mode.

2. Enforce Orchestrator Candidate Preference Rules:
   └── Orchestrator must query ALL surviving replicas and ONLY promote the node
       with the strict mathematical maximum GTID set.
   └── If the most advanced replica is not eligible (e.g. marked non-candidate),
       Orchestrator must inject errant transactions automatically before repointing.

3. Raft/Paxos-Based Replication (e.g. Group Replication / Raft Engines):
   └── Transition from classic master-replica to consensus replication (MySQL Group Replication,
       Vitess, or TiDB). Quorums prevent errant transactions by construction.

6. Systems Engineering Takeaways

  1. A Silent Fallback is an Outage in Disguise: Semi-sync replication that silently degrades to async on timeout gives engineers a false sense of security. You believe you have zero RPO (Recovery Point Objective), but the moment a network blip occurs, you are completely vulnerable to data loss and errant transactions.
  2. GTID Guarantees Consistency at the Cost of Liveness: GTID prevents data divergence by refusing to replicate from masters that lack history. It prioritizes consistency over availability. Automated failover systems must be equipped to reconcile GTID gaps automatically.
  3. Test Failed Failovers in Production: Don't just test happy-path failovers. Inject packet loss to trigger semi-sync degradation, kill the master mid-flight, and verify whether your failover automation deadlocks or completes cleanly.
