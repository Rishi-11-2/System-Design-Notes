1. Roy Fielding's REST Architectural Style: The 6 Constraints

Representational State Transfer (REST) was formulated in Roy Fielding's seminal 2000 doctoral dissertation. REST is not a protocol, standard, or software library; it is an architectural style defined by six foundational constraints:

1. Client-Server Separation

Separates user interface concerns (clients) from data storage and business logic (servers), enabling independent component evolution.

2. Statelessness

Every client request must contain all necessary authentication, state, and context. The server stores zero session state between calls.

3. Cacheability

Responses must explicitly designate themselves as cacheable or non-cacheable to prevent stale data reuse and eliminate redundant server load.

4. Uniform Interface

The core differentiator: resources are identified by URIs, manipulated through representations, and self-descriptive.

5. Layered System

Clients cannot know whether they connect directly to the origin server or via intermediate proxies, CDNs, or load balancers.

6. Code on Demand (Optional)

Servers can temporarily extend client functionality by transmitting executable code (e.g. JavaScript or WebAssembly).

2. HTTP Verbs: Safe & Idempotent Semantics

The power of REST emerges from aligning domain resources with HTTP protocol semantics:

HTTP Verb Domain Purpose Safe? (Read-Only) Idempotent? ($f(f(x)) = f(x)$) Success Status
GET Read resource representation YES YES 200 OK
POST Create new subordinate resource NO NO 201 Created
PUT Replace entire resource state NO YES 200 OK / 204 No Content
PATCH Partial resource mutation NO Conditional 200 OK
DELETE Remove resource NO YES 200 OK / 204 No Content

4. The HTTP Tooling Synergy: Caching & Proxies

The immense popularity of REST is not solely due to elegance; it is driven by the massive global ecosystem of HTTP-aware infrastructure:

  • Edge CDN Caching: Akamai, Cloudflare, and Fastly cache HTTP GET responses automatically using Cache-Control: public, max-age=3600 and ETag entity tags. Millions of read requests can be satisfied without hitting backend origin servers.
  • Universal Tooling: Every programming language, browser, debug proxy (Wireshark, Charles), and load balancer natively understands HTTP/1.1 and HTTP/2 headers.

5. Downsides of REST in Microservices: The Microservice Tax

While unmatched for public-facing edge APIs, REST exhibits serious drawbacks for internal east-west microservice communication:

1. Over-fetching & Under-fetching

Clients either receive huge unwanted payloads (over-fetching 60 fields when only 2 are needed) or must make 5 sequential roundtrips to assemble a view (under-fetching).

2. Text-Based Serialization Tax

JSON serialization consumes up to 40% of microservice CPU cycles at high throughput, compared to zero-copy binary protocols like FlatBuffers or Protobuf.

6. Architectural Decision Matrix: REST vs. gRPC

Architecture Boundary REST (JSON over HTTP) gRPC (Protobuf over HTTP/2)
North-South (Edge / Mobile) Optimal Universal client support, CDN caching, browser native. Requires gRPC-Web proxy; difficult debugging.
East-West (Internal Mesh) High JSON parsing overhead, loose typing, latency. Optimal High throughput, strict proto typing, streaming.

7. Production Engineering Checklist

  • RFC 7807 Problem Details: Standardize HTTP error responses using application/problem+json with type, title, status, and detail.
  • ETag Conditional Updates: Prevent lost updates on concurrent PUT/PATCH calls using If-Match headers.
  • Idempotency Keys on POST: Protect non-idempotent order and payment endpoints against duplicate transmissions.
  • OpenAPI Specification (OAS 3.0): Maintain automated contract schemas to generate client SDKs and mock tests.
