Scaling Discord's Data Platform to Petabytes: ScyllaDB, BigQuery & Real-Time Kafka Pipelines

Storing trillions of chat messages and processing hundreds of gigabytes per second of live event telemetry requires extreme architectural discipline. Discover how Discord scaled its data platform from MongoDB to Apache Cassandra, and ultimately to ScyllaDB in C++, integrated with real-time Kafka pipelines and BigQuery analytical data lakes.

1. Trillions of Messages: The Discord Scale

Discord supports hundreds of millions of monthly active users participating in massive communities (guilds) with over 500,000 concurrent members. Every text channel, voice state update, reaction emoji, and direct message generates continuous persistent data:

  • Message Scale: Over trillions of messages stored across thousands of database nodes.
  • Traffic Profile: High write-throughput with read bursts: when an active user opens a channel, the application requests the last 50 messages, followed by paginated scrolling into history.
  • Latency SLA: Sub-15ms p99 read latencies on recent messages to guarantee smooth real-time conversational user experiences.

2. The Cassandra GC & Compaction Wall

In its early days, Discord migrated from MongoDB to Apache Cassandra. Cassandra's LSM-tree architecture handled high write volumes effectively. However, as dataset size surged into hundreds of terabytes, Cassandra hit severe operational bottlenecks:

  • JVM Garbage Collection Pauses: Java heap allocations from reading large partitions caused stop-the-world GC pauses of up to 2–5 seconds, triggering timeout storms across gateway connections.
  • Compaction Stalls: Cassandra's background LSM compactions competed fiercely with live client reads for NVMe I/O and CPU cores, degrading p99 read latency past 1,000ms.
  • Hot Partitions: High-volume channels (e.g., general chat in mega-servers) created massive partitions spanning gigabytes, overwhelming individual Cassandra nodes.

3. Migrating to ScyllaDB: The C++ Seastar Engine

To permanently eliminate JVM GC pauses, Discord migrated its core message storage cluster to ScyllaDB—a ground-up C++ reimplementation of the Cassandra protocol built on the Seastar asynchronous framework:

┌────────────────────────────────────────────────────────────────────────┐ │ SCYLLADB SHARED-NOTHING THREAD-PER-CORE │ ├────────────────────────────────────────────────────────────────────────┤ │ • CPU CORE 0 ──► Thread 0 (Owns 1/N of memory, NIC queue, & NVMe I/O) │ │ • CPU CORE 1 ──► Thread 1 (Owns 1/N of memory, NIC queue, & NVMe I/O) │ │ • CPU CORE 2 ──► Thread 2 (Owns 1/N of memory, NIC queue, & NVMe I/O) │ │ • CPU CORE K ──► Thread K (Owns 1/N of memory, NIC queue, & NVMe I/O) │ ├────────────────────────────────────────────────────────────────────────┤ │ ZERO LOCKING CONTENTION • ZERO JVM GARBAGE COLLECTION • KERNEL-BYPASS │ └────────────────────────────────────────────────────────────────────────┘

By adopting a shared-nothing, thread-per-core model, ScyllaDB locks each operating system thread to a dedicated physical CPU core with its own local memory arena. Cross-thread mutex contention is eliminated, reducing p99 message read latency from over 1,000ms down to under 15ms across trillions of rows.

4. Message Partitioning & Time-Window Bucketing

To prevent individual channel partitions from expanding infinitely, Discord implemented an intelligent Time-Window Bucketing Scheme: 

CREATE TABLE messages (
    channel_id bigint,
    bucket int,
    message_id bigint,
    author_id bigint,
    content text,
    PRIMARY KEY ((channel_id, bucket), message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);
  • Compound Partition Key: (channel_id, bucket). Each bucket holds approximately 10 days of messages.
  • Clustering Key: message_id DESC. Because Discord uses Twitter Snowflake IDs (where the highest bits encode the creation timestamp), sorting by message_id DESC returns the latest messages with sequential disk I/O.
  • Bounded Partition Sizes: Even for ultra-active channels with millions of messages, each partition is capped at roughly 100MB, eliminating Cassandra/ScyllaDB wide-partition compaction stalls.

5. Real-Time Event Streaming with Kafka

Beyond chat messages, user actions generate hundreds of gigabytes per second of raw telemetry. Discord leverages Apache Kafka as its unified event backbone:

[ Gateway Nodes / WebSockets ] ──► [ Kafka Cluster (Thousands of Partitions) ] │ ┌──────────────────────────────────────┼──────────────────────────────┐ ▼ ▼ ▼ [ ScyllaDB Message Store ] [ Real-Time Trust & Safety ] [ Cloud Storage Data Lake ] (Live Chat Persistence) (Flink / Rust Stream ML) (Secor / GCS Parquet)

6. GCS & BigQuery Columnar Data Lake

For historical analytical queries, business intelligence, and product analytics, Discord decouples storage from compute:

  • Secor Kafka Sink: Streams raw Kafka events directly to Google Cloud Storage (GCS) in partitioned Snappy-compressed Parquet files.
  • BigQuery External Tables: Data scientists query petabytes of event history in BigQuery without putting analytical query loads on the transactional ScyllaDB cluster.
  • Apache Airflow Orchestration: Nightly batch pipelines compute daily active users (DAU), voice channel duration metrics, and retention cohorts.

7. Real-Time Trust & Safety ML Pipelines

With millions of public communities, detecting spam raids, malicious phishing links, and CSAM content in real time is vital:

  • Stateful Stream Processing: Apache Flink and custom Rust microservices tail Kafka topics, maintaining rolling window counters of messages sent per second per user.
  • Nearline Classification: High-risk messages are routed through machine learning classifiers for text sentiment, image perceptual hashes, and link reputation before reaching guild members.

8. Key Architectural Takeaways

  • Thread-Per-Core Replaces JVM GC at Scale: In ultra-high-throughput systems, Java Garbage Collection becomes an unpredictable operational liability. Shared-nothing architectures like ScyllaDB deliver deterministic sub-15ms p99 latencies.
  • Bucket Partitions to Prevent Unbounded Growth: Never allow partition keys to accumulate data forever. Slicing partitions by composite keys (entity_id, time_bucket) caps shard size and guarantees efficient compactions.
  • Decouple Real-Time Serving from Analytics: Write live transactions to high-speed KV/NoSQL databases, stream events to Kafka, and sink them to columnar object storage (Parquet + BigQuery) for analytical workloads.
  • Snowflake IDs Provide Free Temporal Ordering: Embedding timestamps into 64-bit ID generation primitives eliminates the need for secondary indexing on creation dates.
