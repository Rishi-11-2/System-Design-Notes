How GitHub Sharded Their Databases Without Downtime and Broke Their Monolith

By Arpit Bhayani Dissection & GitHub Database Infrastructure Team • October 2026 • 16 min read

1. The Monolith: Scaling `mysql1` to 950K QPS

For over a decade, GitHub's flagship web application—a massive monolithic Ruby on Rails codebase—was backed by a single primary MySQL database cluster affectionately named mysql1. As GitHub grew to support over 100 million developers, 330+ million repositories, and millions of pull requests, the mysql1 cluster was subjected to extreme operational demands, handling upwards of 950,000 queries per second (QPS) at peak.

To sustain this traffic, GitHub exhausted conventional vertical and read-replica scaling techniques:

  • Migrating to colossal bare-metal servers equipped with 128 physical CPU cores, 2 TB of RAM, and RAID-0 arrays of NVMe PCIe SSDs.
  • Deploying dozens of read replicas across multiple data centers.
  • Placing ProxySQL middleware layers to multiplex client connections and split read queries.
  • Implementing Memcached and Redis caches to absorb repeated reads.

2. The Breaking Point: Noisy Neighbors & Blast Radius

Despite extreme hardware, a fundamental architectural bottleneck remained: the single shared database cluster created an unmanageable blast radius and severe "noisy neighbor" contention.

The Shared Fate Problem: In mysql1, tables for completely unrelated business capabilities lived inside the same schema:
  • repositories, pull_requests, and issues (Core Collaboration)
  • gists and gist_comments (Code Snippets)
  • users, public_keys, and gpg_keys (Authentication & Identity)
  • audit_log_entries and notifications (High-volume Activity Streams)
If a developer triggered an expensive query on Gists or an automated bot generated millions of notifications, the resulting lock contention, buffer pool churn, and replication lag degraded critical Git push/pull operations and core developer workflows. A single incident in an auxiliary feature degraded the entire platform.

3. Phase 1: Virtual Partitioning via Schema Domains

Physical database sharding without downtime is notoriously risky. If you attempt to split tables across physical servers while your application code continues to execute relational JOIN operations and cross-table transactions, the application will immediately crash with syntax errors or distributed integrity violations.

GitHub devised a rigorous two-phase strategy:

  1. Phase 1: Virtual Partitioning (Logical Isolation) — Decouple tables and queries in the application layer without moving a single byte of data.
  2. Phase 2: Physical Partitioning (Zero-Downtime Migration) — Move isolated table clusters to dedicated MySQL hardware using GTIDs and ProxySQL routing.

GitHub formalized table groupings in declarative configuration files (db/schema-domains.yml). A Schema Domain defined a cohesive cluster of tables that belonged together functionally and could be co-located indefinitely.

4. Query & Transaction Linters in CI

Defining schema domains in YAML meant nothing unless developers were prevented from writing queries that breached domain boundaries. GitHub built custom AST (Abstract Syntax Tree) static and dynamic linters directly into their test suites and CI pipelines:

1. The Query Linter (Detecting Cross-Domain Joins)

The query linter intercepted every SQL query generated by ActiveRecord. If a query attempted a SQL JOIN or subquery between tables in different schema domains, the build failed immediately: 

-- VIOLATION: Cross-Domain Join between Repositories Domain and Users Domain!
SELECT repos.name, users.login 
FROM repositories repos 
JOIN users ON repos.owner_id = users.id 
WHERE repos.id = 42;
-- Linter Error: Query references multiple schema domains: [:repositories, :users]

Application-Level Refactoring: Engineers refactored queries to execute two targeted point queries and perform the join in application memory: 

# Clean Architecture: Multi-query application-level hydration
repo = Repository.find(42)              # Queries :repositories domain cluster
user = User.find(repo.owner_id)         # Queries :users domain cluster

Surprisingly, GitHub engineers discovered that eliminating multi-table joins frequently improved query performance. Simpler queries made significantly better use of primary key indexes and allowed aggressive caching at the domain level.

2. The Transaction Linter (Detecting Cross-Domain 2PC)

Similarly, the transaction linter asserted that a database transaction (ActiveRecord::Base.transaction) never issued write mutations across multiple schema domains. This guaranteed that when domains were moved to physical clusters, the system would not require distributed Two-Phase Commit (2PC) protocols.

5. Phase 2: Zero-Downtime Physical Partitioning

Once all cross-domain joins and cross-domain transactions were completely eliminated (verified by 100% CI compliance and production telemetry), GitHub proceeded to physical partitioning.

  1. Snapshot Bootstrapping: A complete snapshot of mysql1 was taken using Percona XtraBackup and restored onto the new dedicated cluster hardware (e.g., mysql-gists).
  2. Catch-Up Replication via GTIDs: The new cluster connected to mysql1 as a read replica, replaying continuous binary logs using MySQL Global Transaction Identifiers (GTIDs) until replication lag dropped to zero.
  3. Shadow Verification: Read queries for the isolated domain were mirrored through ProxySQL to both the old and new clusters. Automated inspectors validated that responses and row checksums matched exactly.

6. Traffic Cutover Mechanics with ProxySQL & GTIDs

The cutover procedure executed in under 100 milliseconds with zero human-perceivable downtime:

  • Write Quiescence: The application layer or ProxySQL briefly paused write queries for the specific schema domain by holding incoming connections in the proxy buffer (typically for < 50 ms).
  • Catch-up Catchment: The cutover orchestrator ensured the target cluster had replayed all in-flight GTIDs from mysql1.
  • Routing Rule Swap: ProxySQL dynamic runtime rules were updated to route all read and write traffic for the domain's tables directly to the new cluster.
  • Connection Release: Buffered write queries were released to the new primary.
  • Tear-Down: Once the new cluster was proven stable, the migrated tables on mysql1 were placed in read-only mode and eventually dropped using gh-ost.

7. Production Impact & 50% Load Reduction

The functional sharding of mysql1 into distinct physical domain clusters delivered immediate, transformative improvements across GitHub's infrastructure:

Metric Before Sharding (Monolith) After Schema Domain Sharding Architectural Impact
Primary DB Load Near 100% CPU & I/O saturation at peak 50% reduction in CPU & disk I/O Restored massive operational headroom to core database
Incident Blast Radius Global: Outage in one table affected all services Isolated: Blast radius confined strictly to domain A spike in Gists or Notifications cannot degrade Git push/pull
Replication Lag Frequent replication stalls due to large batch writes Sub-millisecond GTID replication across all clusters Completely eliminated read-your-write replication anomalies

8. First-Principles Summary & Design Lessons

  • Virtual Partitioning Must Precede Physical Migration: Never attempt to move data physically until logical boundaries are enforced in application code. Linters in CI are far more reliable than architectural guidelines.
  • Application Joins Beat Distributed SQL: Deconstructing complex relational joins into targeted point queries hydrated in application memory eliminates cross-database lock contention and enables independent cluster scaling.
  • Proxy-Based Dynamic Cutovers: Layering intelligent connection proxies (ProxySQL, Envoy, Vitess) allows database administrators to pause, buffer, and re-route traffic dynamically with sub-100ms cutovers.
  • Stepwise Sharding Towards Horizontal Scale: Functional schema domain partitioning is the essential prerequisite that prepares a monolithic codebase for subsequent horizontal horizontal sharding (e.g., using Vitess vindexes).
