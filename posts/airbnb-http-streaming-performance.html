Everything About HTTP Streaming & How Airbnb Leverages It in Production

By Arpit Bhayani Dissection & Airbnb Performance Engineering • October 2026 • 15 min read

1. The Flaw in the Buffered "Cup" Model

For decades, the standard mental model for HTTP web servers has been the Buffered Response Model:

  • A client makes an HTTP GET /rooms/12345 request.
  • The application server (Node.js, Ruby on Rails, Django, Go) initializes an empty memory buffer—like a cup.
  • The server executes multiple database queries, queries microservices for pricing and user reviews, computes recommendation models, renders the HTML template, and fills the cup.
  • Once the entire HTML page is 100% assembled, the server calculates the Content-Length header, flushes the entire response buffer down the TCP socket, and closes the transmission.
The Waste of Client Idle Time: While the backend server is busy spending $400\text{ ms}$ querying databases and computing prices, the user's high-speed broadband connection and browser CPU sit completely idle. The browser has zero work to do because not a single byte has crossed the wire!

2. The Network Waterfall Bottleneck

The true cost of the buffered model is the compounding Network Waterfall: 

gantt
    title Traditional Buffered Response Waterfall (Sequential Delay)
    dateFormat X
    axisFormat %s ms

    section Backend Server
    DB & Business Logic (Wait)    :crit, 0, 400
    Flush Full HTML Payload       :done, 400, 450

    section Browser Client
    Idle Waiting for First Byte   :active, 0, 400
    Parse HTML              :done, 450, 470
    Fetch External CSS & JS       :crit, 470, 750
    First Contentful Paint (FCP)  :milestone, 750, 750

Browsers cannot begin downloading critical CSS stylesheets, JavaScript bundles, or web fonts referenced in the HTML <head> until they receive the opening bytes of the document. Under the buffered model, asset discovery is artificially held hostage until the slowest backend database query completes!

3. HTTP Streaming: Chunked Wire Protocols

HTTP Streaming fundamentally inverts this model. Instead of waiting for the entire response to be generated, the server streams data in discrete chunks as soon as parts become available.

The HTTP/1.1 Transfer-Encoding: chunked Wire Format

In HTTP/1.1, streaming is enabled by omitting Content-Length and setting: 

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Transfer-Encoding: chunked
Each chunk is transmitted as a hexadecimal size string, followed by CRLF (\r\n), the raw byte payload, and another CRLF. The stream terminates with a 0-byte chunk: 

1F\r\n
<!DOCTYPE html><html><head>...\r\n
4A\r\n
<body><div id="listings">... [Chunk 2 Payload] ...</div>\r\n
0\r\n
\r\n

In HTTP/2 and HTTP/3, chunking is built directly into the transport layer as native multiplexed DATA frames with an END_STREAM flag on the final frame.

4. Airbnb's Solution: The "Early Flush" Architecture

Airbnb receives massive global traffic on complex search and listing pages that pull data from dozens of internal microservices (pricing engines, review aggregators, host calendars, recommendation systems).

To eliminate network waterfalls, Airbnb re-engineered its rendering pipeline around Early Flush: 

flowchart TD
    REQ[Client HTTP Request Arrives at t0] --> FORK{Fork Execution Pipeline}

    subgraph "Phase 1: Immediate Early Flush (t = 15ms)"
        FORK --> HEAD[Render Static  + Preloads]
        HEAD --> FLUSH1[FLUSH CHUNK 1 IMMEDIATELY TO WIRE]
    end

    subgraph "Phase 2: Parallel Backend Execution (t = 15ms to 350ms)"
        FORK --> SVC1[Query Pricing Service]
        FORK --> SVC2[Query Listing DB]
        FORK --> SVC3[Query Review Microservice]
        SVC1 & SVC2 & SVC3 --> ASSEMBLE[Assemble Main Page Body]
    end

    FLUSH1 --> WIRE[(High-Speed Wire Transfer)]
    WIRE --> BROWSER[Browser Preload Scanner starts fetching CSS/JS/Fonts!]

    ASSEMBLE --> FLUSH2[FLUSH CHUNK 2 (Page Body) TO WIRE]
    FLUSH2 --> FINISH[FLUSH CHUNK 3 (Closing )]
The Early Flush Concept: Within 15 to 20 milliseconds of receiving a request, the server renders and immediately flushes the entire HTML <head> block containing:
  • Meta tags, page titles, and viewport configurations.
  • Critical CSS stylesheet links (<link rel="stylesheet" ...>).
  • JavaScript bundle script tags (<script src="..." defer>).
  • Preload hints for custom fonts and hero image assets (<link rel="preload" ...>).

5. Parallel Pipeline: Browser Preload Scanner

By flushing the <head> early, Airbnb triggers the browser's Preload Scanner while the backend server is still waiting on slow database queries: 

gantt
    title Airbnb Early Flush Pipeline (Total Parallelism)
    dateFormat X
    axisFormat %s ms

    section Backend Server
    Render & Flush  Chunk 1 :done, 0, 20
    Query DBs, Pricing & Reviews   :crit, 20, 350
    Render & Flush Body Chunk 2    :done, 350, 380

    section Browser Client
    Receive Chunk 1               :done, 25, 30
    Download Critical CSS & JS    :crit, 30, 250
    Receive Chunk 2 (Body)        :done, 380, 400
    Immediate Paint (Assets ready!):milestone, 400, 400

Notice how the $220\text{ ms}$ external asset download is completely overlapped with the backend database query time! When Chunk 2 (the page body) arrives at millisecond 380, the browser has already finished downloading the CSS stylesheets and scripts. The browser can construct the render tree and paint the screen instantly.

7. Production Pitfalls: Gzip Buffering & CDNs

Implementing HTTP streaming in large-scale architectures introduces subtle infrastructural pitfalls that must be mitigated:

1. Reverse Proxy & CDN Buffering Traps

Intermediate proxies (Nginx, HAProxy) and CDNs (Cloudflare, Akamai) often default to buffering responses to apply Gzip/Brotli compression or analyze response sizes. If Nginx buffers Chunk 1, the early flush is swallowed and held until the body completes!

The Nginx Fix: Disable proxy buffering for streaming endpoints by sending the header: 
X-Accel-Buffering: no
In Nginx configurations, ensure proxy_buffering off; or tune proxy_buffer_size.

2. Gzip Flush Boundaries

Compression algorithms (zlib) buffer data in memory blocks (typically 4 KB to 32 KB) to find compression dictionaries. If Chunk 1 is only 1 KB, zlib will refuse to emit bytes! Servers must explicitly invoke Z_SYNC_FLUSH after flushing Chunk 1 to force the compression engine to emit the compressed bytes immediately.

8. First-Principles Summary & Design Lessons

  • Overlap Network I/O with Compute I/O: Never allow the client's network connection to sit idle while the backend computes. Flushing critical headers early enables the browser's preload scanner to fetch assets in parallel with backend database queries.
  • FCP Trumps TTFB: HTTP streaming may slightly alter Time-To-First-Byte (TTFB) interpretations in monitoring dashboards, but drastically accelerates First Contentful Paint (FCP) and Largest Contentful Paint (LCP)—the metrics that dictate real user experience.
  • Defensive Proxy Tuning: Transparent streaming requires deliberate coordination across the entire delivery chain (Nginx, reverse proxies, CDN edge nodes, and compression buffers) to ensure early chunks are never held in transit.
