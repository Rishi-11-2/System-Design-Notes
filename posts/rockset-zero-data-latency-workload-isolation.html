1. The Real-Time Dual Holy Grail

In distributed database engineering, real-time analytics requires satisfying two opposing requirements simultaneously:

  1. Zero Data Latency (Data Freshness): When a business event occurs (e.g., an order is placed, an IoT sensor logs a temperature spike, or a fraud vector mutates), the update must be queryable via SQL in under 1 second without micro-batch or hourly ETL delays.
  2. Strict Workload Isolation: High-throughput streaming ingestion writes, latency-sensitive production user-facing queries, and heavy internal BI aggregations must run without resource contention. A rogue 60-second BI reporting query must never degrade the sub-50ms p99 SLA of production customer applications.
The Fundamental Trade-off: In traditional systems, data freshness and workload isolation are mutually exclusive. Keeping data fresh requires running writes and reads on the same cluster, which causes severe CPU and cache contention. Separating workloads across read replicas introduces minutes of replication lag.

2. Why Shared-Resource Architectures Fail

Traditional monolithic databases (PostgreSQL, MySQL, ClickHouse, Elasticsearch) execute writes and queries on shared physical hardware, creating inevitable resource collisions:

  • Buffer Pool Eviction Contention: High-volume streaming writes flush modified pages into memory buffer pools. This evicts the hot working set of active queries, forcing subsequent read queries to perform expensive random disk IO.
  • CPU Thread Starvation: Heavy analytical queries (e.g., multi-table hash joins or GROUP BY aggregations) saturate all available CPU cores. Incoming write threads are delayed, causing upstream Kafka/CDC pipelines to experience backpressure.
  • Replication Lag on Read Replicas: Offloading queries to traditional read replicas breaks the freshness guarantee. Under write bursts, replicas fall behind the primary by seconds or minutes, returning stale data.

3. Virtual Instances (VIs) Architecture

Rockset resolves this conflict through Virtual Instances (VIs). Enabled by the decoupling of compute and storage in RocksDB-Cloud, a Virtual Instance is a dedicated, independently scalable cluster of compute resources (CPU, RAM, and ephemeral NVMe cache) that operates on shared durable data stored in cloud object storage (AWS S3).

4. How Zero Data Latency (< 1s) Actually Works

If the Ingest VI and Query VIs run on completely separate compute nodes, how do Query VIs observe new records in under 1 second without downloading gigabytes of state from S3?

The Micro-Batch Metadata Synchronization Protocol

  1. Continuous Streaming Append: The Ingest VI pulls records continuously from Kafka. It appends records to local RocksDB MemTables and Write-Ahead Logs in memory.
  2. Micro-Batch SST Flushes: Every 500 milliseconds (or upon reaching size thresholds), the Ingest VI flushes an immutable SSTable and uploads it to AWS S3.
  3. Lightweight Manifest Broadcast: The Ingest VI does not broadcast raw data across the network. It publishes a lightweight Commit Manifest (containing SSTable S3 paths, document ID ranges, and delete tombstones) over a fast in-memory pub-sub channel. The manifest payload is only a few kilobytes.
  4. Instant Version Attachment: Query VIs receive the manifest in < 50ms and atomically update their internal RocksDB VersionSet. The new data is instantly queryable!
  5. Lazy / On-Demand Block Caching: Query VIs fetch only the requested columnar or inverted index blocks from S3 or local NVMe cache, avoiding full dataset transfer.

The total latency from Kafka event generation to SQL result reflection is bounded by:

$$T_{\text{freshness}} = T_{\text{ingest\_pull}} + T_{\text{memtable\_flush}} + T_{\text{manifest\_sync}} \approx 20\text{ms} + 500\text{ms} + 50\text{ms} \approx \mathbf{570\text{ ms}}$$

5. Eliminating Compaction Contention

In Log-Structured Merge-tree (LSM) engines, background compactions merge smaller SSTables into larger ones. This process consumes heavy CPU and disk bandwidth, causing tail latency spikes ("write stalls") in monolithic systems.

Serverless Compaction Isolation: Rockset isolates compactions completely into a separate, serverless Remote Compaction Fleet. Neither the Ingest VI nor the Query VIs run compactions locally. The remote fleet reads SSTables from S3, merges them, writes new SSTables back to S3, and updates the shared manifest, preserving 100% of Query VI CPU for user queries.

6. Multi-Workload Topology: Ingest vs Live Apps vs BI

By decoupling compute clusters while sharing durable S3 storage, organizations deploy specialized Virtual Instances tailored to distinct business requirements:

Virtual Instance Tier Hardware Sizing SLA / Latency Target Impact of Adjacent Workload Failures
Ingest VI Memory & Network Heavy (Optimized for JSON parsing). Sub-second streaming throughput. Zero impact from rogue queries or BI dashboards.
Production App VI Compute & NVMe Optimized (High IOPS cache). p99 < 50 ms (Customer-facing apps). Guaranteed 100% compute isolation; zero latency jitter.
Internal BI / Data Science VI Scalable Core Count (Elastic auto-pause). Seconds to minutes (Ad-hoc exploratory SQL). Can be shut down on weekends; zero cost waste.

7. Empirical Isolation & Latency Benchmarks

In stress testing, an Ingest VI was subjected to a 10× write burst (surging from 10k to 100k events/sec) while a BI VI simultaneously executed heavy full-collection aggregations. The latency of the Production App VI was monitored continuously:

Operating Condition Monolithic Architecture (Single Cluster) Rockset Virtual Instance Architecture
Baseline App Query (p99) 24 ms 22 ms
During 10× Ingestion Surge (p99) 185 ms (7.7× degradation) 23 ms (Zero degradation)
During Heavy BI Queries + Write Burst 1,240 ms (51× degradation) 24 ms (Completely Isolated)
Data Freshness (Kafka to Query) 18 – 45 seconds (Replication lag) < 1 second (Guaranteed)

8. Key Architectural Takeaways

  • Separate Compute from Shared Durability: Leveraging cloud object storage (S3) as the immutable single source of truth allows spinning up isolated compute clusters (Virtual Instances) without duplicating raw data.
  • Broadcast Metadata, Not Data: Achieving sub-second freshness across isolated clusters requires broadcasting lightweight commit manifests (< 50ms) rather than copying heavy data payloads.
  • Offload Compaction to Serverless Fleets: Removing LSM-tree compactions from query and ingestion nodes eliminates write stalls and guarantees predictable p99 query latencies.
  • Tailor Compute to Workload Profiles: Ingestion, customer-facing applications, and internal BI have conflicting latency and throughput profiles; dedicating isolated Virtual Instances guarantees robust operational SLAs.
