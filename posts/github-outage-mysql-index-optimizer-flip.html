How a Single MySQL Index Broke GitHub: Query Optimizer Inversion

The dangerous physics of Cost-Based Optimizers: how adding an innocent secondary index tricked MySQL into abandoning primary keys, triggering cascading 100% CPU lockups.

23 min read Arpit Bhayani Outage Dissections Verified 3-Page Companion PDF
📥 Download Technical PDF (3 Pages)
📌 Database Internals Incident Abstract

Developers routinely assume that adding an index to a relational database is a purely additive optimization: at best it accelerates queries; at worst it takes up disk space. In this classic infrastructure incident, GitHub added what appeared to be an innocuous secondary index to a core multi-million-row table. Instead of accelerating traffic, the new index tricked the MySQL Cost-Based Optimizer (CBO) into an catastrophic Index Flip. Rather than executing a 1ms indexed B+ tree seek, MySQL switched query execution plans to scan millions of rows under an ORDER BY ... LIMIT clause. Concurrently executed across thousands of web requests, database CPU surged to 100%, connections backed up, and the platform collapsed.

1. The Innocent Schema Migration

A feature team introduced an index to support a new query filter on a large relational table (e.g. issues or pull_requests). The table contained tens of millions of records and was queried thousands of times per second by high-frequency dashboard queries resembling:

-- Core High-Frequency Dashboard Query
SELECT id, title, state, created_at 
FROM issues 
WHERE repository_id = 12345 
ORDER BY created_at DESC 
LIMIT 30;

Prior to migration, the table had an existing composite index:

-- Existing Optimal Composite Index
INDEX idx_repo_created (repository_id, created_at);

Under idx_repo_created, MySQL performed a direct index seek on repository_id = 12345 and read the first 30 pre-sorted records in reverse chronological order. Execution time was 0.8ms.

2. The Index Flip: How the Optimizer Was Tricked

The migration added a new index on created_at alone to support a global timeline feature:

-- Newly Added Index
INDEX idx_created_at (created_at);
⚠️ The Optimizer Cost Calculation Trap

MySQL's Cost-Based Optimizer calculates two competing query execution paths:

  • Path A (idx_repo_created): Scan rows matching repository_id = 12345, already sorted. Cost estimate: $C_A$.
  • Path B (idx_created_at): Read the idx_created_at index backwards, hoping to find 30 rows matching repository_id = 12345 quickly, avoiding any sorting.

Because the query included LIMIT 30, the optimizer believed it only needed to read 30 rows from the new index! It failed to realize that repository 12345 was a low-volume repository whose records were scattered sparsely across 50,000,000 rows in the global created_at index. Path B resulted in scanning 12,000,000 index pages instead of 30 rows!

3. The Cascading Saturation Breakdown

Because this dashboard query was executed on nearly every repository pageview, the impact was immediate and non-linear:

  1. CPU Spike: Scanning millions of rows across hundreds of concurrent threads drove MySQL server CPU utilization from 20% to 100% in 15 seconds.
  2. Lock Contention: Long-running queries acquired read view locks, stalling the InnoDB purge thread and causing the undo log to balloon.
  3. Connection Queue Overflow: Web workers waited 8+ seconds for query results. The connection pool hit its max_connections cap (2,000 connections). ProxySQL began rejecting queries with Max connections reached.
  4. Health Check Timeouts: Orchestrator probes could not establish connections to execute heartbeats, falsely assuming the master had died and triggering chaotic automated failovers.

4. Engineering Solutions: Defeating Optimizer Inversion

Production systems employ multiple defense-in-depth mechanisms to protect against query optimizer plan flips:

Solution 1: Explicit Optimizer Index Hints (FORCE INDEX)

When an index is critical to platform liveness, do not leave selection to optimizer heuristics:

-- Force the composite index explicitly
SELECT id, title, state, created_at 
FROM issues FORCE INDEX (idx_repo_created)
WHERE repository_id = 12345 
ORDER BY created_at DESC 
LIMIT 30;
Solution 2: MySQL 8.0 Invisible Indexes

In modern MySQL versions, indexes can be created in an INVISIBLE state. The optimizer ignores the index during query planning while the storage engine maintains it in the background. Engineers can test queries explicitly using USE INDEX in staging before making it globally visible:

-- Create index invisibly first
CREATE INDEX idx_created_at ON issues (created_at) INVISIBLE;

-- Validate performance in production canary session:
SET SESSION optimizer_switch = 'use_invisible_indexes=on';
EXPLAIN SELECT ...; -- Verify no plan regressions occur!

-- Safely make visible:
ALTER TABLE issues ALTER INDEX idx_created_at VISIBLE;
Solution 3: Circuit Breaking Runaway Queries (max_execution_time)

Configure a hard execution ceiling on analytical or web queries to terminate runaway scans automatically before they starve CPU:

-- Enforce a 1000ms query execution ceiling
SET GLOBAL max_execution_time = 1000;

5. Systems Engineering Takeaways

  1. Indexes Are Not Purely Additive: Adding an index alters the statistical cost model of every query touching that table. A new index can inadvertently degrade existing queries from $O(\log n)$ to $O(n)$.
  2. Beware of ORDER BY ... LIMIT Optimization Traps: MySQL's optimizer treats LIMIT as an aggressive cost discount. If an index matches the ORDER BY column, the optimizer will frequently choose a massive index scan over an indexed WHERE filter.
  3. Automate EXPLAIN Diffing in CI/CD: Never deploy schema changes without automated query plan verification. Compare EXPLAIN plans on production clones before and after migrations to catch plan inversions before deployment.
