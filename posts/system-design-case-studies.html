📌 Real-World Architecture Blueprints

Extracted from chapters 10-17 of the System Design Notes, this article details production architectures for 7 complex distributed systems: Distributed Rate Limiter, Multi-Channel Notification Engine, URL Shortener (TinyURL) with collision avoidance, PasteBin / Gist object tiering, Real-time Fraud Detection Pipeline, Machine Learning Recommendation Engine, and a Distributed Web Crawler.

Case Study 1: Designing a Distributed Rate Limiter

1.1 Motive & Algorithms

Rate limiters protect servers against DDoS attacks, brute force login attempts, and runaway client scripts. The core algorithms include:

  • Token Bucket: A bucket holds up to $B$ tokens. Tokens refill at rate $R$ per second. Each request consumes 1 token. Allows burst traffic while bounding average rate. Widely used (Amazon API Gateway, Stripe).
  • Leaky Bucket: Requests enter a FIFO queue and leak out at a constant rate. Excess drops. Smoothes bursts into steady output.
  • Sliding Window Counter: Blends requests from previous window and current window: $$\text{count} = \text{current\_requests} + \text{previous\_requests} \times (1 - \text{elapsed\_fraction})$$ Extremely memory-efficient and eliminates boundary spikes.

1.2 Distributed Architecture with Redis

In distributed clusters with 50+ app servers, local in-memory counters fail because a client's requests hit different servers. The solution is a centralized Redis cluster using atomic Lua scripts:

Redis Lua Script: Atomic Sliding Window Rate Limit
local key = KEYS[1]
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])
local clearBefore = now - window

-- Remove timestamps older than window
redis.call('ZREMRANGEBYSCORE', key, 0, clearBefore)
local currentRequests = redis.call('ZCARD', key)

if currentRequests < limit then
    redis.call('ZADD', key, now, now)
    redis.call('EXPIRE', key, math.ceil(window / 1000))
    return 1 -- Allowed
else
    return 0 -- Rejected (429 Too Many Requests)
end

Case Study 3: Designing a URL Shortener (TinyURL)

3.1 Scale & Character Encoding

Requirements: Generate a 7-character short URL from a long URL. Redirection must happen in < 15ms. 100 million URLs generated per month.

  • Base62 Encoding: Using 62 alphanumeric characters ($[a-z, A-Z, 0-9]$).
  • With 7 characters, total possible unique combinations: $$62^7 = 3,521,614,606,208 \approx 3.5 \text{ Trillion URLs}!$$
  • At 100M URLs per month, 3.5 trillion URLs lasts for over 2,900 years.

3.2 Unique ID Generation via Range Reservation

How do we generate unique IDs without distributed lock contention or collision retries?

🎯 Range Reservation Pattern
  1. Maintain a coordinator (e.g. ZooKeeper or central MySQL table) managing ID ranges in blocks of 1,000,000 IDs.
  2. When Shortener Server A boots up, it requests a range: it gets $[1,000,000 \to 1,999,999]$.
  3. Server B boots up: it gets $[2,000,000 \to 2,999,999]$.
  4. Each server increments its local atomic counter in RAM ($O(1)$ with zero network RPCs).
  5. The integer is converted to Base62: integer 1000000 becomes Base62 4c92.
  6. Zero collision probability, zero distributed locking overhead!

Case Study 4: Designing PasteBin / GitHub Gist

Requirements: Users upload arbitrary text snippets, get a public shareable URL, optional expiration date, millions of daily reads.

  • Storage Tiering: Storing text blobs directly in a relational database bloats tables and exhausts buffer pool RAM.
    • Amazon S3 / Blob Storage: Holds the raw text content file. Extremely cheap, 99.999999999% durability.
    • Relational DB / DynamoDB: Holds lightweight metadata: paste_id, s3_key, user_id, expiration_time, created_at.
  • Pre-Signed URLs: Clients upload large files directly to S3 via pre-signed S3 URLs, completely bypassing application servers and saving network bandwidth.

Case Study 5: Financial Fraud Detection Pipeline

Credit card transactions require fraud evaluation in under 50 milliseconds before authorization.

  • Real-Time Path: Transaction event arrives $\to$ Fraud Inference Microservice loads pre-computed user profile from Redis (usual spending location, typical merchant categories, velocity) $\to$ Runs lightweight Random Forest / XGBoost model $\to$ Returns Score (Approve, Deny, Trigger 2FA) in < 30ms.
  • Offline Training Path: Transactions stream into Kafka $\to$ Apache Spark / Flink processes sliding window aggregates (e.g. 5 transactions in last 2 minutes across 2 countries) $\to$ Exports features to feature store $\to$ Periodically retrains models on Amazon S3 training data.

Case Study 6: Machine Learning Recommendation Engine

Powering personalized feeds (YouTube, Netflix, E-Commerce):

  1. Candidate Generation (Retrieval): Narrows 50 million catalog items down to top 500 candidates using Collaborative Filtering (user-item matrix embeddings, FAISS vector search).
  2. Scoring & Ranking: Heavy ML deep learning ranking model predicts Click-Through-Rate (pCTR) and Watch-Time for the 500 items.
  3. Re-ranking & Diversity: Injects diversity rules (not showing 5 videos from the same creator), removes previously watched items, applies freshness boosts.

Case Study 7: Designing a Distributed Web Crawler

Crawling billions of web pages across the public internet to build an inverted search index:

  • Seed URLs: High-authority starting points (e.g. Wikipedia, news domains).
  • URL Frontier: Manages which URLs to crawl next. Implements Politeness Policies (domain cooldown: waiting 5 seconds between requests to the same host) and Priority Queues (crawling breaking news before static pages).
  • Deduplication via Bloom Filters: Checking if a URL has already been visited using an in-memory Bloom Filter ($O(1)$ space and time).
  • Content Storage & Indexing: HTML is stripped of JavaScript/CSS, compressed, batched to S3, and words are mapped to document IDs in an inverted index stored in Elasticsearch.
