Redis Deep Dive — Single-Threaded Event Loop, RESP Protocol & Data Structures

📁 Category: In-Memory & Redis
← Back to All Notes
📌 In-Memory Data Store Internals

Redis (Remote Dictionary Server) is widely renowned for serving over 100,000 queries per second on a single CPU core with sub-millisecond latencies. This comprehensive 17-module deep dive extracts the complete inner mechanics of Redis: the single-threaded event loop, non-blocking I/O multiplexing, the RESP serialization wire protocol, key expiration mechanisms, memory eviction algorithms (Approximated LRU & LFU), persistence tradeoffs (RDB vs AOF), and compact in-memory data structures (SDS, Intset, Ziplist, Quicklist, Geohash, HyperLogLog).

Module 01: What Makes Redis Special?

  • In-Memory Primary Storage: Every dataset operation executes directly in RAM, bypassing disk seek and block serialization bottlenecks.
  • Single-Threaded Execution Engine: Core commands execute on a single main thread, entirely eliminating mutex contention, race conditions, context-switch overhead, and distributed deadlocks.
  • Rich Polymorphic Data Structures: Far more than a key-value store; natively supports Strings, Hashes, Lists, Sets, Sorted Sets (ZSet), Bitmaps, HyperLogLogs, and Geospatial indexes.
  • Event-Driven Asynchronous I/O: Leverages kernel event demultiplexing to service thousands of simultaneous client connections without thread-per-client overhead.

Module 02: Redis Serialization Protocol (RESP)

Redis communicates over TCP using the human-readable, binary-safe RESP (REdis Serialization Protocol). Every data type is identified by its first byte character:

Type Prefix Wire Format Example Description
Simple String + +OK Non-binary safe small status strings; terminated by CRLF.
Simple Error - -ERR unknown command 'FOO' Error messages returned by the server.
Integer : :1000 Signed 64-bit integer values.
Bulk String $ $5 hello Binary-safe strings up to 512MB. $-1 denotes a Null bulk string.
Array * *2 $3 GET $4 name Ordered collection of RESP elements. Used for command invocations.

Module 03: Non-Blocking I/O & IO Multiplexing

Why does Redis stay single-threaded? CPUs are rarely the bottleneck for in-memory caches; network I/O and memory bandwidth are.

Instead of spawning a blocking thread for each incoming socket connection (which consumes 1MB+ stack space per thread and triggers heavy OS context switches), Redis uses I/O Multiplexing (Linux epoll, macOS/BSD kqueue, Solaris evport):

  1. Sockets are marked non-blocking (O_NONBLOCK).
  2. Socket file descriptors (FDs) are registered with the kernel multiplexer.
  3. The kernel notifies the Redis event loop (aeProcessEvents) only when a descriptor is ready to read or write.
  4. Redis processes the pending buffer, executes the command against memory, writes the response to the output buffer, and proceeds to the next ready descriptor.

Module 04: Key Expiration Internals

When a key is set with a Time-To-Live (EXPIRE key 60), Redis stores the absolute expiration Unix timestamp in a separate expires dictionary (db->expires). Redis uses a two-pronged strategy to evict expired keys without blocking:

  • Passive (Lazy) Expiration: When a client queries a key (e.g., GET user:1), Redis first checks if the key exists in db->expires. If expired, Redis immediately deletes it and returns (nil).
  • Active (Periodic) Expiration: Running 10 times per second (10Hz) inside the serverCron cycle:
    1. Test 20 random keys with configured expirations.
    2. Delete all found expired keys.
    3. If more than 25% of the sampled keys were expired, repeat immediately! This ensures memory is reclaimed aggressively without letting expired keys accumulate.

Module 05: Memory Eviction Policies

When memory usage reaches maxmemory, Redis frees space using the chosen eviction policy:

  • noeviction: Returns out-of-memory errors on new write operations (default).
  • allkeys-lru: Evicts the least recently used keys across all keys.
  • volatile-lru: Evicts least recently used keys among those with an expire set.
  • allkeys-lfu: Evicts least frequently used keys across all keys.
  • volatile-lfu: Evicts least frequently used keys among those with an expire set.
  • volatile-ttl: Evicts keys with the shortest remaining Time-To-Live.
  • allkeys-random / volatile-random: Evicts random keys.

Module 06: Pipelining Mechanics

In standard request-response cycles, a client sends command 1, waits for network Round-Trip Time (RTT, e.g. 20ms), receives response 1, then sends command 2. 50 commands take $50 \times 20\text{ms} = 1000\text{ms}$.

Pipelining enables clients to queue 50 commands, transmit them as a single TCP packet burst, and read all 50 responses in one batch. Redis processes them in sequence in memory. Execution time drops from 1000ms down to ~25ms!

Module 07: Redis Persistence (RDB vs AOF)

Mechanism How It Operates Advantages Trade-offs
RDB (Redis Database) Point-in-time binary snapshot saved to disk (e.g. every 15 min). Forks a background child process via bgsave utilizing Linux Copy-on-Write (COW). Extremely compact; fast recovery on restart; zero parent thread disk I/O overhead. Data between snapshots (e.g. last 5-15 min) is lost if server crashes unexpectedly.
AOF (Append Only File) Logs every write command to an append-only log file on disk. Configured via fsync: always, everysec (recommended), or no. Maximum durability (at most 1 second of lost data with everysec); human-readable format. File size grows large (requires background AOF rewrite); slower restart replay time compared to RDB.
Hybrid Persistence Redis 4.0+: Combines RDB snapshot prefix with incremental AOF log tail during AOF rewrite. Fast restart times like RDB with minimal data loss like AOF. Default in modern Redis deployments.

Module 08: The Redis Object Model (robj)

Every key-value entry in Redis is wrapped in a C structure called redisObject:

C redisObject Structure
typedef struct redisObject {
    unsigned type:4;       // OBJ_STRING, OBJ_LIST, OBJ_SET, OBJ_ZSET, OBJ_HASH
    unsigned encoding:4;   // OBJ_ENCODING_RAW, OBJ_ENCODING_INT, OBJ_ENCODING_ZIPLIST, etc.
    unsigned lru:24;       // LRU clock or LFU frequency counter
    int refcount;          // Reference count for memory sharing
    void *ptr;             // Pointer to actual in-memory representation
} robj;

Small Integer Optimization: Redis pre-allocates and shares robj instances for integers between 0 and 9999 at startup. If 10,000 keys store the value 100, all 10,000 keys point to the exact same shared memory pointer, consuming zero additional heap space!

Module 09: Server Stats & Monitoring via INFO

Database statistics are crucial for operational visibility, monitoring health, automating precautionary scaling actions, and alerting on anomalies before service degradation occurs.

The INFO Command Architecture

The INFO command is the primary interface for inspecting Redis runtime telemetry. It formats output as human-readable and machine-parsable bulk strings partitioned into sections, with key-value pairs formatted as field:value terminated by newlines (\r\n).

Common telemetry sections provided by INFO include:

  • # Server: General information including Redis server version, process ID (PID), TCP port, uptime, and configured run mode.
  • # Clients: Number of connected client sockets, longest output buffer, and blocked client counts.
  • # Memory: Total allocated memory (used_memory), resident set size (used_memory_rss), fragmentation ratio, and memory allocator metadata.
  • # Stats: Cumulative processed connections, total commands processed, instantaneous operations per second (OPS), rejected connections, and keyspace hits/misses.
  • # Keyspace: Per-database key counts, expiration tracking, and average TTLs (e.g., db0:keys=4,expires=0,avg_ttl=0).
Production Prometheus & Grafana Ingestion Pipeline

In production deployments, operators do not query INFO manually. Instead, the Redis Exporter daemon runs alongside Redis (often on port 9121). It periodically issues INFO commands to Redis, transforms the raw bulk string fields into standard Prometheus metric exposition format, and exposes an HTTP /metrics endpoint. Prometheus scrapes this endpoint at regular scrape intervals, feeding Grafana time-series dashboards and alert managers.

Module 10: Internals of Approximated LRU

A true Least-Recently-Used (LRU) algorithm requires maintaining every key in a doubly-linked list. Every read operation moves the accessed node to the head of the list. In a cache holding 100 million keys, maintaining pointers and lock contention consumes massive memory overhead.

Redis implements Approximated LRU:

  1. Each robj stores a 24-bit timestamp (lru clock).
  2. When eviction is required, Redis randomly samples $N$ keys (default maxmemory-samples = 5).
  3. It maintains a 16-element candidate pool sorted by idle time ($\text{current\_time} - \text{lru}$).
  4. The key with the greatest idle time in the pool is evicted.
  5. With $N=10$, Approximated LRU matches theoretical true LRU within 1% accuracy while saving gigabytes of RAM!

Module 11: Signal Handling & Graceful Shutdowns

When a server process terminates—such as an operator issuing a CTRL+C in the console or a Kubernetes pod receiving an eviction notice—the database must terminate gracefully rather than dropping active client operations or corrupting data files.

POSIX Signal Handling Fundamentals

Signals are asynchronous notifications dispatched by the operating system kernel to a process to notify it of a specific system event. Redis registers dedicated signal handler routines to guarantee data integrity, flush active buffers, and close open sockets cleanly.

Graceful Termination Signals: SIGTERM and SIGINT

Both SIGTERM (standard termination request) and SIGINT (interrupt generated by CTRL+C) instruct Redis to initiate an orderly, graceful shutdown:

  1. Command Drainage: Ensures all currently executing commands finish execution completely.
  2. Persistence Flush: Flushes append-only file (AOF) buffers and writes an RDB snapshot to disk if configured.
  3. Resource Cleanup: Closes active client sockets and listening TCP/Unix domain descriptors.
  4. Unlink and Exit: Unlinks the PID file and exits cleanly with exit code 0.

Fatal Crash Signals: Diagnostic Core Dumps

When catastrophic faults occur, Redis intercepts hardware and OS exceptions rather than vanishing silently:

  • SIGSEGV: Segmentation fault caused by accessing invalid or out-of-bounds memory addresses.
  • SIGBUS: Bus error resulting from invalid physical memory addressing or alignment faults.
  • SIGFPE: Floating-point error such as arithmetic division by zero or integer overflow.
  • SIGILL: Illegal processor instruction that the CPU cannot decode or execute.

When any of these fatal signals are trapped, Redis invokes its crash reporting engine: it immediately dumps a comprehensive crash report to the log file and disk, including a full stack trace, CPU register dumps (EIP/RIP, ESP/RSP), and the internal state of the client connection that triggered the fault.

Ignored Signals: SIGHUP and SIGPIPE

Redis explicitly ignores SIGHUP (hangup signal sent when a controlling terminal closes) and SIGPIPE (broken pipe signal when writing to a disconnected socket descriptor). This intentional suppression prevents the server from unexpectedly crashing when administrative terminals disconnect or client network sockets close abruptly mid-write.

Modules 12-16: Advanced Compact Data Structures

Simple Dynamic String (SDS)

C strings are null-terminated arrays (char*), which suffer from $O(N)$ strlen lookups and buffer overflow risks. Redis uses SDS:

  • Stores explicit len ($O(1)$ length check) and alloc (preallocated buffer space).
  • Binary-safe: can store raw image bytes or serialized protobufs containing embedded null bytes (\0).

Ziplist & Quicklist

Standard linked lists waste 16-24 bytes of pointer overhead per element. A Ziplist stores sequential elements contiguously in a single flat memory buffer. To avoid reallocating huge buffers on large lists, Redis 3.2+ introduced Quicklist: a doubly-linked list where each node is a compact Ziplist chunk!

Module 13: SET Internals with Intset

Redis provides the SET data type, which represents an unordered collection of unique elements. By default, a set is implemented as a standard Hash Table (where keys are the set members and values are NULL). However, when a set contains exclusively integer values, Redis switches to a hyper-optimized compact data structure called Intset.

Intset Memory Layout

An Intset is stored as a contiguous, sorted flat array of uniform fixed-width integers without hash table buckets or node pointers. The layout consists of:

[ encoding (4 bytes) | length (4 bytes) | int_1 | int_2 | ... | int_N ]

The encoding field specifies the bit width of all stored elements: INTSET_ENC_INT16 (16-bit), INTSET_ENC_INT32 (32-bit), or INTSET_ENC_INT64 (64-bit).

Operational characteristics of Intset:

  • Membership Checks (SISMEMBER): Takes $O(\log N)$ time because the integer elements are strictly sorted, enabling rapid binary search lookups.
  • Insert and Delete: Takes $O(N)$ time. When adding or removing an element, Redis uses memmove to shift adjacent memory bytes left or right. Despite the linear movement cost, the absence of pointer overhead and memory fragmentation makes Intset exceptionally fast for small-to-medium collections.
  • Automatic Encoding Upgrades: If an existing 16-bit Intset receives a 32-bit integer, Redis reallocates the contiguous memory buffer, traverses the existing elements from right to left, converts them to 32-bit representations in-place without data loss, and inserts the new element. Downgrades are never performed.
  • Threshold Escalation: The configuration parameter set-max-intset-entries (default 512) caps the maximum number of items allowed in an Intset. Once element count exceeds this threshold or a non-integer string is added, Redis reallocates the data into a standard Hash Table (OBJ_ENCODING_HT).

Module 14: Geospatial Indexing with Geohash

Redis supports rich geospatial operations—such as GEOADD to register locations and GEORADIUS / GEOSEARCH to query points within a specified proximity radius (e.g., finding nearby drivers within 2 km). Because proximity queries require dynamic runtime bounding boxes with arbitrary zoom-in and zoom-out capabilities, Redis implements spatial indexing via Geohash.

The Geohash Principle: 2D Space Mapped to 1D Integer

A Geohash is a 52-bit integer that uniquely represents a coordinate point $(\text{latitude}, \text{longitude})$ on Earth. The foundational property of Geohash is that two points that are geographically close share a long common Geohash prefix. This reduces complex 2D geographical distance queries into fast 1D prefix and range matching.

How Redis computes and queries Geohash:

  1. Relative Coordinate Normalization: The Earth's coordinates ($\text{lat} \in [-85.05112878, 85.05112878]$, $\text{long} \in [-180, 180]$) are normalized into 32-bit unsigned integer offsets.
  2. Bit-Interleaving: The 32-bit latitude and 32-bit longitude offsets are interleaved bit-by-bit into a unified 64-bit (or 52-bit) integer:
    • Odd bits store the longitude representation.
    • Even bits store the latitude representation.
  3. Zoom Mechanics: Truncating bits from the least-significant end (right) corresponds to zooming out to a broader rectangular bounding box. Preserving more bits corresponds to zooming in with sub-meter spatial precision. Modern CPU architectures execute these interleaving transformations via hyper-fast 64-bit bitwise instructions without looping.
  4. Sorted Set (ZSET) Storage: Redis stores the 52-bit Geohash integer directly as the score inside a standard Sorted Set (backed by a Skip List). A radial proximity query computes the bounding box prefix ranges and performs logarithmic range scans ($O(\log N)$) across the skip list.

HyperLogLog

Used to estimate the unique cardinality of billions of items (e.g. unique website visitors) using only 12 kilobytes of memory with a standard error of 0.81%!

  • Hashes incoming items into a 64-bit bitstring.
  • Uses 14 bits to address 16,384 registers.
  • Estimates cardinality based on the maximum number of leading zeros observed across registers (probabilistic LogLog theorem).

Module 17: LFU With Approximate Counting

Least Frequently Used (LFU) protects against scan anomalies where a rarely accessed key is read once and stays in cache. Redis packs both the last access time and frequency into the 24-bit lru field:

  • 16 bits: Last Decr Time (ldt) — timestamp in minutes. Used to decay frequency over time.
  • 8 bits: Logarithmic Counter (logc) — Uses Morris Approximate Counting. Instead of incrementing on every access ($255$ max), the counter increments with probability $\frac{1}{1 + \text{counter} \times \text{lfu\_log\_factor}}$, allowing an 8-bit byte to represent up to 1,000,000 accesses!
