1. The Analytical Concurrency Challenge

In traditional analytical databases, executing a heavy SQL query involving multi-way joins and aggregations requires significant memory allocations and all-core CPU utilization. In single-cluster or shared-resource databases (such as ClickHouse, Presto/Trino, or traditional data warehouses), concurrent queries compete for thread pools and buffer cache frames.

When customer-facing applications demand hundreds or thousands of concurrent analytical queries per second (e.g., e-commerce personalized search, live financial dashboards), traditional query engines encounter head-of-line blocking, lock queues, and severe tail latency spikes.

The Rockset Solution: Decouple query compute completely from storage state. By employing stateless Aggregator pools that compile distributed query plans and execute push-down operations across stateful Leaf nodes, query compute scales horizontally on demand in seconds without re-sharding storage.

3. Cost-Based Optimization & Predicate Pushdown

Rockset's Cost-Based Optimizer (CBO) leverages metadata continuously maintained by the Converged Index—such as hyperloglog cardinality estimations, min/max values, and null counts—to transform logical relational expressions into optimal physical operators.

1. Aggressive Predicate & Projection Pushdown

Rather than pulling raw records across the network into the Aggregator, the optimizer pushes filtering predicates and mathematical projections directly down to the Leaf nodes hosting the relevant RocksDB shards. If a query filters WHERE created_at > 1704067200 AND status = 'COMPLETED', the Leaf node uses its local Inverted Index to isolate qualifying rows before paging any data into memory.

2. Intelligent Index Selection

For every clause, the CBO calculates the estimated cost of index access paths:

  • High Selectivity (< 5% match rate): Route through the Inverted Search Index. Seek matching document IDs in RocksDB in microseconds.
  • Low Selectivity / Aggregation (> 20% match rate): Route through the Columnar Index. Execute contiguous SIMD vector scans over columnar chunks.
  • Point Lookup by Primary Key: Route directly to the Row Store in RocksDB via an $O(1)$ prefix seek.

4. Leaf-Level Vectorized Execution (SIMD)

Traditional database engines use the classic Volcano Iterator Model, where each relational operator calls next() to evaluate one tuple at a time. This introduces massive virtual function call overhead, poor instruction cache locality, and zero CPU SIMD utilization.

Rockset's Leaf execution engine operates on vectorized batches of 1024 values. Implemented in modern C++, the engine compiles vector kernels that leverage hardware SIMD instructions (Intel AVX2, AVX-512, and ARM Neon):

// Conceptual SIMD Vectorized Sum Kernel over Columnar Chunk
void vectorized_sum_kernel(const double* __restrict__ values, 
                           const uint8_t* __restrict__ null_bitmap, 
                           size_t count, 
                           double& accumulator) {
    __m256d acc = _mm256_setzero_pd();
    size_t i = 0;
    
    // Process 4 double-precision floats per CPU cycle via AVX2
    for (; i + 4 <= count; i += 4) {
        __m256d val_vec = _mm256_loadu_pd(&values[i]);
        acc = _mm256_add_pd(acc, val_vec);
    }
    
    // Horizontal reduction of vector register into scalar
    double temp[4];
    _mm256_storeu_pd(temp, acc);
    accumulator += temp[0] + temp[1] + temp[2] + temp[3];
    
    // Handle scalar remainder
    for (; i < count; ++i) {
        accumulator += values[i];
    }
}

Because the columnar index stores numeric values contiguously in local NVMe blocks, vectorized scans saturate the hardware memory bus, scanning hundreds of millions of records per second per Leaf core.

5. Distributed Joins: Broadcast vs. Hash Shuffle

Unlike search engines that forbid joins, Rockset supports full distributed ANSI SQL joins. The Aggregator selects the join algorithm based on cost and table cardinality:

A. Broadcast Hash Join

When joining a massive fact collection (e.g., 500M transactions) with a smaller dimension collection (e.g., 50k merchants), the Aggregator pulls the small dimension table, builds an in-memory hash table, and broadcasts the entire hash table to all Leaf nodes. Each Leaf evaluates the join locally against its local fact shards with zero network data shuffling.

B. Distributed Hash Shuffle Join

When joining two massive collections (e.g., orders and order_items), neither fits in a single node's RAM. The Aggregator configures an intermediate hash shuffle: Leaf nodes partition intermediate result sets by $\text{hash}(\text{join\_key}) \pmod K$ and stream them across worker nodes, enabling horizontally scalable distributed hash joins.

6. On-Demand Horizontal Scaling of Aggregators

The core superpower of Rockset's Aggregator tier is complete state-independence. Aggregators do not hold shard replicas, do not host local storage, and do not manage database durability.

Elastic Compute Scaling: If an application experiences a 10× traffic spike during a flash sale, Kubernetes or the cloud autoscaler provisions additional Aggregator containers. New Aggregators register with the cluster coordinator and begin serving SQL queries immediately (< 3 seconds boot time) without rebalancing storage shards or transferring data across the network.

8. Key Architectural Takeaways

  • Separate Coordination from Storage: Decoupling stateless Aggregators from stateful Leaves enables on-demand horizontal compute scaling in seconds.
  • Push Predicates to the Edge: Pushing filters and partial aggregations down to Leaf nodes eliminates 90% of inter-node network data transfer.
  • Vectorized SIMD Execution is Mandatory: Modern analytics engines must ditch tuple-at-a-time Volcano models in favor of 1024-value AVX vector blocks to saturate memory bandwidth.
  • Hybrid Join Strategies Enable Real-Time SQL: Dynamically choosing between broadcast joins and distributed hash shuffles allows real-time execution of complex multi-table SQL queries.
